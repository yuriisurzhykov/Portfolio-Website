# views/admin-login — AdminLoginPage

## 2026-07-19 — Фаза 4: `?from=` redirect + `router.refresh()` перед навигацией

**Что нужно сделать.** После логина администратор должен попасть туда,
куда изначально шёл (если его перекинул `proxy.ts` с `?from=/admin/work`),
а не всегда на дефолтную страницу.

**Как сделано.** `from` читается через `useSearchParams()` (поэтому
страница обёрнута в `<Suspense>` в `app/admin/login/page.tsx` — таково
требование Next.js для `useSearchParams()`), с проверкой
`from.startsWith("/admin")` — простая защита от open redirect (небезопасно
слепо доверять произвольному значению query-параметра, взятому из URL, как
адресу для редиректа).

`router.refresh()` вызывается ПЕРЕД `router.push(redirectTo)`, не после и
не вместо: Router Cache Next.js может отдать уже закэшированный,
"недо-аутентифицированный" рендер маршрута, если администратор уже
заходил на него в этой сессии до логина — `refresh()` форсирует реальный
повторный запрос с уже свежей cookie.

**Понятность для другого разработчика.** Комментарий на
`useRedirectTarget()` объясняет и источник `from` (`proxy.ts`), и почему
есть проверка префикса.

**SOLID.** Не применимо напрямую — простой компонент формы.

## 2026-08-09 — Бесконечный редирект на логин при неверном пароле

**Симптом, с которым пришёл пользователь.** Попытка войти уводила обратно
на форму входа, и адрес рос с каждой попыткой:

```
/admin/login?from=%2Fadmin%2Flogin%3Ffrom%3D%252Fadmin%252Flogin%253Ffrom%253D%25252Fadmin
```

**Первопричина — неверная классификация 401.** `adminApi.login()` шёл
через общий `request()`, который трактует 401 как «сессия умерла»:
пытается втихую обновить токен, а затем делает жёсткий
`window.location.assign('/admin/login?from=' + pathname + search)`. Но на
`/api/auth/login` 401 означает «неверный логин или пароль» — сессии,
которая могла бы умереть, ещё не существует. Реакция была не просто
бесполезной, а вредной вдвойне: жёсткая перезагрузка стирала сообщение об
ошибке до того, как его успевали прочитать, а поскольку `from` собирается
из `pathname + search`, редирект на логин **со страницы логина** вкладывал
предыдущее значение внутрь нового и заново его кодировал — отсюда рост
без предела.

**Три правки, каждая закрывает свой слой.**

1. `login` больше не идёт через `request()`, а через
 `requestWithoutSessionRecovery` — без обновления токена и без редиректа,
 401 просто доезжает до вызывающего с текстом сервера. Ровно та же логика,
 которую в этом файле уже давно применяет `refresh`: операция, которая
 САМА является восстановлением, не может проходить через то, что это
 восстановление запускает.
2. `redirectToLogin()` ничего не делает, если мы уже на `/admin/login`.
 Это не «на всякий случай»: именно оно ограничивает рост `from` для любого
 будущего 401 на этой странице.
3. `resolveRedirectTarget` (новый чистый модуль) отказывается принимать
 `from`, указывающий на саму страницу логина. Без этого УСПЕШНЫЙ вход по
 старой ссылке отправлял бы обратно на форму — со стороны неотличимо от
 «не сработало». Заодно правило переехало с наивного
 `from.startsWith("/admin")` на `isSafeRelativePath` — тот же хелпер, что
 уже используют страницы статусов, — так что `//evil.example` отсекается
 явно, а не по случайности.

**Тест сначала оказался декоративным, и это стоит записать.** Первый
вариант e2e проверял «алерт виден и URL не изменился» — и проходил ДАЖЕ с
восстановленным багом, потому что правка №2 сама по себе гасит цикл, а
правка №1 влияет лишь на ТЕКСТ сообщения. Утверждение усилено до точного
текста «Invalid email or password.»: с багом там оказывалось «Your session
has expired. Please sign in again.» — сообщение о протухшей сессии
человеку, который ни разу не входил. После усиления тест проверен обоими
способами: он падает и при возврате правки №1, и при возврате правки №2.

**Понятность для другого разработчика.** Правило «куда можно вернуться
после входа» вынесено из хука в чистую функцию `redirect-target.ts` —
её видно целиком, она покрыта тестами и попадает в мутационное
тестирование, чего нельзя было сделать с логикой внутри React-хука.

**SOLID.** Interface Segregation на уровне модуля: `request()` и
`requestWithoutSessionRecovery` — два разных контракта для двух разных
смыслов 401, вместо одного «универсального» с флагом.
