# views/admin-post-editor — PostEditorPage

## 2026-08-09 — Черновик/публикация разведены: autosave больше никогда не пишет в живой пост

**Что нужно сделать.** Живой баг, пойманный пользователем: редактируешь
уже ОПУБЛИКОВАННЫЙ пост (удаляешь абзац, чтобы переписать) — а
трёхминутный autosave (см. запись 2026-07-31 ниже) успевает сохранить
именно этот промежуточный, наполовину стёртый вид ДО того, как правка
закончена. Если в этот момент оборвётся сессия (например, продолжаешь с
телефона и там же всё стирается) — восстановить нечего, читатели уже
видят битую страницу. Причина — `updatePost` (backend) писал прямо в
живую строку `Post`, autosave и "опубликовано" были одним и тем же
действием.

**Как сделано.** `updatePost` переименован в `savePostDraft` и физически
не может тронуть живую строку — он только сохраняет `ContentDraft`
(`backend/src/content/README.md`'s дневник за эту же дату). Единственная
кнопка Publish/Unpublish превратилась в Publish/Update/Unpublish:
- **Publish** (пост никогда не публиковался) или **Update** (уже
  опубликован, есть черновик) — это ОДИН и тот же эндпоинт
  (`adminApi.publishPost`), просто разная подпись кнопки в зависимости от
  `lifecycleState`. Именно этот клик — единственный момент, когда
  черновик реально долетает до читателей.
- **Discard changes** — появляется только когда `hasUnpublishedChanges`
  истинно; откатывает форму и `<BlockEditor>` целиком на живой контент
  (`adminApi.discardPostDraft`), без единого запроса на публикацию.
- **Preview** — открывает `/journal/[slug]?preview=1` в новой вкладке
  (см. `(site)/journal/[slug]/page.tsx`) — тот же компонент, что видят
  читатели, просто с черновиком вместо живого контента.
- **History** — ведёт на новый `/admin/journal/[slug]/history`
  (`views/admin-post-history`), список опубликованных версий с "Load into
  draft".

**Slug теперь редактируется как ПЕРЕИМЕНОВАНИЕ, не мгновенное действие.**
Раньше `updatePost` мог сменить живой slug прямо во время автосейва, и
`onSlugChanged` уводил URL страницы редактора вслед за ним. Теперь
`AdminPostDetail.draftSlug` (черновик, может отличаться от `slug`) — то,
что видит и редактирует форма; `currentSlug` (состояние компонента)
навсегда закреплён за ЖИВЫМ, маршрутизируемым `slug` до тех пор, пока
рендер не подтвердит реальное переименование (`handlePublish` сравнивает
`result.slug` с `currentSlug` и только тогда делает `router.replace`).
`onSlugChanged` хука `useAutosaveDraft` теперь фактически срабатывает
только один раз — при самом первом создании поста (`savePostDraft` всегда
возвращает НЕИЗМЕННЫЙ живой `slug`, см. его комментарий в
`admin-posts.ts`).

**Auto-unpublish уведомление (2026-07-31, ниже) удалено вместе с самой
фичей** — оно существовало только потому, что мягкое сохранение могло
испортить УЖЕ опубликованный пост; черновик больше не может этого сделать
физически, поэтому и предохранитель, и уведомление о нём стали
бессмысленными.

**`<BlockEditor key={contentVersion}>` — принудительный remount, не
попытка сделать компонент контролируемым.** `Discard changes`/восстановление
из истории обязаны показать НОВОЕ содержимое, а `<BlockEditor>` читает
`initialBlocks` только один раз при монтировании (см.
`shared/ui/block-editor/README.md`) — единственный способ заставить его
перечитать проп без переписывания самого компонента — сменить `key`,
что React трактует как "это другой элемент", и монтирует заново.

**Понятность для другого разработчика.** Комментарий у `onSaved`
(`useAutosaveDraft`'s опции) прямо объясняет, почему проверка
`currentSlug !== null` внутри замыкания отличает первое создание от
последующих правок — без него неочевидно, почему `hasUnpublishedChanges`
не взводится сразу при первом сохранении.

**Нагрузка.** Не увеличилась — тот же дебаунс, тот же один HTTP-запрос на
сохранение; просто конечная точка теперь пишет JSON-блоб вместо
Document/Block транзакции (дешевле, не дороже).

**Расширяемость/заменяемость.** Кнопки Discard/Preview/History — три
независимые, узкие функции компонента, каждая со своим API-вызовом; ни
одна не переиспользует состояние другой, так что удалить/добавить любую
из них не требует трогать остальные.

**Миграция/отказоустойчивость.** Ни одной миграции формы — `FormState`/
`toFormState` не изменили форму, только источник поля `slug` (теперь
`draftSlug ?? slug`, не просто `slug`).

**SOLID.** Open/Closed на уровне хука: `useAutosaveDraft` не изменился ни
на строку — весь этот рефакторинг сделан ИСКЛЮЧИТЕЛЬНО за счёт того, ЧТО
передаётся в его `create`/`update`, а не как.

## 2026-07-31 — Фаза 3 (мгновенный черновик + непрерывный autosave): убран единственный Submit, добавлен `useAutosaveDraft`

**Что нужно сделать.** По плану: первый символ, введённый в Title, должен
создать реальную запись в БД (не клик "Create post"), а каждое дальнейшее
изменение — сохраняться в фоне, без явного "Save changes". Разрыв
соединения посреди набора текста не должен стирать несохранённое.

**Как сделано.** Подключён `useAutosaveDraft<PostInput, PostSummary>`
(`shared/lib/use-autosave-draft.ts`, новый — см. его README) —
`buildInput()` собирает `PostInput` из ТЕКУЩЕГО `form` плюс
`blockEditorRef.current?.getBlocks()`, `isEmpty` — пустой `title`.
`update()`/`updateTitle()` (уже существовавшие обработчики полей) теперь
дополнительно вызывают `autosave.scheduleSave()` — единственное изменение
в них, форма как структура данных не тронута. `<BlockEditor>` получил
`onChange={autosave.scheduleSave}` (см. `shared/ui/block-editor/README.md`'s
одноимённая запись) — тело поста тоже autosave'ится, без изменения
"неконтролируемого" дизайна редактора.

**`handleSubmit`/кнопка "Create post"/"Save changes" удалены целиком**, не
просто скрыты — сохранять стало нечего явно нажимать. `<form>` остался
(не `<div>`) с `onSubmit={(e) => e.preventDefault()}` — единственная его
роль теперь чисто защитная: без реального сабмита `<form>` с одним
текстовым полем всё ещё неявно "отправляется" по Enter в браузере, что без
перехвата вызвало бы настоящую навигацию/перезагрузку страницы.

**`router.push` после сохранения удалён** — переход на список
(`/admin/journal`) теперь только через явную кнопку "Back to list"
(переименована из "Cancel" — это больше не отмена, autosave уже всё
сохранил). Единственное МЕСТО, где всё ещё есть программная навигация —
`onCreated`, вызывающий `router.replace()` на реальный `/[slug]/edit`-урл
сразу после первого успешного создания.

**Индикатор "Saving… / Saved just now / Save failed — retrying"** — просто
рендерит `autosave.status` через маленькую чистую функцию
`autosaveStatusLabel()`, рядом с `<StatusToggle>` в шапке (не внизу формы —
пост может быть длинным, индикатор должен быть виден без скролла).

**Auto-unpublish уведомление (Фаза 2) переехало из `handleSubmit` в
`onSaved`.** Раньше сравнение "было PUBLISHED, стало DRAFT" происходило
один раз, после явного сабмита; теперь оно происходит после КАЖДОГО
autosave — `onSaved(result)` читает `lifecycleState` из замыкания ТЕКУЩЕГО
рендера (обновляется каждый рендер за счёт собственного "always latest
options" паттерна хука — см. его README), так что сравнение всегда
актуально, даже когда результат приходит спустя несколько последующих
рендеров.

**Publish теперь сначала делает `flush()`.** Строгая проверка публикации
(`postPublishSchema`, backend) читает то, что УЖЕ в базе (publish не
принимает тело запроса) — значит, любая правка, всё ещё сидящая в
debounce-окне на момент клика "Publish", должна долететь ПЕРЕД самим
запросом публикации, иначе публикация проверит устаревшее содержимое.

**Дефолт `status` формы — `"upcoming"`, не `"published"`.** Новый пост —
DRAFT (`lifecycleState`, Prisma-дефолт) до явной публикации; дефолтить
публичный `status` в `"published"` в этот же момент было противоречием,
оставшимся с тех времён, когда поля `lifecycleState` ещё не существовало,
а не осознанным выбором. Свободно редактируется в любую сторону с первого
рендера.

**Понятность для другого разработчика.** Комментарий у `onCreated`
объясняет, почему навигация — забота ВЫЗЫВАЮЩЕЙ страницы, а не самого
хука (хук ничего не знает про `/admin/journal` конкретно). Комментарий у
`<form onSubmit>` объясняет, что это защита от неявного submit-on-Enter,
а не забытый обработчик.

**Расширяемость/заменяемость.** `PostEditorPage` не изменил форму
`FormState`/`toFormState` вообще — autosave подключён СНАРУЖИ существующих
данных формы, как дополнительный слой поверх уже существующих
`update()`/`updateTitle()`, а не переписыванием модели.

**Миграция/отказоустойчивость.** Провал сохранения (`onError`) показывает
понятную ошибку И автоматически повторяет попытку (см. хука README) — не
требует от админа лишний раз нажать что-то, чтобы правки долетели после
временного сбоя сети/БД.

**SOLID.** Dependency Inversion: `PostEditorPage` передаёт свои
`adminApi.createPost`/`updatePost` в хук как аргументы — хук зависит от
абстрактной сигнатуры, не от конкретного API-клиента.

## 2026-07-31 — Фаза 2 (lifecycle state machine): Publish/Unpublish + auto-unpublish notice

**Что нужно сделать.** `createPost` теперь always создаёт `lifecycleState:
DRAFT` (Prisma-дефолт, backend/src/content/README.md) — форма больше не
делает пост видимым сама по себе, нужен явный способ его опубликовать/
снять с публикации прямо из редактора.

**Как сделано.** Локальный `lifecycleState` (`useState`, инициализирован
из `initialPost?.lifecycleState`, только для уже сохранённого поста —
у ещё не созданного просто нет состояния публикации) + `<StatusBadge>`
("Draft"/"Published") рядом с кнопками "Add translation"/"Delete". Кнопка
("Publish" если DRAFT, "Unpublish" если PUBLISHED) вызывает
`adminApi.publishPost`/`unpublishPost` — новые узкие эндпоинты (см.
backend/src/content/README.md), без тела запроса, обновляет локальный
`lifecycleState` из ответа.

**Осознанное отклонение от общего правила "Save всегда редиректит на
список".** Redirect после `handleSubmit` остаётся без изменений В ОБЫЧНОМ
случае — полный отказ от редиректа на каждое сохранение (индикатор
"Saving…"/автосейв) — это Фаза 3 плана, не эта. НО: если backend'овский
safety-net (`updatePost`) молча снял пост с публикации из-за мягкого
сохранения (стёрли обязательное поле у уже опубликованного поста),
`handleSubmit` теперь остаётся на странице и показывает явный `notice`
вместо редиректа — редирект в этом одном случае скрыл бы единственный
шанс администратора это заметить (уведомление всё равно исчезло бы при
переходе на список). Отдельное состояние `notice` (не `error`) — это
успешное сохранение с побочным эффектом, не сбой.

**Понятность для другого разработчика.** Комментарий у `wasPublished`/
проверки `result.lifecycleState === "DRAFT"` в `handleSubmit` прямо
объясняет, почему именно этот один путь не редиректит, а не оставляет
читателя гадать, почему тут вдруг `return` без `router.push`.

**SOLID.** Не меняет форму данных `FormState`/`toFormState` вообще —
`lifecycleState` живёт в собственном `useState`, параллельно, а не как
поле формы: оно не участвует в обычном сабмите (`PostInput` по-прежнему
не содержит lifecycle-полей, см. backend's `postDraftInputSchema`), только
в двух отдельных, узких действиях.

## 2026-07-19 — Фаза 4: один компонент для create И edit

**Что нужно сделать.** `/admin/journal/new` и `/admin/journal/:slug/edit` —
две страницы, но фактически одна и та же форма с разным начальным
состоянием и разным API-вызовом при сохранении.

**Как сделано.** Один `PostEditorPage({initialPost?})` — `initialPost`
отсутствует для create, присутствует для edit. Внутри — единственная
ветка `if (isEditing) updatePost(...) else createPost(...)`, а не два
отдельных компонента с продублированной разметкой формы. Форма всегда
отправляет ВЕСЬ объект целиком (`PostInput`), даже при редактировании —
не PATCH с частичными полями — тот же принцип "простая админка", что и
в `replaceDocumentContent` на backend (весь список блоков целиком, не
diff).

Все мутации идут через `adminApi.createPost`/`updatePost`/`deletePost`
(`shared/lib/admin-api.ts`) — обычный `fetch()` на `/api/admin/posts`, не
Next.js Server Action, ровно как того требует план Фазы 4 ("тот же API,
которым сможет пользоваться будущее мобильное приложение").

**Понятность для другого разработчика.** `toFormState(post?)` — единственное
место, которое переводит `AdminPostDetail | undefined` в состояние формы
(включая пустые значения по умолчанию для create) — без него значения по
умолчанию для новой формы были бы разбросаны по инициализаторам `useState`.

**Нагрузка.** Не применимо — обычная клиентская форма.

**Расширяемость/заменяемость.** Блочный редактор (`shared/ui/block-editor`)
подключен как есть, без Post-специфичной обёртки — тот же компонент
использует `WorkEditorPage` для кейс-стади.

**Миграция/отказоустойчивость.** Ошибки API (`AdminApiError`, включая
409 при занятом slug и 400 при невалидных данных) показываются прямо под
формой, без потери введённых данных — в отличие от, например, редиректа
на страницу ошибки, который заставил бы администратора набирать текст
поста заново.

**SOLID.** Single Responsibility: `PostEditorPage` не знает, как именно
блоки превращаются в JSON для API — это инкапсулировано в
`draftToBlockInput` (`shared/ui/block-editor`), вызывается один раз перед
отправкой.

## 2026-07-19 — Английский-только + BlockNote + "Add translation"

**Что нужно сделать.** По плану "WYSIWYG-редактор + переводы как отдельные
страницы": эта форма — только английский контент; перевод — отдельный
экран, не поле рядом.

**Как сделано.** `FormState`/`toFormState` больше не держат `{en, ru}` —
`title`/`category`/`excerpt` теперь простые строки (`post.title.en`, не
весь объект), `LocalizedInputField`/`LocalizedTextareaField` заменены на
обычные `Input`/`Textarea` (см. `shared/ui/form/README.md`'s запись про их
удаление). `updatePost` (backend) сам сохраняет существующий `ru`, если
он уже есть — эта страница физически не может его затронуть, ей просто
негде показать это поле.

Кнопка "Add translation"/"Edit translation" (текст зависит от того, есть
ли уже `post.title.ru`) ведёт на `/admin/journal/:slug/translate` —
отдельный экран (`admin-post-translate`), отдельный API-вызов
(`translatePost`), отдельный `<BlockEditor>` на русское тело. Кнопка
показывается только в режиме редактирования (`isEditing`) — у ещё не
сохранённого поста просто нет slug, на который вести.

Блочный редактор — `<BlockEditor ref={blockEditorRef} initialBlocks=.../>`
(`shared/ui/block-editor`, полностью переписан на BlockNote — см. его
README) вместо `BlockListEditor`/`blocks`/`onChange`. `handleSubmit` читает
`blockEditorRef.current?.getBlocks()` один раз при отправке — компонент не
контролируемый, см. `BlockNoteEditor.tsx`'s комментарий про то, почему
`ref`, а не `value`/`onChange`.

**SOLID.** Не изменилось: `PostEditorPage` всё ещё не знает, как блоки
превращаются в JSON — теперь это `editorBlocksToBlockInputs` (внутри
`BlockEditor.getBlocks()`), вызывается так же один раз перед отправкой.

## 2026-07-19 — Живая обратная связь пользователя: автослаг, статичная дата, цветной статус, chips-категория

**Что нужно сделать.** Пользователь, попробовав форму создания живьём,
дал шесть отдельных замечаний: slug должен генерироваться сам из
заголовка; дата должна быть автоматической, статичным полем сверху, а не
полем ввода; у статуса должен быть цветовой индикатор прямо в форме;
"Date label" — непонятное поле, лучше просто форматировать дату создания;
категория должна выбираться из уже существующих значений как chips;
excerpt — непонятно, что это.

**Как сделано, по каждому пункту:**

1. **Slug** — `slugify()` (`shared/lib/slugify.ts`, новый — в репозитории
   раньше не было утилиты для этого) вызывается на каждое изменение
   `Title`, пока slug не "трогали" руками (`slugTouched`, `useState`,
   стартует `true` для уже существующего поста — retitling не должен
   молча ломать существующий URL, `false` для нового). Поле остаётся
   видимым и редактируемым (не скрыто целиком) — админ может поправить
   автосгенерированный slug, если он не понравился, просто не должен его
   писать с нуля каждый раз.
2. **Дата** — вынесена из формы в шапку страницы, как обычный текст
   ("Created Feb 11, 2026" в режиме редактирования, "Will be dated Feb
   11, 2026 — set automatically on save" для нового поста — превью, не
   ввод) — см. `backend/src/content/README.md`'s одноимённую запись:
   `date` теперь не существует как поле формы вообще, backend сам его
   генерирует.
3. **Цвет статуса** — `<StatusToggle>` (`shared/ui/status-toggle`, новый
   слайс — см. его README) вместо `<Select>`: тот же компонент, что уже
   красил статус в списках (`AdminJournalListPage`), теперь и в самой
   форме редактирования, причём это одновременно индикатор И контрол
   смены статуса, не два раздельных представления одного состояния.
4. **Date label** — удалено полностью, не просто из формы: см.
   `backend/src/content/README.md`.
5. **Category** — `CategoryPicker` (локальный компонент в этом файле —
   только один потребитель, не оправдывает отдельный слайс): chips по
   каждому уже использованному значению (`existingCategories`, проп из
   `getDistinctPostCategories()`, backend) — клик заполняет обычный текстовый
   `<Input>` под ними, который и остаётся единственным источником истины
   для `form.category`; если нужной категории в списке нет — просто
   печатается новая, chips это подсказка, не ограничение.
6. **Excerpt** — не удалён (это реальный, отдельный от лида текст —
   тизер на `/journal`, который видят посетители, ДО того как открыть сам
   пост, см. `views/journal-list/JournalListPage.tsx`), просто получил
   явный `hint` в `<Field>`, объясняющий, где именно он показывается.

**Понятность для другого разработчика.** Комментарий у `slugTouched`
явно объясняет, почему это НЕ то же самое поведение для create и edit —
без него неочевидно, зачем стартовое значение `useState` зависит от
`isEditing`.

**SOLID.** `CategoryPicker` — Single Responsibility в миниатюре: он не
знает, откуда взялся список категорий (просто проп), не знает, что
происходит с выбранным значением дальше (просто `onChange`) — как и сам
`slugify()`, который ничего не знает про формы вообще, просто строка →
строка.

## 2026-07-20 — "Read minutes" — туда же, куда уже уехала дата: статичный текст, авто-оценка

**Что нужно сделать.** Пользователь: `readMins` должен стоять статичным
текстом рядом с "Created", и сам read time должен считаться
автоматически — то же требование, что уже применено к `date` (см. запись
"Живая обратная связь..." выше), теперь к `readMins`.

**Как сделано.** Поле "Read minutes" (`<Input type="number">`) удалено из
формы целиком — `estimateReadMins()` (backend, `reading-time.ts`) считает
его из `blocks` на каждое сохранение, форма больше не может его
переопределить (нет такого поля в `PostInput`, см.
`backend/src/content/README.md`). В шапке рядом с "Created {date}"
добавлена вторая строка того же стиля: `~{initialPost.readMins} min read`
для существующего поста, "Read time — estimated automatically on save"
для нового (там пока ничего не сохранено, значит и оценивать не из чего
— тот же принцип, что уже применялся к дате: "Will be dated X — set
automatically on save").

**Осознанное ограничение — не живой пересчёт по мере набора текста.**
Оценка показывает `initialPost.readMins` (то, что backend посчитал на
момент ПОСЛЕДНЕГО сохранения), не live word count по текущему состоянию
`<BlockEditor>` — тот компонент намеренно "неконтролируемый" (см.
`shared/ui/block-editor/README.md`'s объяснение про `getBlocks()` вместо
`value`/`onChange`, специально чтобы не гонять `blocksToMarkdownLossy` на
каждую нажатую клавишу). Слушать живой word count означало бы отменить
это архитектурное решение ради цифры, которая обновится сама через пару
секунд после следующего сохранения — цена того не стоит. `title`-атрибут
у текста явно объясняет это ("recalculated every time you save, not
editable here"), а не оставляет пользователя гадать, почему число не
двигается при наборе текста.

**SOLID.** Не изменилось структурно — `PostEditorPage` и раньше не знало,
как блоки превращаются в JSON, теперь оно точно так же не знает, как
вычисляется `readMins` — обе детали инкапсулированы на backend.
