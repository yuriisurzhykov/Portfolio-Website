# views/admin-post-history — PostHistoryPage

## 2026-08-09 — Новый слайс: список опубликованных версий + "Load into draft"

**Что нужно сделать.** Часть draft/publish split
(`backend/src/content/README.md`'s одноимённая запись): каждый раз, когда
"Update" на редакторе постов реально применяет черновик к уже опубликованному
посту, предыдущая живая версия сохраняется в `ContentRevision` — нужен экран,
где эти версии видно, и способ вернуться к одной из них без прямой записи в
живую строку.

**Как сделано.** `PostHistoryPage({ slug, revisions })` — список
`RevisionSummary[]` (только `id`+`publishedAt`, backend), каждая карточка с
кнопкой "Load into draft". Кнопка зовёт `adminApi.restorePostRevision(slug,
id)`, который на backend копирует старую версию В `ContentDraft`, НИКОГДА не
трогая живую строку напрямую — после успеха страница просто переходит на
`/admin/journal/[slug]/edit`, где восстановленный черновик уже лежит и ждёт
обычного клика Publish/Update, как любая другая правка.

**Понятность для другого разработчика.** Подсказка над списком прямо
говорит "Load into draft" не публикует ничего сама — без неё выглядело бы
как настоящий откат сайта одним кликом, что не так, и это осознанное
решение (см. backend-комментарий у `restorePostRevision`), не недосмотр.

**Расширяемость/заменяемость.** Не завязан на конкретную форму
`PostInput` — принимает уже готовый `RevisionSummary[]`, вся логика
слияния/применения черновика живёт на backend.

**Миграция/отказоустойчивость.** Не применимо — чисто читающий экран плюс
одна мутация (`restore`), которая уже прошла тестами на backend
(`admin-posts.test.ts`).

**SOLID.** Single Responsibility: этот компонент не знает, как черновик
мержится с живым контентом — только показывает список и вызывает один
API-метод.
