# shared/lib/tech-icons — resolving a tech-stack row's logo, server-side only

## Что нужно было сделать

Пользователь хочет на главной странице ряд монохромных логотипов
технологий (как на референсном скриншоте — C++, AWS, MySQL, TypeScript,
React, Docker, Kubernetes, Python и т.д.), а не текстовые теги, как было
раньше (`TechStack.tsx`). При этом `lucide-react` (единственная
установленная иконочная библиотека — см. `shared/ui/icon-picker/README.md`)
принципиально не содержит брендовых логотипов; нужен новый источник иконок.

## Почему `simple-icons`, и почему резолвинг — только на сервере

[Simple Icons](https://simpleicons.org/) — ~3450 SVG-логотипов брендов,
единый `viewBox="0 0 24 24"`, `path`-строка на иконку, монохромные
(рисуются через `fill="currentColor"`, что само по себе решает задачу
"логотипы должны красиво подсвечиваться accent-цветом на hover/pressed" —
не нужно ни SVG-фильтров, ни отдельных цветных версий каждой иконки).

Пакет целиком — это несколько мегабайт SVG-путей на все бренды сразу; ни
один посетитель не должен скачивать его в браузер, только те ~10-15
иконок, что реально показаны на странице. Решение: `simple-icons`
устанавливается как зависимость `frontend`, но импортируется ИСКЛЮЧИТЕЛЬНО
из серверного кода (Server Component `app/(site)/page.tsx`, Route Handler
`/api/admin/tech-icons`) — в браузер уезжает только уже резолвленная
`path`-строка для конкретной технологии, а не библиотека. `next.config.ts`
получил `serverExternalPackages: ["simple-icons"]`, чтобы Next.js
`require()`-ил пакет из настоящих `node_modules` в рантайме, а не
пытался протащить его через свой сборщик для серверного бандла.

Этот модуль не использует пакет `server-only` (npm) для принудительной
защиты границы — в репозитории он не используется вообще ни для одного
другого server-only модуля (см. `backend/`, целиком серверный пакет без
такой защиты), так что дисциплина "не импортировать из `"use client"`
файла" держится тем же способом, каким она уже держится везде в этом
проекте: явным комментарием на видном месте (`registry.ts`'s верхний
комментарий), а не дополнительной зависимостью для одного слайса.

## Почему индекс строится по `icon.slug`, а не по имени экспорта

Первая идея была: раз пакет экспортирует иконки как `si<PascalCase(slug)>`
(`siDocker`, `siReact`), можно вычислить нужное имя экспорта из slug'а и
проиндексировать через него. Проверка вживую (`node -e "require('simple-
icons')"`) нашла реальные исключения из этого правила — например,
`siHive_blockchain` (slug `hive_blockchain`, с подчёркиванием) не
получается механически восстановить из `PascalCase`. Итоговая реализация
(`registry.ts`) вместо этого один раз проходит `Object.values(simpleIcons)`
и строит `Map<slug, SimpleIcon>` из `icon.slug` — поля, которое сама
библиотека уже гарантированно верно заполнила, а не переизобретает его
из имени переменной.

## Как получается автоматическое сопоставление названия технологии с логотипом

Три источника, каждый работает независимо:

1. **`type: "auto"`** (дефолт для новой строки techStack) —
   `backend/src/content/tech-slug.ts`'s `toSimpleIconSlug(name)` даёт
   лучшую механическую догадку slug'а (lowercase + убрать пунктуацию,
   плюс небольшая таблица исключений для случаев типа `"C++" →
   "cplusplus"`, которые механически не выводятся). `resolveTechIcon`
   ищет этот slug в реальном каталоге и либо рисует найденную иконку, либо
   тихо откатывается на `{ kind: "none" }` — никогда не показывает
   логотип чужого бренда только потому, что догадка случайно совпала с
   чьим-то ещё slug'ом (сам алгоритм в `tech-slug.ts` подробно объясняет,
   почему угадывание в принципе ограничено).
2. **`type: "brand"`** — админ явно выбрал slug из живого поиска
   (`GET /api/admin/tech-icons?q=...`, `shared/ui/icon-picker`-подобный
   паттерн) — используется, когда `"auto"` промахнулся или дал не тот
   бренд (например, у названия "Android Open Source" авто-догадка вообще
   не сработает, а руками выбранный slug `"android"` — сработает).
3. **`type: "url"`/`type: "none"`** — тот же контракт, что уже есть у
   `IconRef` (принципы): произвольная картинка по ссылке, либо явное "нет
   логотипа" (для технологий без реального бренд-лого — `"Coroutines &
   Flow"`, `"KSP"` и т.п.).

## 2026-08-06 — Пятый вариант: `type: "svg"` (сырой, вставленный админом SVG-код)

**Что нужно сделать.** У части технологий (`"Coroutines & Flow"`,
`"Android Open Source"`, `"JNI & C++"`) нет реального лого в Simple Icons
вообще — до этой правки единственный fallback был `"url"` (ссылка на уже
где-то захостенное изображение), что неудобно для технологии без готовой
картинки. Нужна возможность вставить SVG-код напрямую в форму.

**Как сделано.** `techIconSchema` получил `{ type: "svg", value: string }`
— значение хранится СЫРЫМ, без санитайзинга при записи (та же логика, что
уже применена к `Block`'s `diagram`-типу: сырой Mermaid/PlantUML-исходник
в базе, санитайзинг только при рендере). Санитайзинг — на клиенте, в
`shared/ui/tech-icon/TechIcon.tsx`, через `shared/lib/sanitize-svg.ts`
(тот же DOMPurify-санитайзер, что уже использовался для рендера
диаграмм — перемещён в общее место, раз понадобился второй, независимой
фиче).

**Находка по дороге: DOMPurify не работает без `window`.** Первая
реализация звала `sanitizeSvg()` прямо в теле `TechIcon`'s рендера — и
это ломало SSR: `resolveTechIcon` резолвит `type: "svg"` на сервере (в
`app/(site)/page.tsx`), значение приходит в `TechIcon` как обычный проп,
значит вызов санитайзера произошёл бы и при серверном рендере "use
client"-компонента тоже. Проверено вручную: голый `require("dompurify")`
в чистом Node (без jsdom) даёт `DOMPurify.sanitize is not a function` —
падает, а не тихо деградирует. Диаграммы избегают этого случайно —
`DiagramSurface` рендерится только ПОСЛЕ `useEffect`, заполняющего `svg`
через `useState` (сам Mermaid асинхронный и на сервере не может
работать), так что `sanitizeSvg` там физически никогда не вызывается на
сервере. Для `TechIcon` эта случайная защита не действует (данные уже
готовы синхронно, из пропа), так что понадобился явный паттерн: рендерить
`null` на первом рендере (сервер и клиент договариваются — ничего ещё
нет), санитайзить и показывать результат только в `useEffect` после
монтирования — то же решение, что уже задокументировано в правиле
репозитория про гидратацию (`typeof window === "undefined"` в теле
рендера нельзя, а вот "дефолт на первом рендере + `useEffect`-коррекция"
— можно).

**Понятность для другого разработчика.** Комментарий над `SanitizedSvg`
(`TechIcon.tsx`) прямо объясняет и находку про DOMPurify/SSR, и почему это
не `typeof window`-ветвление в теле рендера.

**Расширяемость/заменяемость.** `sanitize-svg.ts` теперь в
`shared/lib/`, не привязан к `diagram/` — третий будущий потребитель
сырого SVG в `dangerouslySetInnerHTML` подключается тем же импортом.

**Миграция/отказоустойчивость.** Ни одной Prisma-миграции. Раздельные
границы доверия: бэкенд хранит значение как есть (никогда не парсит/не
рендерит его), фронтенд санитайзит на каждый рендер (не один раз при
записи) — будущее ужесточение правил DOMPurify применится ко всем уже
сохранённым строкам автоматически, не только к новым.

**SOLID.** Single Responsibility по границе: `resolve-tech-icon.ts` не
знает про DOM/DOMPurify вообще (не может — работает на сервере), только
про то, что `type: "svg"` становится `kind: "svg"` с тем же значением;
`TechIcon.tsx` не знает про Prisma/Zod/`simple-icons`, только про то, как
безопасно показать уже резолвленный `TechIconView`.

## Почему это НЕ тот же `IconRef`, что уже использует `principles`

`IconRef` — `{ none | url | icon }`, где `icon` — точное, руками введённое
имя иконки Lucide (никакого угадывания). У tech-stack ряда другая задача
— "попробовать угадать реальный бренд-логотип автоматически, но дать явный
override", то есть четвёртое состояние (`auto`), которого у `IconRef` нет
и которое не имело бы смысла добавлять туда: оно осмысленно только для
ОДНОГО из двух текущих потребителей `IconRef` (tech-stack, не principles).
Полная аргументация — в комментарии над `techIconSchema`
(`backend/src/content/site-content.ts`).

## `resolveTechIcon` — одна реализация, оба потребителя

Тот же принцип, что уже применён к `IconRefPreview` (см. его README):
резолвинг иконки для конкретной строки `techStack` вызывается ОДИН раз, из
`app/(site)/page.tsx`, до передачи данных в `LandingPage` — секция
`TechStack.tsx` (клиентский компонент, ради `useTranslation()`) получает
уже резолвленный `TechIconView`, а не сырой `TechIcon` + обязанность самой
резолвить его на клиенте (что потребовало бы протащить `simple-icons` в
браузер).

## 2026-08-06 — `GET ?auto=<name>` заменён на batch-`POST`

Изначально у роута `/api/admin/tech-icons` было два GET-параметра:
`?q=<query>` (поиск) и `?auto=<name>` (резолв одного имени). Второй
существовал для одного-единственного превью внутри `TechIconPickerField`.
Когда редактор tech-stack переехал на компактный список, где КАЖДАЯ строка
показывает свой живой логотип, «по одному запросу на строку» перестало
работать: вставка списка из 20 технологий — это 20 round-trip'ов.

Теперь это `POST /api/admin/tech-icons` со всем списком
`{ items: [{ name, icon }] }` → `{ views: TechIconView[] }`. `POST` для
чтения — осознанно: вопрос задаётся про весь список сразу, а `icon` может
нести многокилобайтную вставленную SVG-разметку, которая в query string не
помещается. Ничего не пишется; `defineAdminRoute`'s CSRF-проверка и
audit-log при этом всё равно применяются, что для роута, доступного только
админке, приемлемая цена.

Ключевое свойство обеих версий одно и то же и специально не изменилось:
резолвит `resolveTechIcon` — ТА ЖЕ функция, что вызывает публичный лендинг,
— поэтому превью в админке не может разойтись с тем, что реально покажется.

## Тесты

`registry.test.ts`/`resolve-tech-icon.test.ts`/`search-brand-icons.test.ts`
— все против настоящего установленного пакета `simple-icons` (не мока):
известные реальные slug'и (`docker`, `kotlin`, `cplusplus`) дают
предсказуемый результат, несуществующий slug — `undefined`/`{ kind: "none"
}`, а не исключение. `getSimpleIconBySlug`'s тест на `hive_blockchain`
специально фиксирует находку про нерегулярные имена экспортов (см. выше)
— если реализацию когда-нибудь "улучшат" обратно до вычисления имени
экспорта из slug'а, этот тест упадёт первым.
