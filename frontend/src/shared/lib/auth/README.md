# shared/lib/auth — кто вызывающий и что ему разрешено

## Будет ли переиспользоваться?

Да — `resolvePrincipal`/`hasScopes` (`principal.ts`) и `defineAdminRoute`/
`definePublicRoute`/`requirePage` (`guard.ts`) используются буквально
каждым `route.ts` под `frontend/src/app/api/**` и единственным layout'ом под
`frontend/src/app/admin/(dashboard)/`. Это не вспомогательный код для одной
фичи — это единственный механизм авторизации во всём приложении.

## Что нужно было сделать

До этой фазы решение "разрешён ли этот запрос" принимал `proxy.ts`
(Next.js middleware): смотрел на префикс пути (`/admin/*`, `/api/admin/*`),
проверял JWT, либо редиректил, либо проставлял заголовки
`x-user-id`/`x-user-email`/`x-user-role`, которым каждый нижестоящий route
просто доверял (см. `frontend/src/app/api/admin/me/route.ts`'s старый
комментарий: "the proxy is the single place that checks the token").

Хотелось противоположного: чтобы КАЖДЫЙ route/page сам декларировал, какой
уровень доступа ему нужен, а не полагался на то, что что-то выше по цепочке
это уже проверило.

## Первый заход, который отвергли — таблица путей в `proxy.ts`

Первая версия плана заменяла `pathname.startsWith("/admin")` на явный
реестр `{ pattern: RegExp, requirement: "public" | "admin" }[]`,
перебираемый в `proxy.ts`. Формально это уже "явный контракт вместо
implicit-проверки", но по сути — та же проблема, только в виде таблицы, а
не `if`: `proxy.ts` **физически не может** знать, что нужно конкретному
`route.ts`, потому что выполняется ДО того, как Next.js вообще решит, какой
файл будет обрабатывать запрос — у него есть только форма URL, не
декларация конкретного хендлера. Любая попытка сделать в middleware
детальную карту "что кому нужно" обречена остаться таблицей путей,
оторванной от кода, который эту авторизацию реализует.

## Как сделано вместо этого

**`principal.ts`** — единственное место, которое умеет превращать сырой
access-JWT в `Principal { userId, email, scopes }`. `scopes`, не `role`:
сегодня `scopesForRole("admin")` возвращает ровно `["admin:*"]` (одна роль
в системе), но каждый route уже сегодня декларирует требование как
**список scope-строк**, а не как проверку `role === "admin"` — если завтra
понадобится более узкая роль (например, переводчик с правом только на
`posts:translate`), это правка одной функции (`scopesForRole`), а не
каждого места, где сегодня написано `["admin:*"]`.

**`guard.ts`** — единственное место, где эта проверка ПРИМЕНЯЕТСЯ:

```ts
export const POST = defineAdminRoute(async (request, { params }, principal) => { ... });
export const POST = definePublicRoute(async (request) => { ... }); // login/refresh/logout
```

```ts
// app/admin/(dashboard)/layout.tsx — быстрый редирект на полной загрузке
export default async function AdminDashboardLayout({ children }) {
    await requirePage();
    ...
}

// КАЖДЫЙ page.tsx под этим layout'ом, который читает admin-данные
// напрямую из @portfolio/backend, тоже вызывает requirePage() сам —
// см. дальше "2026-07-28", почему вызова в layout'е одного недостаточно.
export default async function Page() {
    await requirePage();
    return renderOrServiceUnavailable(...);
}
```

`defineAdminRoute`/`definePublicRoute` — это не два независимых куска
кода: оба — тонкие обёртки над одной internal `defineRoute(scopes,
handler)`, которая одна вызывает `resolvePrincipal`/`hasScopes`. Не бывает
route'а, который проверяет права как-то по-своему.

## Почему `proxy.ts` перестал проверять токен вообще

`resolvePrincipal` вызывается заново в каждом `defineAdminRoute`/
`requirePage` — не переиспользует то, что мог бы уже проверить `proxy.ts`.
Это не дублирование в плохом смысле (одна и та же логика написана дважды
руками) — сама проверка живёт в одном месте (`resolvePrincipal`), просто
вызывается там, где принимается решение, а не в слое, который физически не
может знать решение конкретного route'а. Побочный эффект: route защищён
сам по себе, даже если однажды окажется вызван путём, не проходящим через
`proxy.ts` (внутренний вызов, тест, опечатка в будущем matcher'е) —
`proxy.ts` больше не единственная линия обороны, потому что перестал
единственной линией обороны быть по конструкции, а не по обещанию не
ошибиться в конфиге. `frontend/src/proxy.ts`'s собственный комментарий и
`backend/src/auth/README.md` — полная версия этого рассуждения, включая
разбор, какие ДВЕ вещи (rate limiting + locale) остаются законной работой
Edge-уровня и почему.

## Нагрузка / горизонтальное масштабирование

`resolvePrincipal` — чистая проверка подписи JWT (`jose`, без похода в
БД) — одинаково дешёвая и одинаково корректная на любом количестве
инстансов Next.js за балансировщиком, без какой-либо координации между
ними. Двойная верификация (route ещё раз проверяет то, что мог уже
проверить `proxy.ts`) не создаёт сетевой нагрузки — оба раза это чистая
CPU-проверка подписи, без обращения к внешнему хранилищу.

## SOLID

Single Responsibility: `principal.ts` знает только "как получить
`Principal` из токена и сравнить с требованием", `guard.ts` — только "как
применить это к route/page". Open/Closed: новая роль/scope — правка
`scopesForRole` и точки объявления требования на конкретных route'ах, не
структурная правка `guard.ts`. Dependency Inversion: каждый route зависит
от абстракции "мне нужны вот такие scopes", не от деталей верификации JWT
— эти детали спрятаны внутри `principal.ts`.

## 2026-07-28 — Один `requirePage()` в layout'е был недостаточен

**Найдено:** реальным комментарием в PR-ревью (бот, не гипотетический
сценарий), не при написании кода.

**Что нужно было сделать.** Проверить утверждение, которым было прямо
подписано `layout.tsx`: "`requirePage()` вызывается ЗДЕСЬ, один раз — не
повторяется в каждом `page.tsx`... это единственное место, которое
гарантированно выполнится перед ЛЮБОЙ из ~10 страниц".

**Почему это было неверно.** Next.js App Router намеренно НЕ
перерендеривает общий layout при клиентской навигации между соседними
страницами под ним — это и есть весь смысл вложенных layout'ов (общее
состояние/UI переживает переход между страницами). Если сессия
инвалидируется ПОСЛЕ первого рендера (истёк access-токен, вышли в другой
вкладке, куку почистили), клик по `<Link>` на другую страницу этой же
группы может дойти до Server Component той страницы — а несколько из них
(`journal/[slug]/edit`, `work/[slug]/edit`, `journal/[slug]/translate`,
`work/[slug]/translate`, `journal`, `journal/new`, `work`,
`settings/[key]`) вызывают функции `@portfolio/backend` НАПРЯМУЮ (не через
уже защищённый `/api/admin/**`), — без повторного запуска `layout.tsx` и
без единой проверки авторизации на этом пути.

**Как исправлено.** Применён тот же принцип, что уже применяется к
`/api/admin/**` через `defineAdminRoute` — "каждая точка доступа
защищает себя сама, не полагаясь на вышестоящий слой" (см. секцию выше
"Почему `proxy.ts` перестал проверять токен вообще" — это ровно та же
логика, просто ранее применённая только к route'ам, но не к page'ам).
Каждый из 8 файлов теперь вызывает `await requirePage();` первой строкой
своего `Page()`, ДО любого обращения к `@portfolio/backend`. Вызов в
`layout.tsx` НЕ удалён — он остаётся ради быстрого редиректа на полной
загрузке страницы, без вспышки защищённого UI (`AdminNav`,
`SessionKeepAlive`) перед редиректом; реальная граница безопасности
теперь на уровне каждой страницы, а не только в layout'е.

**Почему не тронуты `/admin` (root), `/admin/settings` (index),
`/admin/work/new`.** Проверены отдельно — ни один не читает
admin-данные напрямую: первый только редиректит, второй рендерит
фиксированный список из константы (`SITE_CONTENT_SECTIONS`), третий
рендерит пустую форму без `initialWork` (создание идёт через уже
защищённый `POST /api/admin/work`).

**Понятность для другого разработчика.** Комментарий в `layout.tsx`
переписан целиком — не просто "исправлен", а оставлен как явный пример
неверной первой гипотезы и её опровержения (та же конвенция, что и в
`backend/src/auth/README.md`'s дневниковых записях), чтобы никто не
удалил page-level проверки обратно, посчитав их "дублированием" layout'а.

**Нагрузка.** Один дополнительный `resolvePrincipal()` (чистая
CPU-проверка JWT-подписи, без похода в БД) на каждую защищённую
страницу — то же самое обоснование, что и в разделе "Нагрузка /
горизонтальное масштабирование" выше.

**Миграция/отказоустойчивость.** Не применимо — чисто логика авторизации,
данные/схема не затронуты.
