# shared/lib — cross-cutting frontend utilities

Плоская папка нетипизированных под конкретный UI-виджет вспомогательных
модулей (`admin-api.ts`, `date-format.ts`, `slugify.ts`, ...) — каждый
файл решает одну переиспользуемую задачу, не привязанную к конкретной
странице/компоненту. Этот README документирует только те файлы, у которых
есть что объяснить сверх инлайн-комментариев в самом файле; остальные
самодостаточны.

## 2026-07-31 — Третий баг того же автоматического review: переименование slug'а ломало все следующие autosave

**Что было не так.** `slugRef.current` обновлялся только в ветке
"первое создание" (`create()`), но НЕ в ветке "обычное сохранение"
(`update()`) — а именно через `update()` идёт и сохранение
переименования: администратор редактирует поле "Slug" у уже
существующего поста/work item, backend успешно переименовывает строку
(`updatePost`/`updateWork` пишут новый `slug` в колонку), но этот хук
продолжал считать, что текущий slug — старый. Следующий autosave слал
`update(oldSlug, ...)` на URL, которого уже не существует — 404, тихая
поломка автосохранения до перезагрузки страницы. Хуже того,
`PostEditorPage`/`WorkEditorPage`'s `handlePublish`/`handleUnpublish`/
`handleDelete`/"Add translation" читали `initialPost.slug` — НЕИЗМЕНЯЕМЫЙ
проп, зафиксированный на момент маунта — так что ВСЕ эти действия тоже
слали бы запросы на несуществующий старый slug.

**Проверено вживую, не только рассуждением.** Реальный HTTP-запрос:
создать пост → `PUT` с новым `slug` (переименование, ответ 200,
`row.slug` реально сменился) → `PUT` на СТАРЫЙ slug → `404`. Это
воспроизводит ровно тот сценарий, который ломался.

**Как исправлено.** `getSlug` теперь читается из результата ЛЮБОГО
успешного сохранения (create ИЛИ update), не только create. Бывший
`onCreated` переименован в `onSlugChanged` и расширен: срабатывает не
только на "первое создание" (`null → slug`), но и на любое переименование
(`oldSlug → newSlug`) — сравнением с уже известным `slugRef.current`
ПЕРЕД присваиванием, так что на обычном сохранении без переименования
колбэк не зовётся вообще (не каждый save — событие).

`PostEditorPage`/`WorkEditorPage` завели собственный `currentSlug`
(`useState`, не проп) — источник истины для ВСЕХ действий этого
компонента (Publish/Unpublish/Delete/"Add translation"/заголовок
страницы), синхронизируется из `onSlugChanged`, который дополнительно
делает `router.replace()` на актуальный `/[slug]/edit`-урл — та же логика,
что раньше применялась только к самому первому созданию, теперь покрывает
и переименование уже существующей записи.

**Понятность для другого разработчика.** Комментарий у `currentSlug`
прямо называет источник бага (`initialPost` — проп, фиксированный на
момент маунта) — без него неочевидно, почему READ пропа неверен именно
для ДЕЙСТВИЙ, а не для чтения исходных данных формы (`toFormState`,
которое читает `initialPost` один раз при инициализации — это осталось
корректным, потому что форма и не должна "переоткрываться" при
переименовании, только идентификатор для API-вызовов должен).

## 2026-07-31 — Два реальных бага, найденных автоматическим review (не при повторном чтении файла)

**Баг 1 — `flush()` никогда не отклонялся, даже когда сохранение реально
проваливалось.** Первая версия `performSave()` гасила ошибку внутри
`.catch()` без повторного `throw` — промис, который возвращал `flush()`,
всегда resolve'ился. `handlePublish` (оба редактора) вызывает `await
autosave.flush()` именно для того, чтобы строгая проверка публикации на
backend читала актуальное содержимое — с этим багом `flush()` "успешно"
завершался, и `publishPost`/`publishWork` публиковали то, что уже лежало в
БД (устаревшую версию), без единой видимой ошибки.

**Исправлено** переписыванием `performSave` на пару `performSave`
(синхронная обёртка для `activeSaveRef`) + `runSave` (`async`, настоящий
`try`/`catch`/`throw`) — фоновый retry (`setTimeout`) остаётся
безусловным, отклоняется только сам ПРОМИС, который явно ожидающий
вызывающий код (`flush()`) может поймать. Отдельная тонкость, проверенная
по спеке `Promise.finally`, а не предположенная: если первая попытка
провалилась, но "довесок" (coalesced follow-up) с актуальным вводом
успешен — итоговый промис должен resolve'иться (реальный успех), а не
нести ошибку первой попытки — старая `.finally()`-цепочка на этом
ломалась бы, `async`/`await` с явным `return performSave()` — нет.

**Баг 2 — навигация в окне debounce молча теряла последнюю правку.** Без
единственной кнопки "Save" уход со страницы (клик "Back to list"/"Add
translation") в течение ~800мс после последнего символа был единственным,
что могло произойти, пока правка ещё сидела в debounce-таймере —
unmount-cleanup хука просто отменял таймер, ничего не сохраняя.

**Первая мысль — flush'ить прямо в cleanup-эффекте хука — была
проверена и отклонена, не просто "показалась сложной".** Написан
реальный юнит-тест (React + `@testing-library/react`, не рассуждение):
`useImperativeHandle`-реф ребёнка (`<BlockEditor ref={blockEditorRef}>`)
уже `null` в момент, когда срабатывает cleanup родительского `useEffect`
того же уровня — React разбирает поддерево "снизу вверх", реф ребёнка
отвязывается раньше. Flush изнутри cleanup самого хука вызвал бы
`buildInput()` с уже оторванным рефом блочного редактора — тихо отправив
`blocks: []` и стерев реальное, уже сохранённое тело. Это хуже исходного
бага, не решение.

**Реальное исправление — flush ДО навигации, из компонента-владельца
рефа.** `PostEditorPage`/`WorkEditorPage`'s `navigateAfterFlush(path)` —
`await autosave.flush()`, и только при успехе `router.push(path)`; при
провале — явная ошибка, навигация блокируется (та же логика, что уже
у `handlePublish`). На "Back to list"/"Add translation" навешен
`loading={navPending}`, чтобы блокировать повторный клик пока flush летит.
**Осознанно оставшийся, более узкий разрыв**: пути ухода, не проходящие
через эти кнопки (клик по верхней навигации, "назад" в браузере) — та же
категория "принятое ограничение", что и остальные в этом хуке (см.
запись ниже про создание-и-навигацию).

**Понятность для другого разработчика.** Комментарий у cleanup-эффекта
хука прямо объясняет, ПОЧЕМУ он не пытается флешить сам (со ссылкой на
эмпирическую проверку) — без этого следующий разработчик почти наверняка
"исправил" бы это ровно так, как это было предложено автоматическим
review, и внёс бы худший баг.

## 2026-07-31 — `use-autosave-draft.ts` (Фаза 3: мгновенный черновик + непрерывный autosave)

**Что нужно сделать.** По плану ("Мгновенный черновик + непрерывный
autosave"): первый введённый символ в заголовке должен создать реальную
запись в БД (не по клику "Create"), а каждое дальнейшее изменение —
сохраняться в фоне, без явного сабмита. Ровно ОДИН механизм должен
покрывать и переход "ещё не существует → существует", и все сохранения
после — не два разных пути с двумя наборами багов.

**Как сделано.** Один хук, `useAutosaveDraft<TInput, TResult>`, с debounce
(по умолчанию 800мс) поверх `setTimeout`, не поверх `useEffect([form])` —
это осознанный выбор: `buildInput()` (проп хука) вызывается ЗАНОВО перед
каждой попыткой сохранения, а не один раз при вызове хука, поэтому он
может тянуть значения не только из React-state (`form`), но и из
`BlockEditor`-рефа (`blockEditorRef.current?.getBlocks()`) — то, что
`useEffect`'s dependency array в принципе не умеет выразить (блочный
редактор намеренно неконтролируемый, см.
`shared/ui/block-editor/README.md`). Раз запись ещё не существует
(`slug === null`) — вызывается `create()`; после первого успешного
создания — только `update(slug, ...)`. Вызывающая страница (`PostEditorPage`/
`WorkEditorPage`) сама решает, что делать с новым slug через `onCreated`
(обычно `router.replace()` на реальный `/edit`-урл) — хук ничего не знает
про конкретные URL-шаблоны (Interface Segregation: `/admin/journal/*` и
`/admin/work/*` — разные шаблоны, хуку об этом знать незачем).

**Параллелизм — ровно один запрос "в полёте", ровно один "довесок".**
Если правка приходит, пока предыдущее сохранение ещё не ответило, хук НЕ
отменяет его и НЕ шлёт второй параллельный запрос — выставляется флаг, и
как только текущий запрос завершится, выполняется РОВНО один
дополнительный сейв с содержимым, актуальным на тот момент (не снэпшотом
на момент правки). Это то, что исключает гонку "старый ответ прилетел
поверх нового ввода" — раз запрос в моменте времени только один, гоняться
не с чем. Реализовано через `Promise.finally()`, ВОЗВРАЩАЮЩИЙ вложенный
рекурсивный вызов `performSave()` — без явного `return` `.finally()` не
дожидается вложенной цепочки (проверено юнит-тестом, не только по
спецификации, см. `use-autosave-draft.test.ts`'s тест на `flush()`).

**Осознанное ограничение, не решённое, а принятое.** Самое первое `create()`
меняет URL на другой РОУТ Next.js (`/admin/journal/new` →
`/admin/journal/[slug]/edit`), а не просто адресную строку — то есть
реальный ремонт страницы с новым server-fetched содержимым. Правки,
напечатанные в узком окне между ответом `create()` и завершением этого
перехода, покрываются механизмом коалессинга выше (они точно вызовут один
`update()` до ремонта), но на медленном соединении нет жёсткой гарантии,
что ремонт всегда дождётся именно этого `update()`. Не стали блокировать
навигацию на сетевой запрос ради устранения этой узкой гонки — это
вернуло бы ровно то ощущение "застрял, пока что-то не загрузится", ради
устранения которого существует Фаза 1 (отказоустойчивые сессии). Описано
в JSDoc-комментарии самого хука, а не спрятано.

**Почему НЕ в scope `stryker.config.mjs` (frontend/).** Это React-хук с
`setTimeout`/`useRef`/`useState` — та же категория, что уже осознанно
исключена из mutation-testing scope v1 (`useHideOnScroll`, см.
`stryker.config.mjs`'s комментарий: "DOM-listener hooks... документированный
v1 scope limit для скорости/стабильности, не заявление, что хуки не
заслуживают этого"). Вместо этого — обычный, но целенаправленный набор
юнит-тестов на `renderHook` + `vi.useFakeTimers()`, каждый явно пишущий
mutation-ориентированную проверку границы (debounce ровно N мс, не N-1;
коалессинг ровно один довесок, не ноль и не два; `flush()` реально ждёт
вложенную цепочку, а не только первый запрос) — то есть тот же дух
mutation-testing правила, просто без самого Stryker-прогона.

**Понятность для другого разработчика.** Каждое поле
`UseAutosaveDraftOptions` документировано отдельным doc-комментарием,
включая явное "зачем именно так, а не проще" там, где решение неочевидно
(`buildInput` — функция, а не значение; `getSlug` — отдельный аксессор, а
не структурное требование к `TResult`).

**Расширяемость/заменяемость.** Хук ничего не знает про `Post`/`Work`
конкретно (дженерик по `TInput`/`TResult`) — третий тип контента с тем же
паттерном "черновик → autosave → publish" подключается без изменений
здесь.

**SOLID.** Single Responsibility в чистом виде: этот хук знает только "как
и когда сохранить", ничего не знает о HTTP-контракте конкретных
эндпоинтов (`create`/`update` — переданные функции), о навигации
(`onCreated` — колбэк), о том, что такое "черновик" на уровне бизнес-логики
(`isEmpty` — переданный предикат). Dependency Inversion: страница передаёт
свои `adminApi.createPost`/`updatePost` КАК АРГУМЕНТЫ, хук зависит от
абстрактной сигнатуры `(input) => Promise<TResult>`, не от `adminApi`
напрямую.

## 2026-08-03 — 800мс debounce мешал печатать: увеличен до 3 минут + сохранение по blur

**Что нужно сделать.** Живая жалоба: 800мс — слишком агрессивно, статус
"saving…"/реальный запрос на сервер срабатывал на каждой паузе дольше
секунды, то есть буквально при обычном обдумывании фразы. Нужен debounce
хотя бы в минуту, лучше несколько, ЛИБО сохранение по потере фокуса полем.

**Как сделано — оба, не одно вместо другого.** `DEFAULT_DEBOUNCE_MS`
поднят до 3 минут (`3 * 60 * 1000`) — единственная правка в этом файле,
`debounceMs` и раньше был настраиваемым параметром, так что это не новая
возможность, просто новое значение по умолчанию. Существующие тесты не
задели — каждый из них передаёт свой явный `debounceMs` (100/800/5000),
ни один не проверял именно значение по умолчанию (добавлен отдельный тест
на это, "defaults to a 3-minute debounce...", раз ни один существующий
тест не поймал бы, если бы кто-то по ошибке вернул его обратно к
агрессивному значению).

Отдельно — `PostEditorPage.tsx`/`WorkEditorPage.tsx` получили `onBlur` на
самом `<form>` (не на каждом поле по отдельности): React's `onBlur` на
контейнере технически реализован через нативный `focusout`, который
всплывает, так что один хендлер ловит потерю фокуса ЛЮБЫМ полем внутри
формы, включая `<BlockEditor>` — без единого изменения в
`BlockEditorProps`/`BlockNoteEditor.tsx`. Не `await`-ится и не показывает
ошибку пользователю (в отличие от `handlePublish`/`navigateAfterFlush`'s
`await autosave.flush()`) — это не осознанное действие, которое нужно
блокировать при сбое, а фоновая подстраховка; провал всё равно уходит в
собственный retry-таймер хука.

**Почему оба, а не один.** Просто поднять debounce возвращает реальное
окно потери данных при закрытии вкладки/крэше браузера ПОСРЕДИ правки —
ровно то, ради чего исходные 800мс существовали. Сохранение по blur
закрывает почти всё это окно в обычном использовании (закончил с полем,
перешёл к следующему или к кнопке) без необходимости в коротком интервале.
Уже существующие flush-перед-навигацией (`navigateAfterFlush`,
`handlePublish`) не тронуты и продолжают покрывать остальное.

**Понятность для другого разработчика.** Комментарий у
`DEFAULT_DEBOUNCE_MS` прямо объясняет, почему таким большим значением
можно безопасно рисковать — ссылкой на существование flush-по-blur И
flush-перед-навигацией, а не просто "потому что попросили".

**Нагрузка.** Ниже, не выше — реже реальных сохранений, а не чаще.

**Расширяемость/заменяемость.** Третий редактор с тем же паттерном
"черновик + autosave" (см. хук выше) унаследует оба поведения бесплатно —
`debounceMs` через сам хук, blur — через тот же однострочный `onBlur` на
своём `<form>`.

**Миграция/отказоустойчивость.** Не применимо.

**SOLID.** Open/Closed: изменение — новое значение константы плюс новый
необязательный `onBlur` в JSX вызывающих страниц, ни сигнатура хука, ни
его внутренняя логика (`performSave`/`runSave`/коалессинг) не менялись
структурно.
