# shared/theme — перенос из frontend/ + найденный hydration-баг (Фаза 3/4 верификация)

## 2026-07-19 — Реальный hydration mismatch на теме, найденный пользователем вживую

**Что нужно сделать.** Проверить сайт после остановки/перезапуска Docker —
пользователь увидел в консоли `Console Error: A tree hydrated but some
attributes of the server rendered HTML didn't match the client properties`
конкретно на кнопках переключателя темы (`aria-pressed`, текст лейбла — не
совпадали между сервером и клиентом).

**Как сделано.** `getInitialPreference()` явно ветвился по
`typeof window === "undefined"` — сервер (где `window` всегда `undefined`)
получал `"dark"`, а клиент (где `window` есть всегда, даже до
гидратации) немедленно читал `localStorage` и мог получить `"light"` или
`"system"`, если пользователь уже сохранял такое предпочтение при
предыдущем визите. Первый рендер клиента и HTML, присланный сервером,
оказывались разными — это ровно тот паттерн, который сообщение об ошибке
React называет по имени как частую причину. Баг существовал в коде с
портирования Фазы 1 (унаследован из `frontend/`), но не мог проявиться
там — в чистом Vite SPA без сервера просто не с чем было расходиться.

Исправлено: `getInitialPreference()` теперь всегда возвращает `"dark"`
(детерминированно, одинаково на сервере и клиенте), а реальное сохранённое
значение читается в `useEffect` (клиент-только, после монтирования) и
применяется через `setPreferenceState`, что естественно запускает уже
существующий эффект синхронизации темы. Тот же принцип уже был в
`resolveTheme()` для случая `"system"` — теперь весь модуль единообразно
никогда не трогает `window`/`localStorage` во время самого рендера, только
внутри эффектов.

**Понятность для другого разработчика.** Комментарий у
`getInitialPreference()` прямо называет паттерн-ловушку по имени
(`typeof window !== "undefined"` в рендере) — так что при похожей правке
где-то ещё этот же баг не повторится незамеченным.

**Нагрузка.** Один лишний `useEffect` на монтирование `ThemeProvider` —
пренебрежимо.

**Расширяемость/заменяемость.** Если позже понадобится ещё одно
клиент-only значение (например, реальные системные метрики), тот же
паттерн — детерминированный дефолт на первый рендер + коррекция в
эффекте — переносится без изменений.

**Миграция/отказоустойчивость.** Побочный эффект фикса: пользователь с
сохранённым `"light"` увидит на долю секунды `"dark"`, прежде чем эффект
скорректирует тему — сознательный, принятый trade-off (тот же класс
проблемы, что и i18n-флеш, см. `shared/i18n/README.md`), предпочтительнее
сломанной гидратации.

**SOLID.** Не применимо напрямую — исправление корректности, не
структуры.

## 2026-08-15 — Тот самый "сознательный trade-off" из записи выше оказался корнем регулярно повторяющегося, трудноуловимого Playwright-флейка

**Что нужно сделать.** Пользователь сообщил о падении CI:
`component-gallery.spec.ts`'s `Text @ light` — `toHaveScreenshot` не мог
получить два одинаковых скриншота подряд (`Failed to take two consecutive
stable screenshots`, высота скачет между 1029px и 1030px), таймаут. По
словам пользователя — не первый раз чинили "похожую" проблему, и она
регулярно возвращается. Явный запрос: найти КОРЕНЬ, не расширять таймаут
ещё раз.

**Как было на самом деле.** Запись выше (2026-07-19) уже описала fix для
hydration mismatch — и уже честно предупредила о побочном эффекте:
"пользователь ... увидит на долю секунды `dark`, прежде чем эффект
скорректирует тему". На тот момент это выглядело как безобидный визуальный
нюанс. Оказалось — это ровно тот механизм, что ломает тесты: коррекция
происходит внутри `useEffect`, то есть ПОСЛЕ гидратации И ПОСЛЕ первого
paint — событие, о котором `page.waitForLoadState("networkidle")`
(используется в `visual.spec.ts`, `component-gallery.spec.ts`,
`a11y.spec.ts` — во ВСЕХ e2e-спеках, не только в упавшем) не может знать
вообще ничего, поскольку `networkidle` следит только за сетевой
активностью, а коррекция темы — чисто React-эффект без единого сетевого
запроса.

Комментарий в `frontend/tests/e2e/utils/theme.ts`'s `seedTheme()` прямо
утверждал обратное — что `networkidle` "достаточно рано... чтобы
устояться на засеянной теме до скриншота". Это утверждение было
источником регулярного, зависящего от тайминга флейка: иногда
эффект+ре-рендер+перекраска успевают завершиться до первого стабильного
скриншота Playwright (тест проходит), иногда — нет (нестабильный diff,
таймаут). Именно поэтому "то работает, то ломается снова" — это не
детерминированный баг, а гонка, зависящая от загрузки машины/CI. Это же
объясняет, почему падал именно `@ light`, никогда `@ dark`: dark — уже
дефолт с первого рендера, коррекция вообще не нужна; риск несёт только
`light`/`system`→light — а таких тестов во всём наборе (`visual.spec.ts`
по каждой странице × Desktop/Tablet/Mobile, каждый компонент в
`component-gallery.spec.ts`, каждая a11y-проверка контраста) огромное
количество — системный риск, а не разовая случайность.

**Реальный fix, а не расширение таймаута.** По официальному Next.js guide
([preventing-flash-before-hydration](https://nextjs.org/docs/app/guides/preventing-flash-before-hydration),
проверено вживую против текущей версии доков, не по памяти): синхронный
блокирующий `<script>` в `<head>` (`app/theme-init-script.tsx`),
выполняющийся во время парсинга HTML — строго ДО гидратации и ДО первой
отрисовки — то есть раньше, чем в принципе может успеть любой React-код
(`useEffect` ИЛИ `useLayoutEffect`). Скрипт дублирует логику
`resolveTheme()`/`applyThemeClass()` вручную (не может быть настоящим
импортируемым TS — должен выполняться независимо от любого JS-бандла
приложения). `suppressHydrationWarning` на `<html>` обязателен — без него
React трактует эту намеренную мутацию DOM как ошибку гидратации и
восстанавливается полным ре-рендером поддерева (что само по себе создало
бы ещё один, более заметный флеш).

Существующие `useEffect`'ы в `theme.context.tsx` не удалены — переведены
на `useLayoutEffect` (обе: и коррекция `preference`, и синхронизация
`theme`/`applyThemeClass`). Инлайн-скрипт закрывает реальный кейс
production/CI (Strict Mode double-render там не происходит); `useLayoutEffect`
закрывает отдельный, тоже реальный, но dev-only кейс: React Strict Mode
намеренно перемонтирует дерево один раз в разработке и сбрасывает
`<html>`/`<head>`/`<body>` до только тех атрибутов/классов, которыми
управляет сам React из JSX — стирая то, что успел выставить инлайн-скрипт.
`useLayoutEffect` переприменяет класс до следующей отрисовки; обычный
`useEffect` вернул бы флеш обратно, но только в `npm run dev`.

**Рассмотренная и отклонённая альтернатива: cookie + серверное чтение.**
Казалось бы — сделать как с локалью (`getRequestLocale()` читает заголовок
на сервере и передаёт `initialLanguage`, см. `app/layout.tsx`). Отклонено
по двум причинам, обе подтверждены не на словах:
1. Сами доки Next.js прямо предупреждают: чтение cookie в root layout
 "opts the entire app out of static prerendering" — и их же собственный
 рекомендованный паттерн для cookie-based темы — читать cookie ВНУТРИ
 инлайн-скрипта, на клиенте, а не через `cookies()` на сервере.
2. У локали серверное чтение — не cookie, а ЗАГОЛОВОК, выставляемый
 `proxy.ts`'s `handleLocale` из URL (`/ru/...`), и это решение уже
 стоило реального прод-инцидента: комментарий в `proxy.ts` (см. его
 `handleLocale`) документирует, что per-visitor заголовок ломает любой
 общий кэш (nginx `proxy_cache`, CDN) — `Vary: x-locale` не сработал на
 практике, проверено `curl`'ом дважды. Cookie-based тема воспроизвела бы
 ровно ту же категорию риска для будущей инфраструктуры кэширования,
 которую локаль уже один раз обожглась и исправила переносом в URL. Тема
 никогда не нуждалась в серверном знании вообще — только в том, ЧТОБЫ
 клиентское чтение произошло раньше, а не позже.

**Второстепенная, но реальная сопутствующая причина: `display: "swap"`.**
`app/fonts.ts` (see предыдущая запись про сами шрифты) использовал
`display: "swap"` — с БЕСКОНЕЧНЫМ окном подмены шрифта: браузер может
заменить fallback на настоящий шрифт в любой момент, даже посреди
двух последовательных скриншотов Playwright, если под нагрузкой CI
парсинг/декодирование шрифта задержалось. Для самостоятельно
захостенного шрифта (без непредсказуемой задержки CDN, ради которой
`"swap"` вообще существует) это окно ничем не оправдано. Заменено на
`display: "optional"` — короткий (~100мс), детерминированный блок-период,
БЕЗ последующей подмены: шрифт либо готов почти сразу (для локального
файла — почти гарантированно), либо страница на всю навигацию остаётся
на fallback и больше никогда не подменяет — открытое окно тайминга
убрано полностью, а не сужено.

**Найдено, но намеренно не тронуто в этом проходе.**
`shared/ui/project-graph/`'s `requestAnimationFrame`-цикл WebGL-рендера и
`d3-force`-симуляция продолжают работать даже при `idleFloat={false}` —
этот проп обнуляет только синусоидальное "покачивание" (`gl/idleFloat.ts`),
не сам цикл рендера (`useGraphScene.ts`, строки ~157-177) и не физическую
симуляцию, которая двигает узлы ещё несколько секунд после монтирования
(`useGraphScene.ts`, ~219-220). На той же странице `/storybook`, что и
секция `text` — держит GPU/main thread занятым, что теоретически может
удлинять время стабилизации ЛЮБОГО скриншота на этой странице под
CPU-throttling (тот же класс проблемы, что `frontend/tests/README.md` уже
документирует для hero-фона на главной). НЕ является прямой причиной
скачущей по высоте секции `text` (там нет WebGL) — оставлено на будущее
как реальный, а не забытый пункт, а не тихо проигнорировано.

**Понятность для другого разработчика.** Прошлая запись честно
зафиксировала свой trade-off вместо того, чтобы скрыть его — именно
поэтому эту цепочку было легко восстановить сейчас: причина флейка была
уже написана словами в этом же файле, просто до сегодняшнего дня никто
не проверял, действительно ли `networkidle` покрывает то, что описано.

**Нагрузка.** Инлайн-скрипт — несколько десятков байт чистого JS,
выполняется один раз на полной загрузке страницы; `useLayoutEffect` вместо
`useEffect` — та же по стоимости операция, просто в другой фазе коммита.

**Расширяемость/заменяемость.** Тот же паттерн (детерминированный дефолт
на первый рендер + синхронный pre-hydration скрипт вместо эффекта)
применим к любому будущему client-only значению, для которого
`useEffect`-коррекция окажется недостаточно ранней — не только к теме.

**Миграция/отказоустойчивость.** Не применимо — чисто клиентское,
косметическое исправление тайминга, не меняющее ни одной хранимой
структуры данных.

**SOLID.** Single Responsibility, чётче, чем было: инлайн-скрипт отвечает
только за ВИЗУАЛЬНОЕ состояние DOM до пейнта; `useLayoutEffect`'ы в
`ThemeProvider` — только за то, чтобы собственное React-состояние
(`theme`/`preference`, используемое переключателем темы) не разъезжалось с
тем, что скрипт уже выставил.
