# shared/ui/project-graph — `ProjectGraph`

## 2026-08-12 — WebGL-граф связей между Work-проектами для Hero

### Что нужно было сделать

Заполнить пустую правую половину `Hero`-секции чем-то, что визуально
подтверждает слова из subhead-текста ("event-driven architecture, a custom
navigation engine, ...") — не декоративной картинкой, а структурой,
построенной на реальных данных о проектах.

### Что было сделано (включая тупиковые ветки — они часть истории, не только финальный код)

1. **Связи — по реальным данным, не выдуманные.** Ребро между двумя
   `Work`-проектами существует, только если их `stack`-теги пересекаются
   достаточно (индекс Жаккара >= порога) — то же самое поле, что уже
   рисует `TagList` на карточках `SelectedWork`. См.
   `shared/lib/project-graph/computeProjectGraph.ts`.

2. **Первая попытка "стекла" — CSS/SVG, `feTurbulence` + `feDisplacementMap`
   через `backdrop-filter: url(#filter)`.** Работает только в Chromium,
   дёшево (без канваса), но результат читался как "мутные разводы", не
   как стекло — потому что шум ≠ оптика: `feTurbulence` двигает пиксели
   в случайном направлении, а не по формуле линзы. Оставлено рядом как
   отдельный файл-спайк для сравнения (`playground/graph-network-playground.html`
   в корне репозитория — не часть продакшен-кода).

3. **Вторая попытка — WebGL, одно преломление.** Настоящий `refract()` по
   закону Снеллиуса, но только на ВХОДЕ в сферу — визуально это лупа
   (увеличивает то, что рядом), а не шар (не переворачивает изображение).
   Настоящий переворот у стеклянного шара — от ДВУХ преломлений (вход +
   выход с обратной стороны). Финальная версия (`gl/shaders.ts`,
   `LENS_FRAGMENT_SHADER`) считает обе точки: аналитически находит выход
   луча из той же сферы (`t = -2·dot(p1,r1)` — замкнутая формула
   пересечения прямой со сферой, без итераций) и преломляет ещё раз.

4. **Блик — не константный белый, а Френель.** Изначально был
   `pow(dot(normal, lightDir), 24) * white` — блик без физического
   источника света. Заменён на смешивание ДВУХ реальных сэмплов одной и
   той же сцены (отражённого и преломлённого) по формуле Шлика — и
   единственный настоящий свет добавлен в саму сцену (`GRID_FRAGMENT_SHADER`),
   а не только в шейдер линзы, — чтобы у отражения было что показывать.

5. **Два конкретных бага, пойманные вживую (оставлены как урок, не только
   исправлены):**
   - `Precisions of uniform 'uResolution' differ between VERTEX and
     FRAGMENT shaders` — один uniform был `mediump` во фрагментном шейдере
     (явно) и `highp` в вершинном (по умолчанию, не было явного
     `precision`). Фикс — `precision highp float;` явно в КАЖДОЙ стадии
     каждой программы, а не понадеявшись на дефолт.
   - Локальная переменная `float dot = ...` в GLSL-фрагменте сетки
     молча ломала компиляцию на части драйверов — `dot()` зарезервированное
     имя встроенной функции скалярного произведения. Переименована в
     `dotGlow`.

6. **Диагностика — не только `console.error`.** Провалившийся шейдер не
   бросает JS-исключение вообще (`getAttribLocation`/`getUniformLocation`
   просто возвращают `-1`/`null`) — единственный сигнал раньше был
   "канвас пустой, без объяснений". `GraphScene.diagnostics` собирает
   тексты всех ошибок компиляции/линковки; `useGraphScene` логирует их в
   консоль сразу при создании сцены, вместо тихого ничего.

### Почему это масштабируется и переиспользуется

- `computeProjectGraph` (shared/lib) — чистая функция без React/WebGL,
  тестируется изолированно (`computeProjectGraph.test.ts`), может
  переиспользоваться где угодно, где нужен граф связей `Work`-элементов
  (не только в Hero).
- `GraphScene` (gl/GraphScene.ts) — не знает о React вообще: обычный
  класс с `renderFrame`/`resize`/`dispose`. Это Single Responsibility в
  прямом виде — рендер отделён от жизненного цикла компонента, отделён от
  физики раскладки (`d3-force`, которым владеет `useGraphScene`, а не
  сам `GraphScene`).
- `useGraphScene` — единственное место, где WebGL-класс встречается с
  React-жизненным циклом; сам компонент (`ProjectGraph.tsx`) — тонкая
  обёртка на пропсы.

### Отказоустойчивость

- WebGL недоступен → `canvas.getContext("webgl", ...)` возвращает `null`,
  и конструктор `GraphScene` бросает. **Важно**: это исключение вылетает
  из синхронного тела эффекта — без явного `try/catch` в `useGraphScene`
  оно уходит выше и Next.js подменяет весь сегмент лендинга своим error
  boundary, вместо того чтобы просто не показать декоративный граф (найдено
  код-ревью, не собственным тестированием — см. дату фикса ниже). `catch`
  вокруг `new GraphScene(...)` — единственное место, где это перехватывается;
  если он упал, эффект просто возвращается раньше, `sceneRef` остаётся
  `null`, компонент рендерит пустой (но структурно валидный) слой.
- Шейдер не скомпилировался → `GraphScene.diagnostics` непустой,
  `renderFrame` становится no-op'ом (проверка в начале метода) — вместо
  падения где-то в середине кадра.
- `dispose()` обязателен и вызывается в cleanup-функции эффекта — без
  этого повторные монтирования/размонтирования (переходы по страницам,
  React Strict Mode) копят живые WebGL-контексты до достижения лимита
  браузера, после чего WebGL молча перестаёт работать вообще на странице.

### SOLID-угол

`GraphScene` — Single Responsibility (только рендер, ничего о физике или
React) и Open/Closed (новые визуальные параметры добавляются через
`GraphSceneOptions`, не через правки самого класса). `useGraphScene` —
Dependency Inversion в миниатюре: он зависит от интерфейса `GraphScene`
(конструктор + `renderFrame`/`resize`/`dispose`), а не от деталей его
шейдеров — заменить рендерер на другую реализацию (скажем, чистый
Canvas2D-фолбэк для браузеров без WebGL) не потребует менять
`useGraphScene` дальше конструктора.

### v1 сознательно не делает

- **WebGL-шум/лупа-эффект через CSS** — рассмотрен и отклонён, см. пункт 2
  выше.

## 2026-08-13 — ресайз менял силы симуляции, но не "разогревал" её

Четвёртая находка код-ревью: callback `ResizeObserver` заменял
`center`-force на новый (с актуальными размерами контейнера), но
`d3-force` останавливает свой внутренний таймер, как только `alpha`
опускается ниже `alphaMin` — симуляция "остывает". Замена force ПОСЛЕ
этого момента меняет только то, что БЫЛО БЫ посчитано на следующем
тике — а тика больше не происходит вообще, значит ни новый центр, ни
`boundsForce` (читающий актуальный размер контейнера через геттер, не
снапшот) реально не доходят до позиций узлов. Раньше это било особенно
заметно в сценарии "граф проинициализирован в нулевом мобильном
контейнере, потом раскрыт на `lg`" — но даже после фикса с
`useMediaQuery` (граф теперь не монтируется на мобильных вообще) баг
остаётся реальным для любого ресайза desktop-окна после того, как
раскладка уже устоялась.

Фикс — `simulation.alpha(Math.max(simulation.alpha(), 0.3)).restart()`
сразу после замены force. `Math.max` специально, не голое
`.alpha(0.3)` — не ПОНИЖАЕТ alpha, если ресайз случился посреди драга
или начального "остывания" (уже выше 0.3), просто гарантирует, что
тики продолжатся в любом случае.

## 2026-08-13 — `hidden lg:block` прятал граф визуально, но не по стоимости

Третья находка код-ревью подряд: `Hero.tsx` изначально скрывал
`ProjectGraph` на мобильных через `className="hidden lg:block"`.
`hidden` — это только `display: none`. React всё равно монтирует
компонент: скачивает чанк, создаёт WebGL-контекст, `d3-force`-симуляцию,
запускает вечный `requestAnimationFrame`-цикл — против невидимого,
нулевого по размеру контейнера. Именно то, от чего изначальный
комментарий в коде обещал избавить ("WebGL squeezed into a narrow
column isn't worth the extra JS on mobile") — намерение было верным,
реализация его не выполняла.

Фикс — `frontend/src/shared/lib/useMediaQuery.ts` (тот же
hydration-safety паттерн, что у `usePrefersReducedMotion`: `false` на
первом рендере, коррекция в эффекте, живая переподписка на `"change"`
при пересечении порога вьюпорта). `Hero.tsx` рендерит
`{ isDesktop && <ProjectGraphLazy .../> }` — при `false` компонент не
монтируется вообще, а не просто прячется CSS'ом. `hidden lg:block`
убран из className — теперь ЕДИНСТВЕННый источник правды, монтировать
или нет, это JS-хук, а не дублирующаяся CSS-точка отказа.

## 2026-08-13 — сцена никогда не узнавала об изменившихся `options`

Ещё одна находка код-ревью: `GraphScene` хранил переданный в конструктор
`options` как обычное поле и никогда его не обновлял. Конкретный,
реальный сценарий, где это ломалось: `usePrefersReducedMotion` намеренно
стартует со значения `false` и поправляется в эффекте ПОСЛЕ маунта (тот
же hydration-safety паттерн, что у `theme.context.tsx`) — то есть
`GraphScene` создаётся с `idleFloat: true`, и если у пользователя
реально включено "уменьшить движение" в ОС, поправка на `false`
доходила только до слоя hit-target'ов в `useGraphScene` (там читается
живой `optionsRef.current` каждый кадр) — сама видимая сфера продолжала
"дышать" вечно. Это не просто визуальный баг — это нарушение
accessibility-контракта, который весь смысл `usePrefersReducedMotion` и
должен был гарантировать. Та же дыра — при переключении темы: канвас
оставался на той палитре, с которой был создан, до полного размонтирования.

Фикс: `GraphScene.setOptions()` — публичный метод, переставляющий
ссылку на `options` без пересоздания канваса/программ/FBO (сами кадры
и так читают `this.options.*` заново каждый раз, пересобирать нечего).
`useGraphScene` вызывает его в отдельном эффекте с зависимостью
`[options]` — та самая связка, которой не хватало между "опции
поменялись" и "сцена о них узнала".

## 2026-08-13 — необработанное исключение конструктора могло уронить весь Hero

Код-ревью (не собственное тестирование) поймало то, что живая проверка не
поймала: `new GraphScene(canvas, options)` вызывался в `useGraphScene`'s
эффекте без `try/catch`. `canvas.getContext("webgl")` возвращает `null`
не только в экзотических браузерах — ещё когда страница уже держит
слишком много живых WebGL-контекстов одновременно (см. этот же README,
"Куда смотреть, если что-то не так"). Конструктор в этом случае бросает
`Error`, и без перехвата это исключение уходит из пассивного эффекта
наружу — Next.js в таком случае подменяет весь сегмент лендинга своим
error boundary, а не просто пропускает рендер одного декоративного
компонента. Обёрнуто в `try/catch`: провал создания сцены теперь ведёт
к тому же исходу, что и провал компиляции шейдера (см. пункт 6 выше) —
лог в консоль, пустой слой, страница цела.

## 2026-08-13 — WebGL-канвас не знал о светлой теме

Клиренс-цвет и цвет линий сетки были захардкожены под тёмную тему
(значения буквально скопированы из плейграунда, где другой темы не было
и не предполагалось) — `GraphScene` не читал текущую тему сайта вообще.
В светлой теме получался буквально то, что и должно было получиться:
непрозрачный тёмный прямоугольник поверх светлой страницы, визуально
"отклеенный" от остального UI.

Фикс — `GraphSceneOptions` получил `backgroundColor`/`inkColor`, которые
`ProjectGraph.tsx` вычисляет через `useTheme()` (тот же контекст, что
управляет всем остальным сайтом) и передаёт в шейдер как uniform'ы
(`uBackground`/`uInk` в `GRID_FRAGMENT_SHADER`) вместо константных
`vec3(0.039,...)`/`vec3(1.0)`. Важная деталь: раньше сетка всегда
подмешивала цвет линий К БЕЛОМУ (`mix(col, vec3(1.0), ...)`) — на тёмном
фоне это давало светлую сетку с контрастом, но на светлом фоне подмес к
белому был бы просто невидим (почти тот же цвет, что и фон). Правильное
решение — не "чуть другой белый", а противоположный по контрасту цвет:
почти-белый на тёмной теме, почти-чёрный на светлой.

## 2026-08-13 — драг всё-таки понадобился

Первая версия сознательно не делала драг узлов мышью — рассуждение было
"для декоративного элемента без подсказки интерактивности пользователь
не обнаружит, что можно тащить узел". Оказалось не так: живая проверка
показала, что пользователь ОЖИДАЕТ драг именно потому, что hover уже
работает — "наведение работает, а вот передвижение — нет" читается как
баг, не как осознанное урезание scope. Ожидание интерактивности одного
типа (hover) переносится на соседний тип (drag), если оба выглядят как
"тут что-то отзывается на мышь".

Реализован через raw Pointer Events API, не `d3-drag`:
`setPointerCapture(pointerId)` на `pointerdown` — все последующие
`pointermove`/`pointerup` для этого pointer'а продолжают приходить на
тот же элемент, даже когда курсор физически ушёл за пределы маленького
кружка узла. Один код-путь для мыши/тача/пера, без document-level
слушателей. `touchAction: "none"` — только на самом hit-target-диве
(маленький кружок), не на всей секции: скролл страницы вне узлов не
затронут, тач-драг конфликтует со скроллом только в момент, когда палец
физически касается конкретного узла — тот самый точечный `touch-action`,
о котором договаривались ещё на этапе обсуждения дизайна.

Побочный найденный баг (не связанный с драгом напрямую, но всплывший при
его реализации): `GraphScene` и hit-target-слой в `useGraphScene`
считали idle-float смещение НЕЗАВИСИМО друг от друга — сфера визуально
"дышала" сама по себе, а невидимый hit-target стоял на статичной
физической позиции без смещения. Формула вынесена в общий
`gl/idleFloat.ts`, используемый и рендером, и вычислением позиции
hit-target'а, и коррекцией драга (см. `pointerToSimPoint`'s комментарий) —
единая точка правды вместо двух копий одной формулы, которые не
синхронизировались.

### Куда смотреть, если что-то не так

- Пустой канвас без ошибок в консоли → проверить `scene.diagnostics`
  вручную (`console.log`) — возможно, тихий провал компиляции на
  конкретном GPU/драйвере, который не всплыл при разработке.
- Слишком много одновременных WebGL-контекстов ("WARNING: Too many
  active WebGL contexts") → значит где-то `dispose()` не вызывается —
  первым делом проверить, что `useGraphScene`'s cleanup реально
  срабатывает (React DevTools → Profiler, посчитать монтирования).
