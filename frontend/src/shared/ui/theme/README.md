# shared/ui/theme — Design Token Architecture

## 2026-08-14 — Переход с плоского `tokens.ts` на слоистую, компилируемую архитектуру

### Что нужно было сделать

`ARCHITECTURE.md` (этот же каталог) уже описывал целевую архитектуру
(primitive → semantic → composite, генерируемый CSS, адаптеры) — но ни
строчки из неё не было реализовано: реальным кодом оставался плоский
`tokens.ts` (смешанные цветовые форматы — hex/oklch/rgba, примитивы и
семантика в одной функции `buildColors()`) и `theme.css.ts`, строивший
CSS-переменные во время выполнения через инжектируемый `<style>`-тег.
Отдельно — уже сформулированная, более строгая модель (полный аудит и
build-план см. в истории чата/плане, который привёл к этому изменению):
обязательный/опциональный контракт ролей, граф использования примитивов
для автоматического обнаружения "один primitive используется двумя
независимыми доменами — нужна promotion", и требование сделать это
переносимым на другой проект простой заменой значений.

### Что было сделано (включая тупиковые ветки — они часть истории, не только финальный код)

**Движок вынесен в отдельный npm workspace-пакет.** `packages/design-tokens`
(`@portfolio/design-tokens`) — полностью project-agnostic: ни одного
цвета, ни одного имени роли. Он даёт authoring API
(`definePrimitives`/`defineContract`/`defineTheme`/`defineComponentTokens`/
`defineComposite`), compiler (resolve + validate + usage-graph) и 2
кастомных ESLint-правила. Реальная конкретная лексика (`surfacePrimary`,
`statusDanger`, `codeBlock.keyword`) — целиком в этом каталоге. См.
`packages/design-tokens/README.md` за полным описанием движка, включая
реальные тупиковые ветки при его разработке (сигнатура `mergeTokenTree`,
типы возврата `defineXxx()`, DS101/102 ложные срабатывания на required-роли).

**Найдено вживую, не предположено: коллизия имени модуля.** Новая папка
`tokens/` (примитивы) физически не могла соседствовать с файлом
`tokens.ts` под одним и тем же именем импорта — Node/TS резолвит файл
`tokens.ts` РАНЬШЕ, чем заглядывает в `tokens/index.ts`, так что
`compiler.config.ts`'s `import { radius } from "./tokens"` молча
резолвился в СТАРЫЙ файл и возвращал `undefined` для `radius` — без
единой ошибки. Исправлено переименованием старого файла в
`legacy-tokens.ts` (чистое переименование, ноль изменений поведения) с
перенаправлением его 2 настоящих потребителей.

**Компилятор реально поймал 3 живые архитектурные проблемы при миграции
цвета** — не гипотетические примеры, а то, что `npm run tokens:generate`
буквально отказался компилировать:
1. `components/code-block.ts`'s `keyword` и `composites/shadows.ts`'s
   цвета теней оба ссылались на `{color.brand.500}` напрямую — DS201.
   Решение: оба указывают на уже существующую роль `interactivePrimary`
   (которая именно это и значит), а не изобретают новую.
2. `components/code-block.ts`'s `className` (цвет синтаксиса) и
   `components/skill-card.ts`'s декоративная иконка оба тянулись к
   `{color.accent.purple}` напрямую — DS201, на этот раз настоящий общий
   смысл ("единственный декоративный фиолетовый акцент сайта"). Решение:
   promotion в новую опциональную роль `theme.color.decorativeAccent`
   (см. `themes/shared-roles.ts`).
3. Четыре роли `theme.color.meshSpot*` существовали только для одного
   composite — DS102. Решение: примитивы инлайнятся прямо в
   `composites/gradients.ts`'s `mesh`, без промежуточной роли.

**Компонентный слой (`components/`) — первый реальный кейс.**
`ARCHITECTURE.md` явно откладывал дизайн словаря `CodeBlock`/`SkillCard`
("needs a real component-token design first; not invented here") — это
именно тот дизайн. `code-block.ts` — единственный компонент, чьи цвета
идут напрямую к примитивам (не через `{theme.color.*}`): код-панель
всегда тёмная независимо от темы сайта, так что маршрутизация через
theme-реактивную роль была бы РЕАЛЬНОЙ ошибкой, а не просто лишним слоем.

**Значимое изменение значения, не только рефакторинг:** `statusDanger` —
реально новый, отдельный красный (см. `tokens/color.ts`'s комментарий у
`danger`-шкалы) — до миграции `status-error` был алиасом на warning
(янтарный), отдельного danger-цвета не существовало. Компоненты,
использующие `bg-status-error`/`text-status-error`, увидят другой цвет —
осознанно, не побочный эффект.

**Bridge, не переименование 100+ call sites.** Новые семантические имена
ролей (`surfaceElevated`, `statusDanger`, ...) существуют как источник
истины в `themes/dark.ts`/`light.ts`, но `adapters/tailwind.css`
СОЗНАТЕЛЬНО не 1:1-проброс — он мостит их на СТАРЫЕ, уже используемые по
всему приложению class-facing имена (`--color-surface-base`,
`--color-status-error`, ...). Переименовать каждый вызов в реальных
компонентах в этом же изменении означало бы огромный, рискованный radius
без визуального regression-тулинга в этой среде для проверки. Миграция
самих call sites на новые имена — реальный, документированный follow-up,
а не тихо забытый пункт.

**Раздел `layout`/`zIndex` — сознательно вне периметра.** Это не одна из
категорий этой архитектуры (color/dimension/radius/typography/motion/
shadow) — структурные константы страницы (навбар, z-индексы), не токены
дизайна. Остались на старом механизме runtime-инжекции
(`legacy-layout-vars.ts`), единственный оставшийся кусок этого механизма.

### Понятность для другого разработчика

Каждый файл на границе (adapters/, themes/shared-roles.ts,
composites/gradients.ts) содержит комментарий, называющий РЕАЛЬНОЕ
архитектурное правило, которое он соблюдает или обходит, и почему —
не просто "что" код делает. `contracts/*.ts` — единственное место, где
живёт список обязательных ролей (не два синхронизируемых вручную места).

### Нагрузка

Компилятор (`packages/design-tokens`) — build-time-only зависимость
`frontend/scripts/generate-design-tokens.ts`; ничего из adapters/ не
импортирует его в runtime (кроме одной документированной, обоснованной
исключения — `hslStringToRgb01`, чистая функция без токен-специфичной
логики). `generated/tokens.css` — статический, закоммиченный файл,
подключаемый обычным `@import`, не JS во время рендера.

### Расширяемость/заменяемость

Три операционных процесса (настройка нового проекта с нуля, ре-скин под
новый бренд, расширение любого рода) описаны в
`packages/design-tokens/README.md`, с конкретными примерами кода. Новая
категория (например, `elevation`) повторяет тот же паттерн
`definePrimitives` → `defineContract` → `defineTheme`/`semantic/*.ts`, а
не жёстко заданный список из 6 категорий.

### Миграция/отказоустойчивость

`npm run tokens:check` (генерация + `git diff --exit-code`) — часть CI
(`backend-web-checks.yml`), гарантирует, что закоммиченный
`generated/tokens.css` никогда не расходится с реальным исходником
токенов. Визуальные Playwright-baseline'ы (page-level, component-gallery,
OG-image) требуют регенерации после этого изменения — реальное изменение
пикселей (danger-цвет, hue брендового акцента), не просто рефакторинг;
регенерация — через CI/Docker (см. `frontend/tests/README.md`, раздел 2,
про рендеринг шрифтов), не сырой локальный запуск на Windows.

### SOLID

**SRP** — движок (packages/design-tokens) не знает ни одного имени роли;
контент проекта (этот каталог) не знает, как резолвятся ссылки. **OCP** —
новая категория/роль/компонент добавляется без изменения compile.ts.
**DIP** — `usage-graph.ts` читает `__kind`/`__namespace` с самих объектов
(проставленных authoring-функциями), а не выводит их из пути файла —
compile.ts не зависит от файловой структуры проекта вообще.

## 2026-08-14 — `layout`/`z-index` домигрированы, runtime-инжекция убрана полностью

### Что нужно было сделать

Единственный оставшийся кусок старого механизма — `legacyLayoutVars`'s
runtime-инжектируемый `<style>`-тег в `<head>` (см. запись выше) — убрать,
раз уж движок уже построен и добавить 7-ю/8-ю "категорию" по тому же
паттерну дешевле, чем оставлять два параллельных механизма навсегда.

### Что было сделано

Добавлены `tokens/layout.ts` и `tokens/z-index.ts` — чистые примитивы, без
слоя contracts/semantic (эти значения уже role-shaped, как
`tokens/typography.ts`'s `size`, а не generic-шкала). Ключевой нюанс,
найденный при реальном использовании (`grep` по всем call sites, не
предположение): `layout.*` читается через Tailwind's arbitrary-value
`var()`-синтаксис (`max-w-(--layout-content-max-width)`) — ему НЕ нужна
регистрация внутри `@theme`, только чтобы CSS-переменная существовала
где-то на `:root`. А вот `z-index`'s роли (`navbar`, `overlay`, ...)
используются как НАСТОЯЩИЕ Tailwind-классы (`z-navbar`) — этим ДЕЙСТВИТЕЛЬНО
нужна регистрация внутри `@theme`, иначе Tailwind не сгенерирует класс
вообще. Обе категории собраны под ключами `"layout"` и `"z"` (не `"zIndex"`)
в `compiler.config.ts` — специально, чтобы сгенерированное имя
(`--ds-z-navbar`) совпадало с существующим class-facing именем
(`z-navbar`) после короткого bridge-моста в `adapters/tailwind.css`, без
переименования полутора десятков реальных call sites.

`legacy-layout-vars.ts` и `legacy-tokens.ts` полностью удалены;
`app/layout.tsx`/`global-error.tsx` больше не рендерят `<style
dangerouslySetInnerHTML>` вообще — весь дизайн-токен теперь приходит из
одного статического `@import` в `app/styles/index.css`.

### Проверено вживую

`npx tsc --noEmit`, `npm run build` (полная продакшн-сборка), `npm test`
(468 тестов) — все чистые после удаления runtime-инжекции.

## 2026-08-14 — Реальный живой баг: Mermaid не мог отрендерить `alpha()`-роли

Найдено не линтером — реальной ошибкой на странице: `Diagram render error:
Unsupported color format: "color-mix(in srgb, hsl(20 94% 61%) 12%,
transparent)"`. Причина: `interactivePrimarySubtle` (используется
`adapters/mermaid.ts`'s `tertiaryColor`) резолвился через `alpha()`, который
компилировался в CSS `color-mix()` — валидно для браузера, но у Mermaid's
"base"-темы своя собственная цветовая библиотека без доступа к CSS-движку,
и она не умеет парсить `color-mix()`.

Исправлено в `packages/design-tokens/src/references.ts` (не костылём вокруг
Mermaid): раз все примитивы уже валидированные `hsl()`-строки, `alpha()`
теперь использует нативный alpha-канал `hsl()` (`hsl(H S% L% / A%)`) —
визуально идентично `color-mix(...)`, но это простой, парсимый литерал, а
не CSS-функция. См. полную историю и `color-mix()`-фоллбэк в
`packages/design-tokens/README.md`'s датированной записи.

## 2026-08-14 — Устаревшее замечание бота про `interactivePrimarySubtle`, и мутационные тесты для `adapters/mermaid.ts`

Бот (chatgpt-codex-connector) отметил `adapters/mermaid.ts`'s `tertiaryColor:
c.interactivePrimarySubtle` как всё ещё резолвящийся в `color-mix(...)` —
то есть тот же баг, что выше. Проверка по `generated/resolved.ts` показала,
что замечание устарело: значение уже `"hsl(20 94% 61% / 12%)"`, фикс из
предыдущей записи применился. Но одной проверки по сгенерированному файлу
недостаточно — она не доказывает, что именно `khroma` (реальная библиотека
внутри Mermaid) это распарсит. Проверено напрямую через установленный в
проекте `khroma@2.1.0` (подтверждён как ровно та версия, которую тянет
`mermaid@11.16.1`, через `npm ls khroma --all`):
`khroma.isValid('hsl(20 94% 61% / 12%)')` → `true`,
`khroma.isValid('color-mix(in srgb, hsl(20 94% 61%) 12%, transparent)')` →
`false` (воспроизводит оригинальную ошибку буква в букву).

Чтобы эта проверка не осталась разовым `node -e` в терминале, `khroma`
добавлен в `frontend/package.json`'s `devDependencies` явно (раньше был
доступен только транзитивно через `mermaid`, через hoisting — ломкая
зависимость от структуры `node_modules`), и появился
`adapters/mermaid.test.ts`: параметризованный тест по обеим темам проверяет
через настоящий `khroma.isValid()`, что каждое цвет-значение в
`themeVariables` реально парсится, плюс отдельный тест жёстко фиксирует
`interactivePrimarySubtle` как `"hsl(20 94% 61% / 12%)"` с alpha ≈ 12%
(через `khroma.toHex()`).

**Мутационное тестирование.** `adapters/mermaid.ts` добавлен в
`stryker.config.mjs`'s `mutate` (и тест — в `vitest.mutation.config.ts`'s
`include`). Первый прогон: **60% по файлу, 2 выживших** — оба на строковых
литералах `"transparent"` (background) и `"'JetBrains Mono', monospace"`
(fontFamily). Причина ровно та, что описана выше про `json-ld.ts`: тест
явно исключал эти два поля из цикла `isValid()` (не цвета, `khroma` их не
видит), но ничего не утверждал про их точное значение — мутация в `""`
никакую проверку не ломала. Исправлено тем же способом (усиление
существующего утверждения, а не новый тест): после деструктуризации
`background`/`fontFamily` из цикла добавлены прямые `toBe()` на их
литеральные значения. Повторный прогон — **100% по файлу (5/5 убито)**.

Итог по всему проекту: **97.14%** (571 убито, 2 выживших, 6 таймаутов, 15 без
покрытия из 641 немутированных — статические игнорируются `ignoreStatic`).
Оба оставшихся выживших — в `shared/ui/block-editor/convert.ts`, существовали
до этой задачи и к ней не относятся (см. записи выше про 2026-08-11/12).
Порог `break: 75` не менялся — по той же причине, что и раньше: поднимать
его до фактических ~97 сделало бы любой будущий не-100% файл красным без
отдельного решения об этом.

## 2026-08-14 — Реальный баг из код-ревью бота: `ProjectGraph`'s ink совпадал с фоном

Бот (chatgpt-codex-connector) на `adapters/project-graph.ts` указал, что
`ink` резолвится через `textInverse`, а `textInverse` в обеих темах
**идентичен** `surfacePrimary` (`themes/dark.ts`: оба — `{color.neutral.950}`;
`themes/light.ts`: оба — `{color.neutral.0}`) — семантически `textInverse`
означает «текст НА инверсной поверхности» (например, текст на светлом чипе
в тёмной теме), а не «контраст с primary-фоном». Раз WebGL-сцена берёт
`background`/`ink` как两 отдельные RGB-uniform'ы для фона канваса и
цвета сетки/деталей графа (`ProjectGraph.tsx`), совпадающие значения
делали сетку и детали графа не видимыми на фоне — реальный, а не
косметический баг. Правильная роль — `textPrimary`: она определена именно
как читаемая НА `surfacePrimary` в обеих темах.

**Исправлено:** `ink: hslStringToRgb01(resolved.X.color.textPrimary)`
вместо `textInverse` в обоих темах.

**Тест, который поймал бы это раньше.** Добавлен
`adapters/project-graph.test.ts`: реальный инвариант — `ink !== background`
в каждой теме — плюс жёсткая проверка, что `ink` резолвится именно через
`textPrimary`. Проверено вручную (не предположение): временно вернул
`textInverse` — тест красный, ровно на утверждении про `ink !== background`
и про `textPrimary`; вернул фикс — тест зелёный.

**Второй урок при добавлении файла в мутационный скоуп — то же самое, что
уже описано в записи про `site-url.ts` выше, только не угаданное, а
буквально повторно наступленное.** Первый прогон Stryker с
`project-graph.ts` в `mutate`: все 3 мутанта (единственный top-level
объектный литерал) — `Ignored`, не протестированы по-настоящему. Причина
та же: `projectGraphScenePalette` вычисляется один раз при загрузке модуля,
а обычный top-level `import` в тесте запускает эту загрузку один раз на
весь файл — Stryker не может привязать покрытие к конкретному тесту и
считает мутант статическим. Исправлено идентичным приёмом:
`vi.resetModules()` + динамический `import()` внутри каждого теста.
Повторный прогон — **100% по файлу (3/3 убито)**, никаких `Ignored`.

Итог по всему проекту после обоих файлов: **97.15%** (574 убито, 2
выживших — всё те же, унаследованные, в `block-editor/convert.ts` — 6
таймаутов, 47 без покрытия из 644). Порог `break: 75` не менялся — та же

## 2026-08-15 — Phase 0 миграции dimension/typography: три параллельные системы типографики → одна, fluid `hero`/`h1`

Аудит нашёл три параллельные системы: `tokens/typography.ts` +
`composites/typography-styles.ts` (структура без потребителей — компилятор
`packages/design-tokens`'s `compile.ts` умеет сериализовывать только
composite-виды `"gradient"`/`"shadow"`, `"typographyStyle"` молча
игнорировался, ничего не попадало в `generated/tokens.css`), мёртвый файл
`theme/typography.ts` (fluid `clamp()` на `vh`, экспортировался из
`theme/index.ts`, но ни один реальный компонент его не импортировал — сам
`Text.tsx` уже перешёл на токен-класс через `adapters/tailwind.css`
независимо), и то, что реально рисует `Text.tsx` (фиксированные rem через
Tailwind-бридж, кроме `h4`/`h5` — те падали на голый Tailwind `text-2xl`/
`text-xl`).

**Удалено, не «примирено».** `composites/typography-styles.ts` удалён
целиком (и из `compiler.config.ts`, `composites/index.ts`) — его
size+weight+lineHeight-связка уже дублирует то, что `Text.tsx`'s
`variantClasses` и так делает через композицию Tailwind-классов; чинить
компилятор пакета под несуществующего потребителя не было смысла. Мёртвый
`theme/typography.ts` удалён вместе с реэкспортом `typography`/`TextVariant`
из `theme/index.ts` — подтверждено grep'ом по всему `frontend/src`, что ни
один файл не импортирует ни то, ни другое.

**Fluid `hero`/`h1`, без выдуманных границ.** 4 страницы копировали
`clamp()`-числа руками в JSX, и это оказались 4 РАЗНЫХ диапазона, не один.
Hero.tsx (единственный потребитель `hero`) — `clamp(40px, 5.5vw, 64px)`,
максимум точно совпадал с текущим фиксированным токеном. JournalDetailPage
— `clamp(30px, 4.2vw, 44px)`; WorkDetailPage — `clamp(32px, 4.5vw, 48px)`
для того же по смыслу `h1`. Спросил пользователя, не выбрал сам: для `h1`
принята граница WorkDetailPage (32-48px) — JournalDetailPage's заголовок
на десктопе вырос с 44 до 48px. Обе границы переведены в формулу
`slope/intercept` с опорными ширинами 320px/1280px (методика из
исследования 2026 best practices) и выражены в `rem + vw`, никогда `vh`:
- `hero: clamp(2.5rem, 2rem + 2.5vw, 4rem)`
- `h1: clamp(2rem, 1.67rem + 1.67vw, 3rem)`

Проверено вживую через Playwright на реальном dev-сервере (не поверил
формуле на бумаге): `hero` даёт 40px/51.2px/64px/64px на 320/768/1280/1600px
— плавно, упирается в границы как задумано. `h1` на двух реальных страницах
(`journal/testing-culture`, `work/onvif-camera-library`) — 32.064px на
320px (крошечная погрешность округления коэффициентов, визуально
неотличима) и ровно 48px на 1280px на обеих.

`display` НЕ стал fluid — единственный потребитель этого variant'а —
демо-страница Storybook, значит нет живого числа, которое можно перенести
без выдумывания — оставлен фиксированным `3.25rem`, честно отмечено в
комментарии, а не сделано тихо.

**`font-extrabold`, а не `font-bold`.** Все 4 страницы использовали
`font-extrabold` (800) для заголовка, а `Text.tsx`'s `hero`/`h1` variant
применял `font-bold` (700) — перенос на `<Text>` без этого фикса реально
уменьшил бы вес шрифта. Токен `weight.extrabold: 800` уже существовал в
`tokens/typography.ts`, просто не был прокинут в `adapters/tailwind.css`
(`--font-weight-extrabold` отсутствовал) — добавлен, `hero`/`h1` теперь
используют `font-extrabold`. `display` оставлен на `font-bold` — тоже
нет живого примера, на который можно бы было опереться.

**`h4`/`h5` — снэп к ближайшему, не выдумка.** `h5` реально используется
(6+ мест в админке, всегда как заголовок секции) и его старый `text-xl`
(20px) точно совпадал с токеном `h3` (1.25rem). `h4` не используется вообще
нигде, кроме демо, и его старый `text-2xl` (24px) был БОЛЬШЕ `h3` —
перевёрнутая иерархия заголовков. Оба алиасятся на `h3` вместо выдумывания
нового шага (реальных данных для `h4` нет, а `h5` анализ дал точное
совпадение).

## 2026-08-15 — Phase 1 миграции dimension: реальный баг `w-{key}` (перехват шириной container-скейла), а не только замена хардкода

`adapters/tailwind.css`'s WIDTH-FAMILY RECLAIM (см. запись про Tailwind v4
выше в этом README) регистрирует `--width-xs..4xl` = `var(--container-*)`
— то есть именно для КЛЮЧЕЙ, совпадающих с dimension-шкалой (`xs`...`4xl`),
класс `w-{key}` резолвится в container-ширину, а НЕ в spacing-значение,
хотя `h-{key}` для того же самого ключа резолвится в spacing корректно.
Проверено не рассуждением, а напрямую: прочитан скомпилированный CSS —
`.h-xl { height: var(--spacing-xl); }` (32px, верно) против
`.w-xl { width: var(--width-xl); }` → `var(--container-xl)` (576px,
неверно для иконки). Это уже жило в проде до этой миграции —
`SkillCard.tsx`'s `w-xl h-xl` и `themeToggle.styles.ts`'s `optionIcon`'s
`w-md h-md` оба объявляли иконку шириной в сотни пикселей, замаскированную
чем-то другим в рендере (не воспроизведено визуально как явный баг, но
CSS был объективно неверным). Оба исправлены тем же приёмом, что и все
новые квадратные иконки в этой фазе: `h-{key} aspect-square w-auto` —
`w-auto` обязателен отдельно, иначе `aspect-square` не переопределяет
собственный HTML-атрибут `width` SVG-иконки (проверено: без `w-auto`
получалось `24×32`, не квадрат, хотя `aspect-ratio` в computed style
показывал `1/1`).

Для НЕ-квадратных ширин на зарезервированных ключах (`hover:w-[4.5rem]` в
`AdminListItem.tsx`'s `RevealAction`, 72px→5xl/80px) — `aspect-square` не
применим, использован `w-(--spacing-5xl)` (та же произвольно-var-синтаксис
форма, что уже применяется для layout-токенов — `max-w-(--layout-*)`),
минуя сломанный именной lookup целиком.

**Батч решений по неоднозначным кластерам** (полный список см. в плане
задачи): размеры иконок/контролов без точного совпадения со шкалой —
снэп к ближайшему шагу, при истинной "вилке 50/50" — крупнее для
контролов (touch target), меньше для spacing/gap. Sub-`xxs` (2-3px)
внутри pill-тумблеров (`LanguageSegmentedToggle`, `ThemeSegmentedToggle`,
`DiagramBlock`'s `SegmentedToggle`) оставлены как есть — это уже
pixel-perfect границы внутри pill, а не отступ между блоками. `tracking-
[0.12em]` в `Eyebrow.tsx` снэпнут на `tracking-widest` (0.1em,
Tailwind-дефолт) — категории letter-spacing в токенах вообще нет.

**Найдено и удалено, не мигрировано.** `shared/ui/Input.tsx` (не
`shared/ui/form/Input.tsx` — два разных файла) использовал чужую
Tailwind-палитру (`bg-neutral-900`, `text-neutral-300` и т.п., вообще не
токены этого проекта) — grep по всему `frontend/src` подтвердил: его не
импортирует ни один файл. Удалён целиком, а не починен — фиксить
хардкод в мёртвом коде было бы бессмысленной работой.

**`text-[17px]!` в `RelatedContentCallout.tsx`** — перебивал `variant="h3"`
собственный размер силой; убран, оставлен настоящий h3 (20px) без
подмены. Визуально проверено на реальном посте со связанным проектом —
выглядит нормально.
