# shared/ui/theme — Design Token Architecture

## 2026-08-14 — Переход с плоского `tokens.ts` на слоистую, компилируемую архитектуру

### Что нужно было сделать

`ARCHITECTURE.md` (этот же каталог) уже описывал целевую архитектуру
(primitive → semantic → composite, генерируемый CSS, адаптеры) — но ни
строчки из неё не было реализовано: реальным кодом оставался плоский
`tokens.ts` (смешанные цветовые форматы — hex/oklch/rgba, примитивы и
семантика в одной функции `buildColors()`) и `theme.css.ts`, строивший
CSS-переменные во время выполнения через инжектируемый `<style>`-тег.
Отдельно — уже сформулированная, более строгая модель (полный аудит и
build-план см. в истории чата/плане, который привёл к этому изменению):
обязательный/опциональный контракт ролей, граф использования примитивов
для автоматического обнаружения "один primitive используется двумя
независимыми доменами — нужна promotion", и требование сделать это
переносимым на другой проект простой заменой значений.

### Что было сделано (включая тупиковые ветки — они часть истории, не только финальный код)

**Движок вынесен в отдельный npm workspace-пакет.** `packages/design-tokens`
(`@portfolio/design-tokens`) — полностью project-agnostic: ни одного
цвета, ни одного имени роли. Он даёт authoring API
(`definePrimitives`/`defineContract`/`defineTheme`/`defineComponentTokens`/
`defineComposite`), compiler (resolve + validate + usage-graph) и 2
кастомных ESLint-правила. Реальная конкретная лексика (`surfacePrimary`,
`statusDanger`, `codeBlock.keyword`) — целиком в этом каталоге. См.
`packages/design-tokens/README.md` за полным описанием движка, включая
реальные тупиковые ветки при его разработке (сигнатура `mergeTokenTree`,
типы возврата `defineXxx()`, DS101/102 ложные срабатывания на required-роли).

**Найдено вживую, не предположено: коллизия имени модуля.** Новая папка
`tokens/` (примитивы) физически не могла соседствовать с файлом
`tokens.ts` под одним и тем же именем импорта — Node/TS резолвит файл
`tokens.ts` РАНЬШЕ, чем заглядывает в `tokens/index.ts`, так что
`compiler.config.ts`'s `import { radius } from "./tokens"` молча
резолвился в СТАРЫЙ файл и возвращал `undefined` для `radius` — без
единой ошибки. Исправлено переименованием старого файла в
`legacy-tokens.ts` (чистое переименование, ноль изменений поведения) с
перенаправлением его 2 настоящих потребителей.

**Компилятор реально поймал 3 живые архитектурные проблемы при миграции
цвета** — не гипотетические примеры, а то, что `npm run tokens:generate`
буквально отказался компилировать:
1. `components/code-block.ts`'s `keyword` и `composites/shadows.ts`'s
   цвета теней оба ссылались на `{color.brand.500}` напрямую — DS201.
   Решение: оба указывают на уже существующую роль `interactivePrimary`
   (которая именно это и значит), а не изобретают новую.
2. `components/code-block.ts`'s `className` (цвет синтаксиса) и
   `components/skill-card.ts`'s декоративная иконка оба тянулись к
   `{color.accent.purple}` напрямую — DS201, на этот раз настоящий общий
   смысл ("единственный декоративный фиолетовый акцент сайта"). Решение:
   promotion в новую опциональную роль `theme.color.decorativeAccent`
   (см. `themes/shared-roles.ts`).
3. Четыре роли `theme.color.meshSpot*` существовали только для одного
   composite — DS102. Решение: примитивы инлайнятся прямо в
   `composites/gradients.ts`'s `mesh`, без промежуточной роли.

**Компонентный слой (`components/`) — первый реальный кейс.**
`ARCHITECTURE.md` явно откладывал дизайн словаря `CodeBlock`/`SkillCard`
("needs a real component-token design first; not invented here") — это
именно тот дизайн. `code-block.ts` — единственный компонент, чьи цвета
идут напрямую к примитивам (не через `{theme.color.*}`): код-панель
всегда тёмная независимо от темы сайта, так что маршрутизация через
theme-реактивную роль была бы РЕАЛЬНОЙ ошибкой, а не просто лишним слоем.

**Значимое изменение значения, не только рефакторинг:** `statusDanger` —
реально новый, отдельный красный (см. `tokens/color.ts`'s комментарий у
`danger`-шкалы) — до миграции `status-error` был алиасом на warning
(янтарный), отдельного danger-цвета не существовало. Компоненты,
использующие `bg-status-error`/`text-status-error`, увидят другой цвет —
осознанно, не побочный эффект.

**Bridge, не переименование 100+ call sites.** Новые семантические имена
ролей (`surfaceElevated`, `statusDanger`, ...) существуют как источник
истины в `themes/dark.ts`/`light.ts`, но `adapters/tailwind.css`
СОЗНАТЕЛЬНО не 1:1-проброс — он мостит их на СТАРЫЕ, уже используемые по
всему приложению class-facing имена (`--color-surface-base`,
`--color-status-error`, ...). Переименовать каждый вызов в реальных
компонентах в этом же изменении означало бы огромный, рискованный radius
без визуального regression-тулинга в этой среде для проверки. Миграция
самих call sites на новые имена — реальный, документированный follow-up,
а не тихо забытый пункт.

**Раздел `layout`/`zIndex` — сознательно вне периметра.** Это не одна из
категорий этой архитектуры (color/dimension/radius/typography/motion/
shadow) — структурные константы страницы (навбар, z-индексы), не токены
дизайна. Остались на старом механизме runtime-инжекции
(`legacy-layout-vars.ts`), единственный оставшийся кусок этого механизма.

### Понятность для другого разработчика

Каждый файл на границе (adapters/, themes/shared-roles.ts,
composites/gradients.ts) содержит комментарий, называющий РЕАЛЬНОЕ
архитектурное правило, которое он соблюдает или обходит, и почему —
не просто "что" код делает. `contracts/*.ts` — единственное место, где
живёт список обязательных ролей (не два синхронизируемых вручную места).

### Нагрузка

Компилятор (`packages/design-tokens`) — build-time-only зависимость
`frontend/scripts/generate-design-tokens.ts`; ничего из adapters/ не
импортирует его в runtime (кроме одной документированной, обоснованной
исключения — `hslStringToRgb01`, чистая функция без токен-специфичной
логики). `generated/tokens.css` — статический, закоммиченный файл,
подключаемый обычным `@import`, не JS во время рендера.

### Расширяемость/заменяемость

Три операционных процесса (настройка нового проекта с нуля, ре-скин под
новый бренд, расширение любого рода) описаны в
`packages/design-tokens/README.md`, с конкретными примерами кода. Новая
категория (например, `elevation`) повторяет тот же паттерн
`definePrimitives` → `defineContract` → `defineTheme`/`semantic/*.ts`, а
не жёстко заданный список из 6 категорий.

### Миграция/отказоустойчивость

`npm run tokens:check` (генерация + `git diff --exit-code`) — часть CI
(`backend-web-checks.yml`), гарантирует, что закоммиченный
`generated/tokens.css` никогда не расходится с реальным исходником
токенов. Визуальные Playwright-baseline'ы (page-level, component-gallery,
OG-image) требуют регенерации после этого изменения — реальное изменение
пикселей (danger-цвет, hue брендового акцента), не просто рефакторинг;
регенерация — через CI/Docker (см. `frontend/tests/README.md`, раздел 2,
про рендеринг шрифтов), не сырой локальный запуск на Windows.

### SOLID

**SRP** — движок (packages/design-tokens) не знает ни одного имени роли;
контент проекта (этот каталог) не знает, как резолвятся ссылки. **OCP** —
новая категория/роль/компонент добавляется без изменения compile.ts.
**DIP** — `usage-graph.ts` читает `__kind`/`__namespace` с самих объектов
(проставленных authoring-функциями), а не выводит их из пути файла —
compile.ts не зависит от файловой структуры проекта вообще.

## 2026-08-14 — `layout`/`z-index` домигрированы, runtime-инжекция убрана полностью

### Что нужно было сделать

Единственный оставшийся кусок старого механизма — `legacyLayoutVars`'s
runtime-инжектируемый `<style>`-тег в `<head>` (см. запись выше) — убрать,
раз уж движок уже построен и добавить 7-ю/8-ю "категорию" по тому же
паттерну дешевле, чем оставлять два параллельных механизма навсегда.

### Что было сделано

Добавлены `tokens/layout.ts` и `tokens/z-index.ts` — чистые примитивы, без
слоя contracts/semantic (эти значения уже role-shaped, как
`tokens/typography.ts`'s `size`, а не generic-шкала). Ключевой нюанс,
найденный при реальном использовании (`grep` по всем call sites, не
предположение): `layout.*` читается через Tailwind's arbitrary-value
`var()`-синтаксис (`max-w-(--layout-content-max-width)`) — ему НЕ нужна
регистрация внутри `@theme`, только чтобы CSS-переменная существовала
где-то на `:root`. А вот `z-index`'s роли (`navbar`, `overlay`, ...)
используются как НАСТОЯЩИЕ Tailwind-классы (`z-navbar`) — этим ДЕЙСТВИТЕЛЬНО
нужна регистрация внутри `@theme`, иначе Tailwind не сгенерирует класс
вообще. Обе категории собраны под ключами `"layout"` и `"z"` (не `"zIndex"`)
в `compiler.config.ts` — специально, чтобы сгенерированное имя
(`--ds-z-navbar`) совпадало с существующим class-facing именем
(`z-navbar`) после короткого bridge-моста в `adapters/tailwind.css`, без
переименования полутора десятков реальных call sites.

`legacy-layout-vars.ts` и `legacy-tokens.ts` полностью удалены;
`app/layout.tsx`/`global-error.tsx` больше не рендерят `<style
dangerouslySetInnerHTML>` вообще — весь дизайн-токен теперь приходит из
одного статического `@import` в `app/styles/index.css`.

### Проверено вживую

`npx tsc --noEmit`, `npm run build` (полная продакшн-сборка), `npm test`
(468 тестов) — все чистые после удаления runtime-инжекции.
