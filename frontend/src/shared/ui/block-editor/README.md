# shared/ui/block-editor — BlockNote WYSIWYG editor (replaces `BlockListEditor`/`BlockFields`)

## Будет ли переиспользоваться?

Да, ровно как и раньше: `admin-post-editor` использует `<BlockEditor>` для
тела поста, `admin-work-editor` — для нарратива кейс-стади, а с этой
фазой к ним добавились `admin-post-translate`/`admin-work-translate` —
русский перевод тела/кейс-стади это тот же самый `<BlockEditor>`, просто с
другим начальным содержимым (см. `backend/src/content/README.md`'s
unification rationale — тело поста и кейс-стади это один и тот же
`Document`, теперь ещё и русский перевод — тоже просто `Document`, не
отдельная форма).

## Зачем полностью новый компонент, а не доработка `BlockListEditor`

**Что нужно сделать.** Заменить форму "выбери тип блока из списка → нажми
Add block → заполни поля" на настоящий WYSIWYG: слэш-меню для вставки
блока, тулбар форматирования (**bold**/*italic*/ссылки) при выделении
текста, смену типа блока через тот же слэш-интерфейс.

**Как сделано.** [BlockNote](https://www.blocknotejs.org/) (`@blocknote/core`
+ `@blocknote/react` + `@blocknote/mantine`) — редактор поверх
ProseMirror/Tiptap с собственной схемой блоков, слэш-меню и тулбаром "из
коробки". Старый `BlockListEditor`/`BlockFields`/`draft-block.ts`
(`DraftBlock`, add/remove/reorder кнопки, восемь отдельных мини-форм)
удалены целиком, а не доработаны — они решали ровно проблему "форма для
редактирования полей", которую WYSIWYG-редактор не имеет вообще (нет ни
`DraftBlock`, ни кнопок "вверх"/"вниз": переставить блок в BlockNote — это
просто перетащить его).

### Схема (`schema.ts`) — почему не "все блоки — кастомные" и не "все — дефолтные"

`BlockNoteSchema.create({ blockSpecs: {...} })` с явным списком, не
`.create().extend({...})` (дефолты + добавки) — сайт рендерит ровно 10 типов
блоков (`backend/src/content/blocks.ts`; было 8 до записи 2026-08-03 ниже,
добавившей `list`), а полный дефолтный набор BlockNote (таблицы,
video/audio/file, свой `codeBlock`) дал бы редактору создавать контент, для
которого у `<ContentBlocks>` просто нет кейса. `bulletListItem`/
`numberedListItem` — исключение из этого правила, см. запись ниже.

Только `paragraph` и `heading` — настоящие дефолты BlockNote (`heading`
переконфигурирован на уровни 2/3 — `createHeadingBlockSpec({ levels: [2, 3] })`
— у поста/кейс-стади нет визуального `<h1>`, это уже `<h1>` страницы).
Все остальные — кастомные (`blocks/*.tsx`), и не потому что "все кастомные
интереснее", а по конкретной причине на тип:

- **`quote`** — переопределён, не расширен: у встроенного `quote` нет
  `attribution`, только `backgroundColor`/`textColor`.
- **`note`** — нет дефолтного аналога вообще (callout с вариантом
  info/warning/tip).
- **`image`** — свой `alt` (обязательный, для доступности) вместо
  дефолтных `name`/upload-виджета, которому тут не с чем работать (нет
  backend-эндпоинта загрузки — как и раньше, картинки лежат в
  `frontend/public/`, это просто текстовое поле URL).
- **`code`** — свой `filename`, которого у встроенного `codeBlock` нет;
  сам текст кода — `props.code` (обычный `<Textarea>`), не BlockNote
  rich-text — код не должен получать bold/italic из тулбара.
- **`approachList`** — нет дефолтного аналога вообще; список
  title+description пар нет способа выразить как BlockNote-проп напрямую
  (`PropSchema` — только `boolean | number | string`), поэтому это один
  JSON-строковый проп `itemsJson` (`parseApproachItems`/`JSON.stringify`)
  с собственным add/remove/edit UI внутри блока — тот же UX, что был у
  старого `ApproachListFields`, просто как нода внутри канвы редактора, а
  не отдельная секция формы.

### Конвертация (`convert.ts`) — почему через "голый paragraph", а не напрямую

**Что нужно сделать.** Хранилище (Postgres) видит блок как plain-string
`text`/`data` (`backend/src/content/blocks.ts`) — редактор видит его как
BlockNote-блок с rich-text `content` (список inline-нод со стилями). Нужна
граница между двумя формами в обе стороны, причём **bold**/*italic*/ссылки
должны реально сохраняться как Markdown, не потеряться.

**Как сделано, и какой был неверный первый заход.** Первая идея — звать
`editor.blocksToMarkdownLossy([block])` прямо на блоке "heading"/"quote"/
"note" целиком. Не подошло: эти методы сериализуют блок ПОЛНОСТЬЮ, включая
его собственный блочный Markdown-синтаксис — `"## "` для heading, `"> "`
для quote — а `type` блока в этой схеме уже кодирует "это heading", хранить
`"## "` ещё и внутри `text` означало бы задвоение (на публичной странице
`<ContentBlocks>` уже сама решает, что это `<h2>`). Исправлено: перед
сериализацией/парсингом content оборачивается в "голый" `{ type:
"paragraph", content }` — у paragraph нет собственного префикса, так что
результат — ровно inline-разметка, ничего больше. Симметрично в обе
стороны: `markdownToInlineContent`/`inlineContentToMarkdown`.

Парсинг (`tryParseMarkdownToBlocks`) — метод РЕДАКТОРА, не отдельная
утилита (Markdown-поддержка в BlockNote завязана на ту же
ProseMirror-схему, что и сам редактор), но оба метода в этой версии
BlockNote синхронные (не `Promise` — проверено по `ExportManager.d.ts`),
поэтому `blocksToPartialBlocks` создаёт свой одноразовый, никогда не
монтируемый `BlockNoteEditor.create({ schema })` только для парсинга —
`.create()` без последующего `.mount(element)` не создаёт реальный
ProseMirror `EditorView`, так что ничего не нужно чистить/уничтожать после
использования.

### `BlockEditor` — почему `ref.getBlocks()`, а не `value`/`onChange`

Старый `BlockListEditor` был полностью controlled: `blocks`/`onChange`,
родитель (`PostEditorPage`) хранил `DraftBlock[]` в своём `useState` и
пере-рендерился на каждое изменение. `<BlockEditor>` — нет: BlockNote
(`useCreateBlockNote`) уже держит живой ProseMirror-документ всё время,
пока редактор смонтирован; зеркалить каждую нажатую клавишу обратно в
родительский `Block[]`/`BlockInput[]` (гоняя `blocksToMarkdownLossy` на
каждый символ) — чистая трата, если это значение не нужно никому до
момента отправки формы. Вместо этого `BlockEditor` — `forwardRef` с
`useImperativeHandle`, отдающий `getBlocks(): BlockInput[]` — вызывается
ровно один раз, в `handleSubmit` вызывающей страницы.

## 2026-07-19 — Два реальных краша, найденных вживую после первого деплоя (не в тестах)

**Что произошло.** Пользователь открыл `/admin/journal/[slug]/edit` для
поста с блоком кода и получил `Runtime Error`. Оба нижеописанных бага —
классический пример того, почему "вручную проверено в браузере" не
опционально: юнит-тесты (jsdom) прошли зелёными, `next build` прошёл, но
jsdom и настоящий Next.js SSR — не одна и та же среда.

**Баг 1 — `"code"` не может быть одновременно блоком и inline-стилем.**
Кастомный блок `code` был зарегистрирован в BlockNote под тем же именем
`"code"`, что и дефолтный inline-стиль `code` (форматирование `` `код` ``
в тексте, часть `defaultStyleSpecs`, который эта схема не переопределяла).
ProseMirror требует, чтобы одно имя в схеме было либо node, либо mark,
никогда оба — конструктор редактора падал с `RangeError: code can not be
both a node and a mark`, что BlockNote оборачивает в куда менее понятное
"Error creating document from blocks passed as `initialContent`" (и это
сообщение появлялось даже для ЧУЖОГО, не связанного с кодом временного
редактора внутри `blocksToPartialBlocks` — оба редактора используют одну
и ту же схему, так что ошибка конструктора схемы бьёт по обоим).
Диагностировано не по описанию ошибки (оно указывало на неправильную
строку), а прогоном `BlockNoteEditor.create({schema})` изолированно в
vitest и чтением `error.cause` — реальная причина была в `cause`, не в
верхнем сообщении. Исправлено переименованием BlockNote-внутреннего типа
в `"codeSnippet"` (`blocks/CodeBlock.tsx`) — формат хранения
(`BlockInput.type: "code"`) не тронут, конвертация в `convert.ts` просто
маппит одно имя на другое на границе.

**Баг 2 — BlockNote не может выполняться при серверном рендере.** Даже
после фикса №1 страница редактирования падала уже по-другому:
`ReferenceError: document is not defined`. Next.js рендерит Client
Component (директива `"use client"` тут не означает "никогда не
выполняется на сервере" — означает "может выполняться на клиенте")
СНАЧАЛА на сервере для первого HTML, и только потом гидрирует на клиенте
— `useCreateBlockNote`/`BlockNoteEditor.create()` полагаются на реальный
браузерный DOM (`document`), которого в Node.js-процессе Next.js просто
нет. Это задокументированное собственное ограничение BlockNote (см. их
гайд "With Next.js" — "make sure Next.js does not try to render
BlockNote as a server-side component"), не что-то специфичное для схемы
этого проекта. Официальная рекомендация — `next/dynamic(..., { ssr:
false })` вокруг всего компонента редактора; здесь применён
функционально эквивалентный "mounted-гейт": `BlockEditor` (тонкая
обёртка) рендерит placeholder до тех пор, пока `useEffect` (который
никогда не выполняется при SSR) не переключит `mounted` в `true`, и
только тогда монтирует `MountedBlockEditor` — весь код, реально
касающийся BlockNote, недостижим до этого момента вообще, а не просто
условно вызывается. Выбран этот вариант, а не `next/dynamic`, чтобы
избежать вопроса, как `next/dynamic` прокидывает `ref` через свой
lazy-loading wrapper — здесь `ref` идёт прямо в настоящий
`useImperativeHandle` внутри `MountedBlockEditor`, без прокси-слоя.

**Почему юнит-тесты этого не поймали.** `convert.test.ts` (ниже) вызывает
`BlockNoteEditor.create()` напрямую в vitest — тестовое окружение jsdom
ПРЕДОСТАВЛЯЕТ `document` (это буквально его смысл), так что баг 2 в
принципе не мог проявиться там. Баг 1 тест бы поймал (и теперь ловит,
`convert.test.ts` использует настоящий конструктор редактора, не только
проверяет форму данных) — но только тогда, когда сам тест существовал;
до этой сессии его не было — конвертация проверялась только на форме
JSON, не на факте, что схема с этими данными реально собирается.

**Понятность для другого разработчика.** Комментарий в `BlockNoteEditor.tsx`
прямо объясняет, почему `BlockEditor` — не один компонент, вызывающий все
хуки условно (это сломало бы правило "одинаковый порядок хуков на каждый
рендер"), а два компонента, один из которых просто не существует до
маунта.

**SOLID.** Не пострадал структурно — `MountedBlockEditor` содержит ровно
тот же код, что раньше был во всём `BlockEditor`; единственное изменение
— условие, ПРИ КОТОРОМ этот код вообще выполняется.

## 2026-07-31 — Фаза 3 (autosave): один новый `onChange` prop, ноль изменений к `ref.getBlocks()`

**Что нужно сделать.** Continuous autosave (`shared/lib/use-autosave-draft.ts`)
нужно запускать и на изменения ТЕЛА поста/кейс-стади, не только на
изменения текстовых полей формы — но без отмены уже принятого решения
"не гонять `blocksToMarkdownLossy` на каждый символ" (см. секцию выше).

**Как сделано.** Добавлен один необязательный проп `onChange?: () =>
void` на `BlockEditorProps`. `MountedBlockEditor` подписывается на
СОБСТВЕННОЕ событие BlockNote — `editor.onChange(callback)` (см.
`BlockNoteEditor.d.ts`, официальный API редактора, не самодельный слушатель
DOM) — внутри `useEffect`, и просто вызывает переданный колбэк. Колбэк не
читает `getBlocks()` сам — он получает `autosave.scheduleSave` (просто
(пере)запускает debounce-таймер), а сам `getBlocks()` вызывается один раз,
позже, тем же самым `ref`, что и раньше, когда debounce-таймер выстрелит.
То есть на каждое нажатие клавиши по-прежнему НЕ выполняется ни
сериализация в Markdown, ни ре-рендер родителя — просто взводится таймер.

**Почему `onChangeRef`, а не `onChange` напрямую в зависимостях эффекта.**
`PostEditorPage`/`WorkEditorPage` передают `onChange={autosave.scheduleSave}`
— новую функцию на каждый рендер (метод объекта, возвращаемого хуком,
пересоздаётся при каждом вызове хука). Если бы `useEffect` зависел от
`onChange` напрямую, `editor.onChange()` пересоздавал бы подписку на
каждое изменение ЛЮБОГО другого поля формы — бессмысленная работа, эффекту
достаточно один раз подписаться на `editor` и всегда звать АКТУАЛЬНЫЙ
колбэк через ref.

**Понятность для другого разработчика.** Комментарий у `onChange` в
`BlockEditorProps` прямо говорит, что колбэк НЕ должен сам читать
`getBlocks()` — без этого следующий разработчик мог бы "оптимизировать"
подписку, случайно вернув именно ту нагрузку на каждый символ, которую всё
это архитектурное решение (`ref.getBlocks()` вместо `value`/`onChange`)
существует, чтобы избежать.

**SOLID.** Open/Closed в чистом виде: `BlockEditorProps` получил новое
необязательное поле, ни один существующий вызов (`admin-post-translate`/
`admin-work-translate`, которые ещё не подключают autosave) не должен
измениться, чтобы продолжить работать.

## Тесты и проверка

Юнит-тестов на сам смонтированный `<BlockEditor>` (клики по тулбару,
слэш-меню как UI) нет — BlockNote внутри использует реальный
ProseMirror/Tiptap `EditorView`, которому для такого теста нужна
настоящая DOM-среда с contentEditable-семантикой, которую jsdom не
реализует достаточно полно (типичное ограничение для rich-text
редакторов; см. `@testing-library`'s собственные предупреждения про
contentEditable). Но `convert.test.ts` ДЕЙСТВИТЕЛЬНО конструирует
настоящий `BlockNoteEditor.create({schema, initialContent})` (не только
проверяет форму JSON, которую возвращают `blocksToPartialBlocks`/
`editorBlocksToBlockInputs`) — именно этот тест поймал бы Баг 1 выше
(`"code"` как node и mark одновременно), если бы существовал раньше;
теперь он часть обычного прогона `vitest run`, а не только ручной
проверки. Баг 2 (SSR) jsdom не может поймать в принципе (jsdom
предоставляет `document`, а сама суть бага — его отсутствие в Node.js
без jsdom) — здесь единственная реальная проверка это ручной прогон
через `next build && next start` и настоящий HTTP-запрос к
`/admin/journal/[slug]/edit`/`/admin/work/[slug]/edit` для контента,
у которого есть код-блок (см. оба журнала выше). Дополнительно проверено
вручную: создание/редактирование каждого из 8 типов блоков, слэш-меню,
тулбар форматирования, сохранение и перезагрузка страницы (round-trip
через backend) — см. корневой план, "Тесты и проверка".

## 2026-08-03 — Списки, "потерянный `\`" после разрыва строки, умная вставка markdown, экспорт code/diagram

**Что нужно сделать.** Четыре смежные жалобы на редактор: (1) нет
bullet/numbered списков; (2) после мягкого разрыва строки (Shift+Enter — не
Ctrl+Enter, см. ниже) на публичной странице иногда виден лишний символ `\`;
(3) вставка markdown из другого приложения (fenced-код, ```mermaid,
цитаты) не превращалась в настоящие блоки; (4) копирование/перетаскивание
целого code/diagram блока экспортировало разметку самой формы
редактирования, а не код.

### 1. Списки — родные `bulletListItem`/`numberedListItem`, не кастомный блок

Регистрировать `defaultBlockSpecs.bulletListItem`/`numberedListItem`
как есть, без обёртки — единственное исключение из правила "не дефолты"
выше (см. `schema.ts`'s обновлённый комментарий), потому что делает это
осознанно бесплатным: типовые шорткаты `"- "`/`"1. "`, `Mod-Shift-7`/
`Mod-Shift-8`, `Tab`/`Shift-Tab` для вложенности (через `children` — общий
для ЛЮБОГО блока механизм, не специфичный для списков, см.
`nestBlock.ts`) и парсинг markdown-списков при вставке — всё это уже
реализовано внутри BlockNote, просмотрено вживую в его исходниках
(`node_modules/@blocknote/core/src/blocks/ListItem/*`), не предположено.

Хранилище (`backend/src/content/blocks.ts`) — ОДИН блок `type: "list"` на
весь (вложенный) список, тем же паттерном, что уже был у `approachList`, а
не одна строка на пункт: `Document.blocks` — плоский массив, вводить в него
понятие "эти N строк — один список" было бы architecturally тяжелее, чем
хранить вложенное дерево `{ text, children }[]` внутри одного блока.
`convert.ts` — граница между этими двумя формами: `blocksToPartialBlocks`
разворачивает ОДИН `"list"`-блок в N соседних верхнеуровневых
`bulletListItem`/`numberedListItem` (по одному на верхний пункт,
рекурсивно строя `children`), `editorBlocksToBlockInputs` — наоборот,
группирует МАКСИМАЛЬНЫЕ последовательные забеги одного и того же типа
пункта обратно в один `"list"`-блок (забег обрывается на любом
не-списочном блоке ИЛИ на смене типа bullet↔numbered — у одного блока
только одно значение `ordered`).

**Задокументированный, а не притворно решённый, пробел.** Пункт списка,
под который через Tab вложен НЕ-списочный блок (нетипичное, ничем в UI не
подсказанное действие) — сохраняет текст, если у вложенного блока есть
rich-text `content` (иначе реального текста для сохранения просто нет), но
теряет структуру: у `"list"` нет способа выразить "пункт списка содержит
картинку", только текст (см. `childToListItem`'s комментарий в
`convert.ts`).

### 2. Потерянный `\` после разрыва строки — найдено чтением исходников BlockNote, подтверждено живым прогоном, не предположено

Первая гипотеза (двойной `.trim()` внутри `convert.ts`) была верной лишь
частично — реальный триггер найден только после того, как через
`editor.tryParseHTMLToBlocks`/`blocksToMarkdownLossy` пропустили РЕАЛЬНЫЙ
HTML, а не придуманный: `<p>Line1<br></p>` (без артефакта) уже корректно
даёт `"Line1\n"` — БЕЗ `\`. А `<p>Line1<br> </p>`/`<p>Line1<br>&nbsp;</p>`
(тот самый пробел/`&nbsp;`, который некоторые браузеры оставляют в опустевшей
строке contenteditable) дают `"Line1\\\n"` — регэксп BlockNote'а
(`trimHardBreaks` в `htmlToMarkdown.ts`, `/(\\\n)+$/`) требует, чтобы
`\`+newline были АБСОЛЮТНО последним, что есть в строке, и не матчит,
если после них идёт ещё пробел. `inlineContentToMarkdown`'s собственный
`.trim()` в конце дальше убирает висящий `\n`, но не сам `\`, — и он
остаётся последним символом сохранённого текста, что на публичной
странице не образует настоящий CommonMark-разрыв (ему ведь ничего не
предшествует "переносить"), а просто рисуется буквально.

**Также найдено, но не то, что ожидали:** реальный шорткат BlockNote для
мягкого разрыва — **Shift+Enter**, не Ctrl+Enter (`KeyboardShortcutsExtension.ts`:
`"Shift-Enter": () => handleEnter(true)`, никакого `Mod-Enter`-байндинга
для разрыва вообще нет). Баг воспроизводится независимо от того, какую
именно комбинацию нажимал пользователь — фикс работает на уровне
экспортируемой строки, а не привязан к конкретной клавише.

**Исправлено** узкой `stripDanglingTrailingHardBreak` в `convert.ts`,
требующей РЕАЛЬНЫЙ newline сразу после `\` (не просто любой висящий `\`) —
намеренно осторожно, чтобы не съесть специально напечатанный экранирующий
`\` в самом конце поля без разрыва строки после него.

### 3. Умная вставка markdown — новый `pasteHandler` + новый `Enter`-шорткат, не переписанный парсер

**Что нужно сделать.** Вставка fenced-кода (` ```lang `), ` ```mermaid `/
` ```plantuml ` и цитат (`> `) должна создавать настоящие
`codeSnippet`/`diagram`/`quote` блоки, а не терять форматирование.

**Что уже работало бесплатно, проверено вживую, не предположено.**
`editor.tryParseMarkdownToBlocks` на реальной схеме этого редактора уже
верно превращает заголовки/`**bold**`/списки/ссылки в настоящие блоки —
BlockNote's собственный `pasteHandler` (`fromClipboard/pasteExtension.ts`)
уже эвристикой `isMarkdown()` включает это для вставки как есть, без
единой новой строчки кода. Не работало (тоже проверено, не предположено):
` > текст ` парсится в обычный paragraph без цитаты; fenced-код парсится в
paragraph с ИНЛАЙН `` `code` ``-стилем, а не в блок — оба типа не
зарегистрированы у нас под именами, которые узнаёт нативный парсер
(`codeBlock`/`blockquote`), у нас `codeSnippet`/`quote`.

**Как сделано.** `paste-handler.ts` — построчный (не regex-на-весь-текст)
разбор вставленного `text/plain` на сегменты `fence`/`quote`/`text`,
каждый `fence`/`quote`-сегмент вставляется напрямую как
`codeSnippet`/`diagram`(`mermaid`/`plantuml`)/`quote`-блок через
`editor.insertBlocks`, а каждый `text`-сегмент идёт через
`editor.pasteMarkdown` — тот же самый вызов, что и стандартный путь
вставки. Активируется только если во вставленном тексте реально есть
fence/цитата — иначе `defaultPasteHandler()` без изменений.

Для "напечатал ` ```kotlin `, нажал Enter" — отдельная механика,
`fence-shortcut.ts`, не входное правило (`inputRules`). Проверено вживую
(не предположено): input rules в ProseMirror триггерятся только через
`handleTextInput` (вставка символа), никогда через Enter — а нативный
`codeBlock`'s собственное правило (`find: /^```(.*?)\s$/`) реагирует на
пробел, не на Enter. Вместо этого — `keyboardShortcuts: { Enter: ... }` в
самостоятельном top-level расширении (`useCreateBlockNote({ extensions:
[...] })`), который проверяет, что ВЕСЬ текст текущего параграфа — просто
` ``` `+язык, и если да — конвертирует блок и "съедает" Enter (возвращает
`true`), не давая сработать стандартному разбиению блока. Подтверждено
настоящим смонтированным редактором и настоящим
`KeyboardEvent("keydown", {key: "Enter"})`, отправленным в `view.dom` — не
вызовом функции-обработчика напрямую, что доказало бы только её логику,
но не то, что она реально достижима раньше дефолтного поведения Enter.

### 4. `toExternalHTML` для `codeSnippet`/`diagram` — раньше не было вообще

**Что было не так.** `createReactBlockSpec` без явного `toExternalHTML`
использует ВМЕСТО него `render` (см. `@blocknote/react`'s исходник) — то
есть копирование/перетаскивание ВЫДЕЛЕННОГО (не текста внутри
`<Textarea>`, а самого блока как узла) экспортировало разметку формы
редактирования (лейблы, `<input>`), а не код/диаграмму.

**Исправлено** — оба блока теперь рендерят `<pre><code data-language>` в
`toExternalHTML`, ту самую форму, которую `htmlToMarkdown.ts`'s
`serializeCodeBlock` умеет превращать в настоящий fenced-блок. Diagram
использует ТУ ЖЕ форму (engine как "язык"), не отдельный формат — у
`htmlToMarkdown.ts` нет понятия "диаграмма", только "код с языком", а
`paste-handler.ts` уже понимает ` ```mermaid `/` ```plantuml ` как
диаграмму на вставке — значит копирование diagram-блока и вставка его
обратно (даже в этот же редактор) восстанавливает настоящий diagram-блок,
не codeSnippet с подозрительным именем языка. Проверено вызовом
`editor.blocksToMarkdownLossy` (тот же метод, что и настоящее копирование)
напрямую на каждом типе блока — результат: `` "```kotlin\nfun main() {}\n```" ``
и `` "```mermaid\n...\n```" `` соответственно.

**Не найдено бага** в самом копировании текста ИЗ `<Textarea>`/
`react-simple-code-editor` (выделил текст, Ctrl+C) — оба поля это
настоящий `<textarea>` внутри `contentEditable={false}`-обёртки, что
заставляет собственный перехват копирования BlockNote (`copyExtension.ts`'s
`checkIfSelectionInNonEditableBlock`) пропускать это мимо себя, отдавая
браузеру нативное (сохраняющее `\n`) копирование `<textarea>`. Если баг
всё же воспроизводится вживую — это не то же самое, что найденный и
исправленный здесь гэп (whole-block copy), и требует отдельного
расследования.

### 5. Что осталось только для ручной проверки в браузере

Максимум автоматической проверки для этой сессии сделан через настоящий
смонтированный редактор + настоящие DOM-события (`KeyboardEvent`,
`view.someProp("handleTextInput", ...)`) — та же техника, что уже
подтвердила Баг 1/2 выше в этом файле в 2026-07-19. НЕ покрыто
автоматически (см. `paste-handler.ts`'s комментарий у `pasteMarkdown`):
`editor.pasteMarkdown` требует настоящий `ClipboardEvent`, которого у
jsdom просто нет (`ReferenceError: ClipboardEvent is not defined`) — так
что смешанная вставка (fence + обычный markdown-текст в одной вставке)
проверена только сегментацией текста (`paste-handler.test.ts`), не
реальным вызовом `pasteMarkdown`. Настоящая вставка из внешнего
приложения (не сконструированного `ClipboardEvent`) — тоже только вручную.

## 2026-08-03 (продолжение) — Самопроверка нашла пять реальных пробелов, все закрыты живой проверкой

**Что нужно сделать.** После записи выше пользователь попросил честную
самооценку решения — самопроверка нашла пять реальных, не притворных
пробела; каждый закрыт отдельным фиксом, каждый подтверждён вживую (не
рассуждением).

**1. Гонка Delete vs. фоновый autosave.** Клик "Delete" теперь (после
записи выше про `onBlur`) сначала уводит фокус с последнего поля →
триггерит фоновый `flush()` → почти одновременно вызывает
`deletePost()`/`deleteWork()`. Если `update()` долетал до сервера ПОСЛЕ
удаления строки — тихая 404, проглоченная `.catch`. Исправлено
`await autosave.flush().catch(() => {})` В САМОМ НАЧАЛЕ `handleDelete`,
до вызова `deletePost`/`deleteWork` — не блокирует удаление при провале
флаша (сохранять уже нечего), просто гарантирует порядок.

**2. Визуальный разрыв между bullet→numbered split.** `convert.ts`'s
группировка верно разбивает список на два `"list"`-блока при смене типа
пункта посреди списка — но `ContentBlocks.tsx`'s общий `gap-md` рисовал
между ними зазор размером с абзац. Исправлено: `groupConsecutiveLists`
группирует ЛЮБОЙ забег соседних `"list"`-блоков в одну обёртку
`flex flex-col` без зазора; переключение типа пункта посреди списка теперь
не выглядит как два несвязанных списка. Понадобился рефакторинг: весь
`switch` вынесен в отдельную `renderBlock(block, ln, key)` — `key` явным
параметром, не `block.id` изнутри, потому что этот же `renderBlock` теперь
используется и для `BlockInput`-блоков без своего `id` (пункт 5 ниже).

**3. Вставка посреди текста теряла порядок.** `paste-handler.ts`'s
`insertSegments` всегда вставляла новые блоки ПОСЛЕ всего "якорного" блока
— верно, если курсор в конце (частый случай "вставка на пустую строку"), но
неверно, если курсор посреди текста: текст ПОСЛЕ курсора оставался
привязан к исходному блоку и оказывался ПЕРЕД вставленным контентом, а не
после. Первая гипотеза фикса — сырой `tr.split()` — проверена вживую и
провалилась: `TransformError: Invalid content for node blockContainer`
(обычный ProseMirror-сплит не знает о вложенной схеме блоков BlockNote).
Исправлено без него: смещение курсора внутри блока вычисляется через
`editor.transact` + `getBlockInfoFromTransaction` (публичный API), `content`
блока вручную режется на "до"/"после" с сохранением стилей ПОРЕЗАННОГО
рана (плоское flatten-и-нарезка строки потеряло бы границы `**bold**`),
"до" остаётся в исходном блоке через `updateBlock`, "после" вставляется
новым блоком через `insertBlocks` — тем же публичным примитивом, что уже
использовался. Заодно исправлено: реальное (не свёрнутое) выделение текста
в момент вставки теперь удаляется первым (`tr.deleteSelection()`), как и
должно быть при обычной вставке "вместо" выделенного.

**4. `fence-shortcut.ts` не работал внутри пункта списка.** Расширено на
`bulletListItem`/`numberedListItem` (та же форма контента, что и
paragraph) — но простое добавление типов не сработало: список-пункт
"перехватывал" Enter первым. Найдено вживую, не по документации:
`sortByDependencies` (`util/topo-sort.ts`) даёт ОДИНАКОВЫЙ приоритет по
умолчанию любому расширению без явного `runsBefore`, и на практике при
равенстве выигрывает расширение самого типа блока
(`bullet-list-item-shortcuts`), а не топ-уровневое. Исправлено явным
`runsBefore: ["bullet-list-item-shortcuts", "numbered-list-item-shortcuts"]`
— убирает неоднозначность вместо того, чтобы полагаться на порядок,
который может незаметно сломаться при обновлении BlockNote. Заодно:
защита от срабатывания, если у пункта уже есть `children` (иначе они
"зависли" бы под блоком, для этого не предназначенным), и регэксп теперь
терпим к случайному пробелу перед Enter.

**5. Пункт списка терял НЕ-списочный вложенный контент.** Задокументированный
(но не решённый) пробел из первой записи: картинка/код/диаграмма,
вложенная через Tab под пункт списка, полностью теряла структуру при
сохранении. Исправлено расширением `ListItemInput`
(`backend/src/content/blocks.ts`) вторым полем `blocks: BlockInput[]`,
ОТДЕЛЬНЫМ от `children` (`children` — только настоящие вложенные пункты
списка; `blocks` — всё остальное, рекурсивно переиспользующее ВЕСЬ
`blockInputSchema`, той же техникой взаимного `z.lazy()`, что уже была у
`children`). `convert.ts`: `childToAttachedBlock` конвертирует такой
дочерний блок через уже существующий `convertSingleBlock` — ту же
функцию, что и для блоков верхнего уровня, не дублируя логику; обратное
направление интерливит `item.blocks` обратно в тот же `children`-массив
BlockNote, которым сам BlockNote и оперирует (BlockNote не различает
"дочерний пункт списка" и "просто вложенный блок" — оба живут в одном
массиве `children`, разделение на два поля — сугубо для простоты формы
хранения). `ContentBlocks.tsx`: `<li>` рендерит `item.blocks` через тот же
`renderBlock`, что и верхний уровень — переиспользуя фикс пункта 2.

**Понятность для другого разработчика.** Каждый из пяти фиксов
задокументирован comment'ом прямо у места фикса со ссылкой на РЕАЛЬНУЮ
проверку (конкретная ошибка, конкретный лог), а не на рассуждение — та же
дисциплина, что и в первой записи этой сессии.

**Нагрузка.** Не применимо — ни один фикс не меняет частоту/объём
запросов к серверу.

**Расширяемость/заменяемость.** `blockToPartialBlocks`/`convertSingleBlock`
теперь буквально единственное место, которое знает "как один блок
превращается в редакторный/сохранённый вид" — и для верхнего уровня, и для
вложенного под пункт списка контента; третье место, где понадобится та же
конвертация, тоже сможет её переиспользовать, а не копировать `switch`.

**Миграция/отказоустойчивость.** Не применимо — новое опциональное
(`.default([])`) поле, не меняет форму уже сохранённых данных.

## 2026-08-03 (продолжение) — Автоматический review PR нашёл два реальных бага в дизайне `blocks`/`children` из предыдущей записи

**Что произошло.** Отдельный `children: ListItemInput[]` рядом с `blocks:
BlockInput[]` (см. предыдущую запись) прошёл ревью и юнит-тесты, но
чатgpt-codex-connector нашёл на PR два реальных, воспроизводимых бага в
самом дизайне разделения на два поля — не в реализации отдельной функции.

**Баг 1 — вложенный под-список терял СВОЙ `ordered`.** `ListItemInput`
хранил под-пункты как `{text}` без собственного флага "нумерованный или
маркированный" — `listItemToPartialBlock` наследовал `itemType` от
РОДИТЕЛЬСКОГО списка для абсолютно всех потомков. Пример: маркированный
список, где у одного пункта под-список — нумерованный (` -
Пункт\n  1. Под-пункт `) — при сохранении под-список тихо становился
маркированным тоже.

**Баг 2 — порядок между под-списком и прикреплённым блоком терялся.**
Разбивка ОДНОГО упорядоченного массива `children` BlockNote на ДВА
раздельно типизированных поля (`children` сначала, `blocks` — после)
физически не могла сохранить, что было раньше что при восстановлении —
`listItemToPartialBlock` всегда клала все под-пункты ПЕРЕД всеми
прикреплёнными блоками, независимо от их настоящего порядка в BlockNote.

**Как исправлено — не патч, а пересмотр модели.** `ListItemInput` потерял
`children` целиком: `{ text: string; blocks: BlockInput[] }`. Продолжение
под-списка — это теперь просто ОБЫЧНАЯ вложенная `"list"`-запись внутри
`blocks`, того же самого рекурсивного `blockInputSchema`, что и любой
другой вложенный блок — не отдельное понятие. Это закрывает оба бага
СТРУКТУРНО: у своего `"list"`-элемента уже есть собственный `data.ordered`
(баг 1 решён самой формой данных, не дополнительной логикой), и `blocks`
— единственный, единственно-упорядоченный массив, который обходится в его
реальном порядке (баг 2 решён тем, что второго массива, с которым можно
было бы разойтись по порядку, просто не существует больше).

`convert.ts`: `childToListItem`/`childToAttachedBlock`/
`partialBlockToListItem`'s раздельная логика заменена ОДНОЙ функцией
`blockArrayToBlockInputs` — тем же самым алгоритмом группировки соседних
`bulletListItem`/`numberedListItem`-забегов, что уже был у
`editorBlocksToBlockInputs`, просто применённым РЕКУРСИВНО и к
верхнеуровневому документу, и к `children` любого пункта списка — не два
похожих алгоритма, один.

**Понятность для другого разработчика.** Комментарий у `ListItemInput`
прямо называет оба бага по имени и объясняет, почему их фиксит именно
УДАЛЕНИЕ поля, а не добавление третьего — та же дисциплина "первая
гипотеза была неверна, показать исправление", что и в остальных записях
этого README/репозитория.

**Расширяемость/заменяемость.** Модель стала ПРОЩЕ, не сложнее — один
рекурсивный массив на пункт списка, а не два с ручной синхронизацией
порядка между ними; третье измерение вложенности (если понадобится)
ничего не потребует менять в этой части.

**SOLID.** Тот же принцип, что уже применён к `renderBlock`/
`convertSingleBlock`: `blockArrayToBlockInputs` — единственное место,
которое знает, как превратить плоский список сиблингов BlockNote в
`BlockInput[]`, используется и для документа, и рекурсивно для пункта
списка — не два похожих места, которые могли бы разойтись.

## SOLID

Single Responsibility: `schema.ts` знает только "какие блоки существуют и
как они выглядят", `convert.ts` — только "как переводить между
хранилищем и редактором", `slash-menu.ts` — только "что показывать по
`/`", `BlockNoteEditor.tsx` — только "смонтировать редактор и отдать
`getBlocks()`", `paste-handler.ts` знает только "как разобрать вставленный
текст на сегменты и куда их вставить", `fence-shortcut.ts` — только
"конвертировать блок по Enter после ` ``` `", а `renderBlock`
(`ContentBlocks.tsx`) — единственное место, которое знает "как один
`Block`/`BlockInput` превращается в JSX", независимо от того, верхнеуровневый
он или вложен под пункт списка. Open/Closed: новый тип блока — это новый
файл в `blocks/` плюс одна строка в `schema.ts`'s `blockSpecs` и один пункт
в `slash-menu.ts` — ни `convert.ts`, ни `BlockNoteEditor.tsx` не меняются
структурно (только добавляется `case` в двух `switch`) — кроме `"list"`,
чья особая group/expand-логика в `convert.ts` — намеренное исключение,
задокументированное там же, а не нарушение этого правила по недосмотру.
