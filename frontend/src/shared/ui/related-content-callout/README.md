# shared/ui/related-content-callout — RelatedContentCallout, CompactRelatedLink

## Будет ли переиспользоваться?

Да: `RelatedContentCallout` уже сразу заменяет ДВА независимо выросших,
но байт-в-байт идентичных по разметке блока — "связанный проект" на
`JournalDetailPage` и "связанный пост" на `WorkDetailPage`. Оба использовали
один и тот же набор классов (`bg-surface-base border ... flex justify-between
...`) и одну и ту же композицию `Eyebrow` + `Text(h3)` + `Text(caption)` +
`LinkButton`, отличаясь только контентом. `CompactRelatedLink` — второй
экспорт этого же модуля, для компактных мест (списки/ledger), где полноразмерный
callout был бы слишком тяжёлым.

## 2026-08-11 — Первая версия, часть унификации Work/Post UI

**Что нужно было сделать.** У `Post.relatedWorkSlug`/`Work.relatedPostSlug`
уже была связь в схеме, но каждая сторона рисовала её отдельно
написанным JSX-блоком — пользователь явно попросил унифицировать все
такие появления по сайту.

**Как сделано.** `RelatedContentCallout` принимает уже готовые
(`pick()`'нутые) строки (`eyebrow`/`title`/`body`/`buttonLabel`) и `href` —
он ничего не знает про то, `Post` это или `Work` на другом конце связи,
и никогда не должен: это дело вызывающей стороны, у которой уже есть
типизированный `PostSummary`/`WorkDetail`. `CompactRelatedLink` —
отдельный, независимый компонент (тот же файл-модуль, разный экспорт) —
настоящая `<Link>` с ВИДИМОЙ подписью, а не голая стрелка.

**Понятность для другого разработчика.** Сознательно НЕ единый компонент
с `kind: "post" | "work"` веткой внутри — такая ветка добавила бы условную
логику ради данных, которые вызывающая сторона уже знает и уже
разрешила в конкретные строки; проще и честнее пяти параметров, которые
компонент просто раскладывает по вёрстке.

**Нагрузка.** Ноль — чистая презентация, ни `RelatedContentCallout`, ни
`CompactRelatedLink` не держат состояния.

**Расширяемость/заменяемость.** Новый тип связанного контента (например,
"связанный доклад") в будущем — тот же компонент, просто другие строки
и `href`, без единой правки здесь.

**Миграция/отказоустойчивость.** Не применимо — чистые презентационные
компоненты.

**SOLID.** Single Responsibility по обоим компонентам: раскладка
контента отдельно от того, ЧТО этот контент означает (это остаётся
на стороне `JournalDetailPage`/`WorkDetailPage`, которые продолжают
решать, показывать блок вообще или нет, и что в него положить).
