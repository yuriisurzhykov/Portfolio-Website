# shared/ui/token-combobox — TokenCombobox

## Что нужно было сделать

Пользователь хочет заполнять поле Stack у проекта не строго по названиям
из лендингового `techStack`, а гибко — "чтобы он контекст грубо говоря
улавливал", с автодополнением по списку уже объявленных технологий, но без
жёсткой блокировки произвольного текста. Раньше это было обычное
текстовое поле с подсказкой "Comma-separated, e.g. Kotlin, Jetpack
Compose." — ничего не подсказывало и ничего не проверяло.

## Почему это НЕ жёсткий select/multi-select

`values` осознанно не ограничен подмножеством `suggestions` — админ должен
уметь ввести технологию, которой ещё нет в `techStack` вообще (обычный
случай: новый проект использует что-то, чего нет на лендинге). Вместо
блокировки — мягкая подсказка: у уже введённого токена, который похож, но
не совпадает точно с известной технологией, появляется маленький
"Possibly ...?" (`title`) и другой акцент цвета чипа
(`status-warning`-тон). Ничего не мешает сохранить форму как есть.

## Почему два РАЗНЫХ алгоритма нечёткого поиска в одном файле (`fuzzy-match.ts`)

Первая идея была — один алгоритм на всё. Оказалось, что это две разные
задачи с разными допустимыми уровнями "шума":

1. **Дропдаун во время набора текста** (`fuzzySearch`/`fuzzyMatchScore`) —
   субпоследовательное сопоставление (как VS Code's Quick Open): каждый
   символ запроса должен встретиться в целевой строке по порядку, не
   обязательно подряд. Именно это позволяет `"jc"` находить `"Jetpack
   Compose"` — j и c оба попадают на начало слова, что даёт бонус к
   очкам. Здесь высокий "шум" (много ложных совпадений при активном
   наборе текста) — это нормально, пользователь сам видит и выбирает
   нужный вариант из списка.
2. **Подсказка "did you mean" у уже введённого токена**
   (`findClosestSuggestion`) — тот же субпоследовательный алгоритм СЛИШКОМ
   щедрый для этой задачи: он охотно "нашёл бы совпадение" у двух
   совершенно разных слов, если буквы просто встретились в правильном
   порядке где-то в строке. Здесь используется простое, консервативное
   вхождение подстроки в любую сторону (case-insensitive) — именно
   реальный случай пользователя: `"Python"` — подстрока
   `"Python & Jinja2"`. Ложные совпадения тут дороже (висящая ложная
   подсказка на каждом чипе), поэтому алгоритм заведомо более строгий.

## Почему без внешней библиотеки combobox

ARIA 1.2 "combobox with list popup" реализован вручную:
`role="combobox"` + `aria-expanded`/`aria-controls`/`aria-activedescendant`
на `<input>`, `role="listbox"`/`role="option"` на списке. Полностью
управляется с клавиатуры (стрелки, Enter, Escape, Backspace на пустом
поле удаляет последний чип). Для одного поля в одной форме — не тот
случай, чтобы тянуть зависимость; тот же принцип, что уже применён к
`Drawer`/`BlockEditor`'s редактору списков (см. их README) — простой,
полностью доступный с клавиатуры паттерн без сторонней библиотеки, когда
объём и частота использования этого не требуют.

## Почему `onBlur` не коммитит недописанный текст

Первая версия коммитила `inputValue` на `blur` (стандартный паттерн для
некоторых tag-input'ов). Отклонено: админ, кликнувший в другое поле формы
без явного Enter/запятой/выбора из списка, не должен молча получить
недописанный текст как новую запись в стеке технологий. `onBlur` только
закрывает дропдаун; текст остаётся в поле до явного коммита или до
следующего фокуса.

## Тесты

`fuzzy-match.test.ts` — обе функции поиска отдельно, включая негативные
случаи (не подстрока → `null`, не субпоследовательность → `null`) и
сравнение очков (contiguous match важнее scattered, ранняя позиция важнее
поздней) — ассерты написаны так, чтобы флип любого бонуса/штрафа в
реализации завалил тест, не просто "функция не бросает исключение".
`TokenCombobox.test.tsx` — весь пользовательский путь: рендер чипов,
добавление через Enter, дедупликация (case-insensitive), удаление через
кнопку и через Backspace на пустом поле, выбор из дропдауна мышью и с
клавиатуры, наличие/отсутствие "did you mean"-подсказки.
