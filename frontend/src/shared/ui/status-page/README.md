# shared/ui/status-page — StatusPage

## Будет ли переиспользоваться?

Да, с самого начала спроектирован для нескольких мест одновременно, а не для
одного: `app/error/[code]/page.tsx` (standalone-визит), `(site)/error.tsx`
(встроенный React error boundary для 500), `ServiceUnavailable` (встроенный
fallback для 503 при недоступной БД) и `not-found.tsx`/`(site)/not-found.tsx`
(404, добавлено 2026-07-28 позже в тот же день). Дизайн/копирайт живут в
одном месте (`StatusPage.tsx` + `status-content.ts`), а не копируются
построчно в несколько файлов — при следующей правке шутки/иконки/цвета для
конкретного кода это одна правка, а не несколько синхронных.

## 2026-07-28 — "Прикольные" страницы для 400/401/403/429/500/501/503

**Что нужно было сделать.** До этого в приложении было два разных, скучных
UI для ошибок (`ServiceUnavailable` и `(site)/error.tsx`), 429 отдавался
только сырым JSON даже для настоящей навигации в браузере, а 400/401/403/501
не имели вообще никакого отображения — только JSON-ответы API или (для 401)
уже существующий редирект на логин.

**Как сделано.**
- Один `STATUS_CONTENT` (`status-content.ts`) — единственный источник
  правды про иконку/тон/primary-action для каждого из 7 кодов. `StatusPage`
  ничего не знает о конкретном коде напрямую — просто читает эту таблицу и
  рендерит `Card` + `IconBadge` + `Eyebrow` (`HTTP {code} · {формальное
  имя}`) + шутливый заголовок + описание + одну primary-кнопку
  (retry/signIn/home) + вторичную "на главную", если primary — не она же.
- `proxy.ts`: реальная браузерная навигация (не `/api/*`, не
  `next-router-prefetch`, `Accept` содержит `text/html`), упёршаяся в лимит,
  теперь редиректится на `/error/429?retryAfter=N` вместо голого JSON;
  JSON-контракт для API/префетчей не тронут (см. `proxy.test.ts` — старые
  тесты не выставляют `Accept` и остаются на JSON-ветке без изменений).
- `(site)/error.tsx` и `ServiceUnavailable` теперь рендерят тот же
  `StatusPage` (`code={500}`/`code={503}`) вместо собственной разметки —
  `onRetry` пробрасывается как `reset()`/`router.refresh()` соответственно.
- Добавлен `global-error.tsx` (не существовал вообще) — падение самого
  корневого layout раньше падало в голый нестилизованный экран Next.js по
  умолчанию.
- 401/400/403/501 существуют ТОЛЬКО как `/error/<code>` — сознательно не
  переключали существующие потоки (`requirePage()`'s редирект на
  `/admin/login`, `admin-api.ts`'s silent-refresh) на промежуточную
  "прикольную" страницу: тот путь уже хорошо спроектирован (см.
  `frontend/README.md`'s запись от 2026-07-27), добавлять лишний переход
  ради шутки — не обмен, который стоило делать. 403 и 501 сегодня вообще не
  имеют ни одной точки вызова (single-role модель никогда не производит
  403, 501 никогда не возвращается) — страницы существуют для полноты
  набора и на будущее.

**Первая гипотеза, которую отвергли.** Изначально предполагалось отдавать
429/503 через `NextResponse.rewrite()` с `status: 429` в `init`, чтобы адрес
в браузере не менялся и HTTP-статус был честным. Проверено (не
предположено) по обсуждениям в самом Next.js (vercel/next.js#37095,
#50155): `rewrite()` в App Router либо игнорирует `status` из `init` вообще,
либо ведёт себя непоследовательно между версиями — на это нельзя полагаться.
Вместо этого используется настоящий `redirect()`: сам редирект — честный
429/307, а страница-назначение уже отдаётся с 200. Тот же компромисс, на
который идут большинство "прикольных" страниц лимита запросов.

**Понятность для другого разработчика.** Комментарий в `enforceRateLimit`
(`proxy.ts`) объясняет и exemption для `/error/*` (иначе редирект на
`/error/429` для уже исчерпавшего лимит IP сам был бы заблокирован →
бесконечный редирект), и почему это `redirect`, а не `rewrite`.

**Нагрузка.** Компонент — чистый React без сетевых запросов; `/error/[code]`
исключён из rate-limit бюджета (см. `stripLocalePrefix`-проверку в
`enforceRateLimit`), так что не может случайно "съесть" чужой бюджет или
сам попасть в петлю редиректов.

**Расширяемость/заменяемость.** Добавить восьмой код — это одна запись в
`STATUS_CONTENT` + три i18n-ключа (`error.status.<code>.{caption,title,
description}`), без правок самого `StatusPage.tsx`. `parseStatusCode`
(рантайм-валидация значения из URL) держит `/error/[code]` защищённым от
произвольного кода — незнакомое значение уходит в `notFound()`.

**Миграция/отказоустойчивость.** Не применимо к данным — чистый UI-слой.
`global-error.tsx` — единственное место, которое обязано само
переимпортировать глобальные стили (см. его комментарий): оно
полностью заменяет корневой layout, а не рендерится внутри него.
(2026-08-14: `themeVars`/`legacyLayoutVars`'s runtime-инжектируемый
`<style>`-тег полностью убран — все токены, включая layout/z-index, теперь
приходят из статического `generated/tokens.css`.)

**SOLID.** Single Responsibility: `status-content.ts` знает "что показывать
для какого кода", `StatusPage.tsx` знает только "как это разметить", ни один
из call site (`/error/[code]`, `(site)/error.tsx`, `ServiceUnavailable`) не
знает ни того, ни другого — только передаёт
`code`/`onRetry`/`retryAfterSeconds`/`from`. Open/Closed: новый код
добавляется расширением таблицы, а не веткой `if` внутри `StatusPage`.

### 2026-07-28 (позже в тот же день) — 404 тоже получил "прикольную" страницу

**Что нужно было сделать.** Изначально 404 сознательно оставили за
пределами набора — при планировании выбрали "как вы сказали" (400/403 —
да, 404 — нет). Живой вопрос "а почему для 404 ничего красивого нет?"
показал, что это ожидание было неверно откалибровано: раз компонент уже
существует, отсутствие 404 выглядит как пробел, а не как осознанный выбор.

**Как сделано.** `404` добавлен в `STATUS_CONTENT` (`Compass`, `warning`,
`home` — та же пара, что у 400/403/501, но с собственным текстом). В
отличие от них, 404 подключён к РЕАЛЬНОМУ потоку сразу, а не только к
`/error/404`: `(site)/not-found.tsx` (рендерится внутри `(site)/layout.tsx`,
сохраняя Nav/Footer — как и `(site)/error.tsx`) и корневой
`app/not-found.tsx` (standalone, как `/error/[code]`) — стандартная
Next.js-конвенция для `notFound()`, вызываемого во множестве мест
(`journal/[slug]`, `work/[slug]`, админские edit/translate-страницы). До
этой правки `notFound()` показывал голый дефолтный экран Next.js — тот же
класс проблемы, что решил `global-error.tsx` для 500.

**Понятность для другого разработчика.** Пара `not-found.tsx` файлов
зеркалит уже существующую пару `error.tsx`/`global-error.tsx` — то же
рассуждение "внутри (site) — с шапкой/футером, вне — standalone", не новый
паттерн, а применение уже принятого.

**Расширяемость/заменяемость.** Ничего не потребовалось менять в
`StatusPage.tsx`/`status-content.ts`'s форме — `404` такая же запись в
таблице, как остальные 7.

### 2026-07-29 — Реальный клик по `<Link>` не редиректился на `/error/429`

**Что нужно было сделать.** Ревью (chatgpt-codex-connector) верно указал:
условие `Accept: text/html` в `enforceRateLimit` ловит полную загрузку
документа, но не клиентскую навигацию App Router — та запрашивает RSC-пейлоад
с `Accept: */*`, значит проваливалась в JSON-ветку вместо `/error/429`.

**Первая гипотеза, которую отвергли (проверено вживую, не предположено).**
Первый инстинкт — добавить проверку заголовка `rsc: 1` (стандартный
Next.js-заголовок RSC-навигации) в дополнение к `Accept: text/html`. Живая
проверка (Playwright, реальный клик по `<Link>`, плюс отдельно — curl с
явным заголовком, и на `next dev`, и на `next build && next start`) показала:
`request.headers.get("rsc")` внутри `proxy.ts` всегда возвращает `null`,
даже когда браузер этот заголовок реально отправил (подтверждено сетевым
трейсом самого запроса). Причина — задокументированное поведение самого
Next.js: страница `proxy` в официальной документации прямо говорит, что
`rsc`, `next-router-state-tree` и `next-router-prefetch` вырезаются из
`request.headers` до того, как Proxy их увидит — "to prevent accidentally
handling an RSC request differently than the HTML request". Тем же самым
живым дампом заголовков выяснилось, что уже СУЩЕСТВОВАВШАЯ (из записи от
2026-07-27/28 в `backend/src/auth/README.md`) проверка `isPrefetch` через
`next-router-prefetch` страдает от ТОЙ ЖЕ проблемы — она никогда не видит
этот заголовок на реальном сервере, значит фактически всегда `false`, и
фоновые префетчи с самого начала делят бюджет `global` с реальными
навигациями, а не используют отдельный `prefetch`-тир, как предполагала та
запись. Собственные unit-тесты того тира проходят только потому, что
конструируют `NextRequest` напрямую в обход настоящего конвейера запроса
Next.js — они проверяют логику функции, а не то, что заголовок реально
доходит.

**Как сделано.** Раз ни `Accept: text/html`, ни `rsc` не различают реальную
RSC-навигацию от фонового префетча или прямого `curl` без специальных
заголовков — весь набор одинаково неотличим для `proxy.ts` — решение:
перестать пытаться их различать вообще (это буквально то, что советует сама
документация Next.js: не обрабатывать RSC-запрос иначе, чем HTML). Условие
редиректа упростилось до `!isPrefetch && !pathname.startsWith("/api")` —
любой заблокированный запрос к НЕ-API пути редиректится на `/error/429`,
независимо от `Accept`. Это не костыль, а более честная модель: раз путь не
начинается с `/api`, его настоящий ответ и так был бы `text/html` — значит
HTML-страница ошибки корректнее JSON для ЛЮБОГО такого запроса, будь то
клик, префетч или прямой `curl`. `isPrefetch`-проверка оставлена (не
удалена) как безвредный no-op на случай, если заголовок когда-нибудь станет
видимым (будущая версия Next.js, другая конфигурация reverse-proxy) —
почему не удалена и что это значит для нагрузки, см. подробный комментарий
прямо в `enforceRateLimit`.

**Понятность для другого разработчика.** Оба комментария (`isPrefetch` и
`wantsRedirect` в `proxy.ts`) прямо цитируют официальную документацию
Next.js и описывают, как именно это было проверено вживую — чтобы следующий
человек не наступил на те же 40 минут отладки "почему заголовок null, если
браузер его отправляет".

**Нагрузка/масштабирование.** Не изменилась сама модель лимитов — только
то, какой ответ отдаётся при блокировке. Отдельно зафиксировано как
известный, сознательно не решённый в этой правке пробел: реального
разделения бюджета `global`/`prefetch` сегодня не существует — если это
станет проблемой на практике, решение потребует либо поднять `GLOBAL_LIMIT`
с учётом реального объёма префетчей, либо иной сигнал вместо заголовков.

**SOLID.** Не применимо сверх уже описанного в записи от 2026-07-28 —
изменилось только конкретное булево условие, не форма/ответственности
функции.

### 2026-07-29 (позже в тот же день) — "Try again" на `/error/429` не помогал

**Что нужно было сделать.** Ещё одно ревью (chatgpt-codex-connector) верно
указало: standalone `/error/429` не получает `onRetry`, значит его "Try
again" вызывал `router.refresh()` — но `/error/429` сам исключён из
rate-limit (см. запись выше про защиту от петли редиректов), поэтому
рефреш этой страницы никогда не может "разблокироваться" сам по себе.
Посетитель залипал на странице ошибки навсегда, даже сильно позже
истечения настоящего окна лимита.

**Как сделано.** `proxy.ts` теперь кладёт исходный заблокированный путь
(включая query-строку, например `/journal?page=2`) в `from` рядом с
`retryAfter`. `StatusPage` для retry-действия (429/500/503) при отсутствии
`onRetry` теперь делает `router.push(from)` вместо рефреша — то есть
реально повторяет ИСХОДНУЮ навигацию, а не саму страницу ошибки. Если
лимит уже снят, `/journal` откроется нормально; если ещё нет, `proxy.ts`
снова отредиректит на `/error/429` со свежим `retryAfter` — цикл работает
сам по себе, без ручного вмешательства.

**Security-аспект, не пропущенный по ходу.** `from` приходит из query
string — значит доступен любому, кто способен прислать/расшарить ссылку
вида `/error/429?from=https://evil.example` или `//evil.example`
(протокол-относительный URL, браузер трактует его как ВНЕШНИЙ несмотря на
ведущий `/`). Добавлен `shared/lib/safe-relative-path.ts`
(`isSafeRelativePath`) — принимает только одиночный ведущий `/`, не `//` и
не `/\`, — и `StatusPage` валидирует `from` ИМ, а не просто проверкой
`Boolean(from)`, прежде чем когда-либо передать его в `router.push()`. Не
переиспользовано в существующей `/admin/login`'s `?from=`-обработке
(`useRedirectTarget()` в `AdminLoginPage.tsx`) — та уже безопасна на своих
собственных условиях (`from.startsWith("/admin")`, более узкая и
достаточная проверка для её конкретного случая), трогать её не было
необходимости.

**Понятность для другого разработчика.** Комментарий на самом `from` в
`StatusPageProps` прямо объясняет оба использования (retry-навигация И
`?from=` для входа) одним предложением, вместо того чтобы читателю
самому сопоставлять два разных use case у одного пропа.

**Расширяемость/заменяемость.** `isSafeRelativePath` — самостоятельная,
не завязанная на `/admin` проверка; годится для любого будущего места,
читающего "куда вернуться" из URL.

**Тесты.** `safe-relative-path.test.ts` — сам guard (абсолютный URL,
протокол-относительный, `/\`-вариант, путь без слэша, `undefined`/`null`).
`StatusPage.test.tsx` — retry с безопасным `from` вызывает `router.push`,
а не рефреш; retry с НЕБЕЗОПАСНЫМ `from` — наоборот, падает обратно на
рефреш, а НЕ на `push`; `onRetry`, если передан, по-прежнему имеет
приоритет над `from`. `proxy.test.ts` — `from` в редиректе точно равен
исходному пути+query, и сохраняет `/ru`-префикс для русской навигации.

### 2026-07-29 (третье ревью за день) — "На главную" на русской 404 уводил на английскую версию

**Что нужно было сделать.** Третье ревью (chatgpt-codex-connector) верно
указало: на `/ru/journal/unknown` эта страница рендерится по-русски (см.
`x-locale`-заголовок из `handleLocale` в `proxy.ts`), но и primary
"на главную", и вторичная ссылка "на главную" были захардкожены на `"/"` —
после клика посетитель молча оказывался на английской версии сайта.

**Как сделано.** `StatusPage` теперь читает `language` из
`useTranslation()` (уже используется для `ln()`, просто раньше не читали
второе поле) и строит `homeHref = language === "ru" ? RU_PREFIX : "/"` —
ровно та же логика, что уже применяет `LanguageSegmentedToggle`
(`widgets/nav/LanguageSegmentedToggle.tsx`) для EN/RU переключателя в
шапке, просто локально, без обращения к текущему `pathname` (здесь всегда
известно, что цель — именно домашняя страница, а не "тот же путь на другом
языке"). И primary-кнопка (для `action === "home"`), и вторичная ссылка
получили эту переменную вместо литерала `"/"`.

**Понятность для другого разработчика.** Комментарий у `homeHref`
прямо указывает на `LanguageSegmentedToggle` как на прецедент того же
самого рассуждения — чтобы это не выглядело как две независимые, случайно
похожие правки в разных файлах.

**Тесты.** `StatusPage.test.tsx` — новый `renderStatus`'s второй параметр
(`language`) рендерит с `initialLanguage="ru"`; проверено, что и primary-,
и secondary-ссылка "на главную" получают `href="/ru"` по-русски и `"/"`
по умолчанию (английский).

### 2026-07-29 (четвёртое за день) — редирект на `/error/429` завешивал `npm run test:e2e`

Побочный эффект того, что 429 теперь честно редиректит (вместо игнорируемого
JSON): Playwright-суита (`frontend/tests/`) генерирует достаточно трафика с
ОДНОГО IP, чтобы исчерпать `global`-бюджет, и дальше КАЖДЫЙ фоновый префетч
на страницах с большим количеством ссылок получал настоящий редирект —
Next.js роутер не мог поймать "networkidle", тест висел 60 секунд. Полный
разбор и исправление (`DISABLE_RATE_LIMIT`) — в
`frontend/tests/README.md`'s разделе 11/12 за эту же дату; здесь фиксируется
только связь с этим компонентом, не дублируется сам разбор.

## Тесты

- `status-content.test.ts` — `parseStatusCode` отклоняет посторонние
  значения (502, мусор, `429.5`), а не молча совпадает с чем-то похожим;
  `STATUS_CONTENT` реально использует оба измерения (`tone`/`action`), а не
  одно константное значение, скопированное на все записи.
- `StatusPage.test.tsx` — заголовки для разных кодов реально разные (не
  единая заглушка, включая 404 против 400 — у них одинаковый `action`, но
  разный текст), `retryAfterSeconds` действительно меняет текст описания,
  primary-action рендерит правильный тип контрола (`<button>` для retry,
  `<a>` для signIn/home) с правильным `href`, клик по retry вызывает именно
  `onRetry`, если он передан, и `router.refresh()` — если нет.
- `proxy.test.ts` (новый describe-блок) — HTML-навигация редиректится на
  `/error/429` с настоящим `retryAfter`, `/ru`-префикс сохраняется в цели
  редиректа, `/api/*` и *объявленные* префетчи остаются на JSON-ветке даже
  с `Accept: text/html`, `/error/429` сам по себе исключён из лимита
  (защита от петли), и — регрессионный тест от 2026-07-29 — запрос вообще
  без `Accept`-заголовка (как настоящая RSC-навигация или голый `curl`)
  ТОЖЕ редиректится, а не проваливается в JSON.
