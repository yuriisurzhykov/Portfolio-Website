# shared/ui/related-item-picker — RelatedItemPicker

## Будет ли переиспользоваться?

Да: заменяет ДВА разных голых `<Input>` — `PostEditorPage.tsx`'s
`relatedWorkSlug` и `WorkEditorPage.tsx`'s `relatedPostSlug`. Оба сегодня
принимают произвольную строку без какой-либо проверки, что такой slug
реально существует.

## 2026-08-11 — Первая версия, часть унификации Work/Post UI

**Что нужно было сделать.** `relatedWorkSlug`/`relatedPostSlug` стали
основой наследования hue (`resolvePostHue`) — опечатка или устаревший
(переименованный/удалённый) slug в свободном текстовом поле молча
деградирует к обычной категории, без единого сигнала админу, что связь
не сработала. Нужен виджет, гарантирующий: то, что сохранено — либо
`null`, либо реально существующий slug.

**Как сделано.** Односелектный (в отличие от `TokenCombobox`,
множественного) searchable-виджет: полный список вариантов приходит
пропом (`options: {slug, label}[]`, получен на сервере тем же способом,
что и `PostEditorPage`'s `existingCategories` — без нового backend-эндпоинта
поиска, см. план), фильтрация — на клиенте через уже существующий
`fuzzyMatchScore` (`token-combobox/fuzzy-match.ts`, тот же алгоритм,
не второй). Закоммитить можно ТОЛЬКО реальный вариант из списка — Enter
без выделенной опции, потеря фокуса без клика по опции — всё это
откатывает поле назад к текущему выбранному значению, никогда не
принимает набранный текст как есть.

**Понятность для другого разработчика.** Сознательно НЕ переиспользует
`TokenCombobox`, хотя визуально похож (тот же ARIA combobox-паттерн,
тот же алгоритм фаззи-поиска) — `TokenCombobox` по своей природе
множественный и свободнотекстовый (см. его `README.md`), а этому
виджету нужно ровно противоположное в обоих измерениях: один выбор,
и только из реально существующих элементов. Попытка натянуть один
компонент на обе задачи означала бы либо два несовместимых режима внутри
одного файла, либо борьбу с чужим поведением на каждом взаимодействии.

**Нагрузка.** Клиенту передаётся весь список постов/work-элементов
одним пропом — приемлемо на масштабе личного портфолио (десятки, не
тысячи элементов), тот же расчёт, что уже сделан для `CategoryPicker`'s
чипов.

**Расширяемость/заменяемость.** Если список вырастет достаточно, чтобы
клиентская фильтрация стала дорогой — единственное, что придётся
поменять, это ОТКУДА берётся `options` (серверный поиск по запросу
вместо полного списка), сам компонент фильтрует уже готовый список и не
будет знать о разнице.

**Миграция/отказоустойчивость.** Не применимо — чистый презентационный
компонент, ничего не пишет напрямую в БД (вызывающая сторона решает,
что делать с `onChange`'нутым slug'ом).

**SOLID.** Single Responsibility: компонент не проверяет существование
`options`' элементов В БАЗЕ — это ответственность страницы, которая их
туда передала; он гарантирует только то, что САМ может гарантировать —
что закоммиченное значение — это ровно один из переданных вариантов
или `null`.

## Исключён из Storybook-снапшотов

Как и `TokenCombobox` (см. `component-gallery.manifest.ts`'s doc-комментарий) —
этот компонент нужен только за админ-аутентификацией, и вся его реальная
ценность (фаззи-выпадающий список, навигация с клавиатуры, откат при потере
фокуса) проявляется только через взаимодействие, которое статичный
скриншот не проверяет. Покрыт напрямую `RelatedItemPicker.test.tsx`.
