# web — Next.js-приложение (SSR + admin + backend)

Это версия сайта, которая реально работает в проде: Next.js (App Router),
рендеринг на сервере, данные из PostgreSQL, встроенная админка. Cutover на
nginx уже произошёл — `https://yuriisoft.me/` и `https://dev.yuriisoft.me/`
отдаются этим приложением (проверяется по заголовку `X-Powered-By: Next.js`).
`frontend/` (старый Vite SPA) больше ничего не обслуживает и держится в
репозитории только до завершения его удаления и последующего переименования
`web/` → `frontend/` — отдельный шаг, ещё не выполненный на момент этой
записи. *(Оба шага выполнены позже — см. записи ниже.)*


## Журнал решений

### 2026-07-18 — Где живёт новый проект относительно `frontend/`

**Что нужно сделать.** Выбрать расположение нового Next.js-проекта в
репозитории так, чтобы миграция не сломала текущий деплой `frontend/` и
не мешала одновременной разработке.

**Как сделано.** Новый проект создан в `frontend/` — отдельной директории на
верхнем уровне репозитория, рядом с `frontend/`. Ни один файл `frontend/` не
тронут. `frontend/` продолжает собираться и деплоиться существующим
GitHub Actions workflow (`deploy_release.yaml`) без изменений, пока весь
функционал не будет перенесён и проверен. Переключение (cutover) — отдельный,
более поздний шаг: замена nginx-конфига с раздачи `frontend/dist` на
проксирование в Next.js-процесс, и только после этого `frontend/` можно будет
удалить или архивировать.

**Понятность для другого разработчика.** Разделение прозрачное: два корневых
проекта, у каждого свой `package.json`, свой `README.md`. Не требует
понимания монорепо-инструментов (Turborepo/Nx/pnpm workspaces) — это два
независимых npm-проекта, что соответствует единственному Next.js-приложению
без микросервисной архитектуры backend'а.

**Нагрузка.** Не применимо к этому решению — это вопрос организации кода в
репозитории, а не рантайм-архитектуры.

**Расширяемость/заменяемость.** Полностью: старый `frontend/` можно удалить
одним `git rm -r`, ничего в `frontend/` от этого не изменится, так как между ними
нет общих файлов и импортов.

**Миграция данных / отказоустойчивость.** Не применимо к этому шагу — данные
появятся начиная с Фазы 2 плана.

**SOLID.** Не применимо к структуре директорий, но по духу — это Dependency
Inversion на уровне инфраструктуры: деплой-пайплайн `frontend/` не зависит от
того, что происходит внутри `frontend/`, и наоборот.

### 2026-07-18 — Один процесс Next.js, backend — это папка внутри проекта, а не отдельный сервис

> **Уточнено позже в тот же день**: "внутри проекта" в итоге означает не
> `frontend/src/backend/`, а `/backend` как отдельный npm workspace-пакет рядом с
> `frontend/` на верхнем уровне репозитория — тот же однопроцессный runtime, но
> более явное разделение по вашей просьбе. Полный разбор, включая находку
> про Turbopack и то, почему обычный путь-алиас не подошёл — в
> `backend/README.md`. Оставляю эту запись ниже как есть — рассуждение о
> "один процесс vs отдельный сервис" не изменилось, изменилось только ГДЕ
> физически лежит папка.

**Что нужно сделать.** Определить, где живёт "backend"-логика (Prisma, работа
с БД, авторизация, бизнес-логика) — в отдельном сервисе (Express/Fastify) или
внутри самого Next.js-приложения.

**Как сделано.** Выбран второй вариант: один Next.js-процесс на VPS, а
backend-логика организована в `src/backend/` внутри этого же проекта.
"Backend" здесь — архитектурный слой (папка с серверным кодом), а не
отдельный деплоймент. Next.js Route Handlers (`src/app/api/**/route.ts`)
и Server Components обращаются к этому слою напрямую, без HTTP-запроса
между "фронтом" и "бэком" — они выполняются в одном процессе.

**Понятность для другого разработчика.** Название папки (`backend`) прямо
говорит о её назначении, что важно, раз мы отказались от буквального
разделения на два сервиса — человек, ожидающий увидеть "papку backend",
её увидит, просто внутри, а не как соседний проект.

**Нагрузка.** Один процесс — меньше сетевых прыжков на каждый запрос
(no HTTP hop между "frontend" и "backend"), что быстрее и не требует
отдельного пула соединений с БД на каждый сервис.

**Расширяемость/заменяемость.** Если в будущем понадобится вынести backend в
отдельный сервис (например, ради независимого масштабирования), код в
`src/backend/` уже изолирован от `src/app/` через чёткую границу импортов —
его можно вынести в отдельный npm-пакет/сервис позже без переписывания
бизнес-логики, только слоя транспорта (Route Handlers → HTTP-клиент).

**Миграция данных / отказоустойчивость.** Не применимо к этому шагу.

**SOLID.** Dependency Inversion: `src/app` (Route Handlers, Server
Components) зависит от абстракций backend-слоя (сервисов), а не от деталей
Prisma/JWT напрямую в каждом файле роута — сами детали спрятаны внутри
`src/backend`.

### 2026-07-18 — Находка: `styled-components` заявлен в зависимостях, но не используется

**Что нужно сделать.** По плану миграции предполагалось настроить SSR registry
для `styled-components` (стандартный шаг при переносе styled-components в
Next.js App Router).

**Как сделано.** Перед тем как тратить время на registry, проверено:
`grep` по всему `frontend/src` на `styled(` и `from "styled-components"` —
ноль совпадений. Пакет висит в `package.json`, но реально не импортируется
ни в одном файле. Вся стилизация — Tailwind v4 + CSS custom properties
(design tokens в `shared/ui/theme/theme.css.ts`, собираются в строку и
вставляются как обычный `<style>`, без runtime styled-components). Значит,
шаг "styled-components SSR registry" из плана — не нужен, и сам пакет в
`frontend/` не добавляется вовсе.

**Понятность для другого разработчика.** Упрощает картину: один способ
стилизации (Tailwind + CSS-переменные), а не два конкурирующих подхода.

**Нагрузка.** Меньше на один runtime-зависимость (styled-components
генерирует и вставляет `<style>`-теги на клиенте при каждом рендере
компонента) — обычный CSS через Tailwind дешевле по CPU/памяти на слабом
VPS.

**Расширяемость/заменяемость.** Не теряется ничего: если styled-components
понадобится позже для конкретного компонента, его можно добавить точечно, не
меняя остальную архитектуру.

**Миграция данных / отказоустойчивость.** Не применимо.

**SOLID.** Это скорее YAGNI/KISS, чем SOLID напрямую — не тащим
инфраструктуру (SSR registry, доп. babel/next-plugin конфигурацию) под
зависимость, которая нигде не используется.

### 2026-07-18 — Границы Client Component из-за `useTranslation()`/`useTheme()`

**Что нужно сделать.** Next.js App Router по умолчанию рендерит компоненты
на сервере (Server Components) и не даёт им использовать React-хуки вообще
— ни `useState`, ни `useContext`. `useTranslation()` и `useTheme()` из
`shared/i18n`/`shared/theme` — это обёртки над `useContext`, а значит любой
компонент, вызывающий их напрямую, обязан быть Client Component
(директива `"use client"` в первой строке файла).

**Как сделано.** Через `grep` по всему `frontend/src` на `useTranslation()` /
`useTheme()` / `useState` / `useEffect` / `useContext` найдены все файлы,
которые вызывают хук напрямую (а не только те, что мне казались
интерактивными на глаз) — добавлена директива `"use client"` туда, где её
не было: `Nav`, `AppLayout`, обе detail-страницы, обе list-страницы, секции
лендинга (`Hero`, `Principles`, `TechStack`, `ContactCta`, `SelectedWork`,
`JournalPreview`), `Footer`, оба переключателя в `Nav`, `ContentBlocks`,
`CodeBlock`/`CodeBlockContent`, сам `ThemeProvider`/`I18nProvider` и их
хуки, `ThemeToggle`, `DesignSystemPlayground`, `Storybook`.

**Понятность для другого разработчика.** Директива стоит прямо в файле,
который использует хук — не нужно знать "откуда-то сверху" в дереве
компонентов, что конкретный файл на самом деле клиентский; в этом смысле
явное дублирование директивы в каждом файле-потребителе хука безопаснее,
чем полагаться на неявное наследование границы от родителя.

**Нагрузка.** Существенная часть страницы (весь текст, зависящий от
`pick()`/`ln()`) рендерится на клиенте, а не на сервере — то есть SSR
Фазы 1 даёт SEO/скорость первой отрисовки в первую очередь для разметки и
статических частей (например, `layout.tsx`), но не устраняет клиентский
рендеринг текста целиком. Это ожидаемо и совпадает с решением "не трогать
архитектуру i18n в Фазе 1" — если в будущем понадобится полный SSR для
переведённого текста, i18n-систему придётся пересмотреть отдельно (скорее
всего в сторону чтения словаря на сервере вместо Context на клиенте).

**Расширяемость/заменяемость.** Компоненты, которые НЕ используют
`useTranslation()`/`useTheme()` напрямую (например, чисто презентационные
`Card`, `Tag`, `Text`, `Button`), остались без директивы — они могут в
будущем рендериться и на сервере, если когда-нибудь понадобится страница без
i18n-хуков.

**Миграция/отказоустойчивость.** Не применимо.

**SOLID.** Не затрагивает SOLID напрямую — это ограничение платформы
(Server/Client Component boundary), а не структуры классов/модулей.

### 2026-07-18 — Коллизия имён: FSD-слой `pages/` vs Next.js Pages Router

**Что нужно сделать.** `frontend/` использует feature-sliced-слой с именем
`pages/` (`pages/landing`, `pages/journal-detail`, ...). Это обычное имя
слоя в FSD — но у Next.js есть свой, отдельный от App Router, легаси-роутер
("Pages Router"), который автоматически превращает **любую** папку `pages/`
(в том числе `src/pages/`) в маршруты, по одному файлу на маршрут.

**Как сделано.** При первой сборке (`npm run build`) Next.js упал с ошибкой
`App Router and Pages Router both match path: /storybook` — он
самостоятельно нашёл `src/pages/storybook/` и решил, что это легаси-роут
`/storybook`, что конфликтует с явным `app/storybook/page.tsx`. Никакого
флага "отключить автоопределение Pages Router, но оставить App Router" в
Next.js нет — единственное решение — не называть папку `pages`. Слой
переименован в `views/` (`src/views/landing`, `src/views/journal-detail`,
...), обновлены все 6 импортов из `app/**/page.tsx`.

**Понятность для другого разработчика.** Само по себе `views` вместо
`pages` менее привычно для FSD-документации (там канонично `pages`), так что
это стоит явно знать при онбординге в проект — что здесь `views` это тот же
концепт, что в FSD называется `pages`, просто переименован из-за конфликта
имён с Next.js.

**Нагрузка.** Не применимо.

**Расширяемость/заменяемость.** Не теряется ничего — просто другое имя папки,
весь остальной FSD-слой (widgets/feature/shared/entities) сохраняет
стандартные имена, коллизия была только у этого одного слоя.

**Миграция/отказоустойчивость.** Не применимо.

**SOLID.** Не применимо — вопрос именования, не структуры зависимостей.

### 2026-07-18 — Явные `.ts`/`.tsx` в путях импорта не проходят тайпчек Next.js

**Что нужно сделать.** Часть кода в `frontend/` пишет
`from "./Component.tsx"` (с расширением) — Vite это нормально ест.

**Как сделано.** `next build` компилируется, но падает на этапе тайпчека:
`An import path can only end with a '.tsx' extension when
'allowImportingTsExtensions' is enabled`. Вместо включения этого флага (он
предназначен для специфичных сценариев, не для обычного кода) убраны
расширения `.ts`/`.tsx` из всех путей импорта/экспорта по всему `frontend/src`
(один regex-проход по всем файлам) — это и есть стандартный, переносимый
способ писать импорты в TypeScript, независимо от Vite/Next.js/webpack.

**Понятность для другого разработчика.** Импорты без расширений — то, что
ожидает увидеть любой TS/React-разработчик; версия с `.tsx` в импорте была
скорее особенностью конкретной настройки Vite, чем осознанным стилем.

**Нагрузка / расширяемость / миграция.** Не применимо — чисто синтаксическая
правка, поведение кода не изменилось.

**SOLID.** Не применимо.

### 2026-07-18 — `lucide-react` закреплён на версии `frontend/`, а не latest

**Что нужно сделать.** Установить те же runtime-зависимости, что использует
`frontend/` (`clsx`, `lucide-react`, `prismjs`, `tailwind-merge`).

**Как сделано.** `npm install lucide-react` без версии поставил `^1.25.0`
(на две мажорных версии новее, чем `^0.553.0` в `frontend/`) — и тайпчек
сразу упал: `Github` больше не экспортируется под этим именем (иконки в
lucide-react периодически переименовываются между мажорными версиями).
Закреплено на точную версию `frontend/` (`lucide-react@0.553.0`) — это не
"более старая/хуже" версия, а гарантия, что набор иконок и их API идентичны
уже проверенному в проде коду, без риска визуальных отличий или новых
поломок API при апгрейде "заодно" с миграцией на Next.js.

**Понятность / нагрузка / расширяемость / миграция / SOLID.** Не
применимо — версия зависимости, не архитектурное решение. Апгрейд
lucide-react до последней версии — отдельная, самостоятельная задача, не
часть миграции на Next.js.

### 2026-07-19 — `middleware.ts` → `proxy.ts` (Next.js 16 rename) + утечка Node-only кода в Edge через общий индекс пакета

**Что нужно сделать.** Защитить `/admin/*` и `/api/admin/*` через
Next.js middleware, проверяя access-токен.

**Как сделано, две находки сразу при первой сборке:**

1. Сборка вывела предупреждение: `The "middleware" file convention is
   deprecated. Please use "proxy" instead.` — в Next.js 16 файл
   `middleware.ts` и экспортируемая функция `middleware()` переименованы в
   `proxy.ts`/`proxy()` (официальный codemod:
   `npx @next/codemod@canary middleware-to-proxy .`). Причина переименования
   от самой команды Next.js — слово "middleware" путали с Express.js
   middleware, что провоцировало не по назначению использовать эту фичу;
   "proxy" честнее описывает, что это сетевая граница перед приложением.
   Файл переименован, функция переименована, `export const config` (matcher)
   не изменился.

2. Более серьёзная находка: сборка также предупредила — `A Node.js module is
   loaded ('node:crypto') which is not supported in the Edge Runtime`, с
   трейсом импортов `proxy.ts → @portfolio/backend (index) →
   auth/session.ts → auth/tokens.ts → node:crypto`. `proxy.ts`
   (Edge-рантайм по умолчанию) импортировал `verifyAccessToken` из ГЛАВНОГО
   входа пакета `@portfolio/backend` — а этот вход одним модульным графом
   тащит за собой `Session`/`login`-логику, которая использует
   `node:crypto`, Prisma и `pg` — ничего из этого не работает в Edge.
   Turbopack на это только предупреждает, не проваливает сборку — то есть
   легко было бы задеплоить это незамеченным и получить реальную ошибку
   уже в рантайме на Edge.

   Исправлено добавлением отдельной, edge-безопасной точки входа в пакет:
   `backend/src/edge.ts` (экспортирует только `verifyAccessToken`/
   `signAccessToken`, зависящие исключительно от `jose`) + subpath export
   `"./edge"` в `backend/package.json`. `proxy.ts` импортирует
   `@portfolio/backend/edge`, а не `@portfolio/backend` — после этого
   предупреждение исчезло полностью.

**Понятность для другого разработчика.** Комментарий в `edge.ts` прямо
говорит: "добавляй сюда экспорт только после проверки, что он не тащит
Node-only модули" — иначе кто-то по привычке добавит туда что-то из
`session.ts` и молча воссоздаст ту же проблему.

**Нагрузка.** Edge-бандл `proxy.ts` теперь весит заметно меньше — не тащит
Prisma/`pg` целиком, только `jose`.

**Расширяемость/заменяемость.** Паттерн "главный вход + `/edge` subpath"
масштабируется на будущее: если понадобится больше Edge-безопасных
утилит, они добавляются в `edge.ts`; если понадобится защитить ещё
какой-то путь через `proxy.ts`, он уже готовый образец, как правильно
импортировать.

**Миграция/отказоустойчивость.** Не применимо к этому шагу.

**SOLID.** Interface Segregation в чистом виде: `@portfolio/backend/edge`
— это узкий, специально урезанный интерфейс для одного конкретного
потребителя (Edge-рантайм), а не "экспортируй всё и надейся, что
tree-shaking разберётся".

### 2026-07-19 — Next.js молча запекал контент из БД как статику при сборке

**Что нужно сделать.** Перевести `/`, `/journal`, `/work` на чтение из
Postgres (Фаза 3).

**Как сделано.** Первая сборка после перевода прошла успешно, но вывод
`next build` показал `/`, `/journal`, `/work` со значком `○` (Static) —
Next.js сам определил, что у этих страниц нет ничего "динамического"
(нет `cookies()`/`headers()`, нет параметров маршрута), и **сгенерировал
их HTML один раз во время сборки**, зашив в него то, что вернули
`getFeaturedWork()`/`getJournalEntries()`/`getAllWork()` в этот конкретный
момент. Это ровно та проблема, ради решения которой затевалась вся
миграция: пост, добавленный через будущую админку (Фаза 4), не появился бы
на этих страницах до следующей полной пересборки и передеплоя сайта —
Next.js незаметно вернул бы нас туда, откуда мы уходили.

Исправлено: `export const dynamic = "force-dynamic";` в `page.tsx` каждого
из трёх маршрутов — принудительно рендерит их на каждый запрос, как уже
по умолчанию происходит с `/journal/[slug]` и `/work/[slug]` (их Next.js
сам считает динамическими из-за параметра маршрута).

**Понятность для другого разработчика.** Комментарий в каждом файле прямо
объясняет, почему флаг нужен именно здесь — без него не очевидно, почему
"обычный" Server Component вдруг требует специальной пометки.

**Нагрузка.** Каждый запрос к этим трём маршрутам теперь бьёт в Postgres
напрямую вместо чтения готового статического HTML. Для сайта такого
масштаба (личный сайт-визитка, не высокий трафик) это несущественно —
запрос к локальной/соседней Postgres занимает единицы миллисекунд. Если
трафик когда-нибудь станет проблемой — см. следующий пункт.

**Расширяемость/заменяемость.** Явно оставлен путь назад: когда в Фазе 4
у публикации/сохранения контента появится серверный action, он может
вызвать `revalidatePath("/journal")` и т.д. сразу после записи в БД — тогда
эти страницы можно вернуть к обычному статическому рендерингу (ISR
"on-demand revalidation") и получить обратно производительность статики,
не теряя мгновенного обновления после публикации. Не сделано сейчас
только потому, что механизма публикации ещё не существует — незачем
строить revalidation под то, чего пока нет.

**Миграция/отказоустойчивость.** Прямое отношение к тому, зачем всё это
затевалось — без этого фикса "миграция на БД" была бы фактически
бесполезна для главной цели (контент без пересборки).

**SOLID.** Не применимо напрямую — это платформенное поведение Next.js
(автоматическая статическая оптимизация), а не структурное решение в коде
проекта.

### Заметка для отладки: если `next dev` "принимает" запросы, но не отвечает

При верификации Фазы 3 порт 3000 перестал отвечать на ЛЮБые запросы (даже
на `/storybook`, не трогающий базу) после множества перезапусков
dev-сервера в одной сессии — при этом `netstat` показывал порт как
`LISTENING`, TCP-хэндшейк проходил (`curl -v` подключался), но ответ не

(`next dev -p 3005`). Если это повторится — это чинить окружение
(процессы/кэш/порт), не искать баг в коде.

### 2026-07-19 — Отказоустойчивость при недоступной БД + найденный `instanceof`-баг между Next.js-контекстами

**Что нужно сделать.** Сайт упал с сырым Prisma-стектрейсом, когда Docker
(и, соответственно, Postgres) был не запущен — нужна красивая страница
вместо краша, и это не должно повторяться.

**Как сделано.**

1. **`backend/src/errors.ts` + `db/client.ts`**: один Prisma Client
   Extension (`$extends`) в `db/client.ts` перехватывает ЛЮБОЙ запрос к
   базе и, если это именно "сервер недоступен" (код Prisma `P1001` или
   `PrismaClientInitializationError` — стабильный, документированный
   признак, а не парсинг текста ошибки), перевыбрасывает как собственный
   `DatabaseUnavailableError` — без внутренних деталей (хост, порт,
   драйвер), которые не должны утекать до `frontend/`.
2. **`frontend/src/shared/lib/render-with-fallback.tsx`**: общая обёртка для
   всех 5 `page.tsx`, которые тянут контент — при `DatabaseUnavailableError`
   рендерит `<ServiceUnavailable/>` (красивая страница с кнопкой "Попробовать
   снова") вместо падения; любая другая ошибка улетает дальше, в общий
   `app/(site)/error.tsx` (сеть безопасности для настоящих багов).
   `<AppLayout/>` (Nav/Footer) рендерится вокруг этого как ни в чём не
   бывало — `error.tsx`/ручной catch в `page.tsx` заменяют только контент
   самого сегмента, не родительский layout.
3. **`frontend/src/shared/lib/api-error-response.ts`**: то же самое для
   `/api/auth/login`, `/refresh`, `/logout` — 503 + `Retry-After` вместо
   голого 500 без тела.

**Найденный по дороге баг**: первая версия проверяла
`error instanceof DatabaseUnavailableError` — типы компилировались чисто,
но на живом запросе (остановленный Postgres + `curl` на `/api/auth/login`)
проверка молча возвращала `false`, и в логах всё равно был голый 500.
Причина: Next.js/Turbopack компилирует `@portfolio/backend` ОТДЕЛЬНО для
разных контекстов выполнения (Server Components — один бандл, Route
Handlers — другой) — класс, брошенный в одном бандле, не признаётся
`instanceof` в другом, даже будучи буквально тем же файлом на диске.
Исправлено проверкой по `error.name` (`isDatabaseUnavailableError()` в
`backend/src/errors.ts`) — обычная строка на инстансе, которая переживает
пересечение этой границы бандлов, в отличие от идентичности класса.
Показательно, что `render-with-fallback.tsx` (Server Components) при
первом тесте СЛУЧАЙНО сработал корректно с `instanceof` — но раз один из
двух вызывающих контекстов ломался, оба переведены на надёжную проверку,
а не оставлен "работает по случайности" код рядом с явно поломанным.

**Понятность для другого разработчика.** Комментарий у
`isDatabaseUnavailableError()` прямо объясняет, зачем проверка по имени, а
не по классу — иначе кто-то может "оптимизировать" обратно в `instanceof`
при рефакторинге и молча вернуть баг.

**Нагрузка.** Расширение Prisma добавляет один `try/catch` вокруг каждого
запроса — пренебрежимо по сравнению с самим сетевым round-trip к БД.

**Расширяемость/заменяемость.** Любая новая функция в `backend/src/content`
или будущих сервисах Фазы 4 автоматически получает такую же трансляцию
ошибок — не нужно оборачивать каждую новую функцию вручную.

**Миграция/отказоустойчивость.** Прямое отношение — это и есть fix на
отказоустойчивость. Проверено вживую: `docker stop` контейнера Postgres →
`/`, `/journal`, `/work` отдают 200 с красивой страницей (Nav/Footer на
месте), `/api/auth/login` отдаёт 503 с понятным JSON вместо голого 500 →
`docker start` → сайт восстанавливается сам, без перезапуска.

**SOLID.** Dependency Inversion: `frontend/` реагирует на собственный,
контролируемый тип ошибки backend-пакета (`DatabaseUnavailableError`/его
предикат), а не на детали конкретного Prisma error code — если Prisma
когда-нибудь поменяет код/класс для этого случая, меняется только
`backend/src/errors.ts`, ни один потребитель в `frontend/` не тронут.

альтернатив (таблица путей, NestJS-style декораторы, policy engine, tRPC)
и почему выбран именно этот вариант — в чате, приведшем к этому изменению;
здесь только само решение и его следствия для структуры `frontend/`.

**Как сделано.** `proxy.ts` больше не проверяет JWT и не решает "admin или
нет" — это переехало в `frontend/src/shared/lib/auth/`
(`resolvePrincipal`/`defineAdminRoute`/`definePublicRoute`/`requirePage`,
см. его собственный README для полного обоснования). `proxy.ts` сузился до
двух вещей, которые Edge-слой физически способен решать по одной только
форме URL: locale-роутинг (без изменений) и IP-based rate limiting (новое,
см. `backend/src/auth/README.md`'s 2026-07-27 запись). Единственное, что он
всё ещё делает для `/admin`/`/api` — проставляет заголовок с текущим
pathname (`x-pathname`), чтобы `requirePage()` мог собрать `?from=`
редирект (у Server Component нет другого способа узнать текущий путь).

**Первый заход, который отвергли по ходу обсуждения.** Изначальный план
заменял `pathname.startsWith("/admin")` внутри `proxy.ts` на явную таблицу
`{ pattern, requirement }[]` — формально "явный контракт", но по сути та же
проблема: middleware выполняется ДО того, как Next.js резолвит конкретный
`route.ts`, так что у него физически нет доступа к тому, что нужно
конкретному хендлеру — только к форме URL. Таблица путей неизбежно
осталась бы оторванной от кода, который авторизацию реализует.

**Понятность для другого разработчика.** `frontend/src/shared/lib/auth/
README.md` — вся аргументация целиком, включая отвергнутый вариант.

**Нагрузка/масштабирование.** `resolvePrincipal` — чистая проверка подписи
JWT, без похода в БД — одинаково дёшева на любом числе Next.js-инстансов за
балансировщиком. Rate limiting теперь общий (Upstash Redis) для всех
инстансов вместо in-memory на процесс — последний stateful угол сессионной
модели, требовавший внешнего хранилища, теперь его использует.

**SOLID.** Dependency Inversion на уровне файла: каждый `route.ts`/
`page.tsx` зависит от абстракции "мне нужны вот такие scopes"
(`defineAdminRoute(handler)`), не от деталей верификации токена — те
спрятаны в `shared/lib/auth/principal.ts`.

### 2026-08-08 — SEO-слой: метаданные, robots/sitemap, JSON-LD, OG-картинки, IndexNow

Полный разбор — `src/shared/lib/seo/README.md`. Здесь только то, что
касается всего приложения, и три вещи, найденные вживую.

**Найденный по дороге баг, который не имеет отношения к SEO, но ломал его
русскую половину: под `next start` КАЖДЫЙ `/ru/...` URL рендерился
по-английски.** `<html lang="en">`, английский `<title>`, английское тело —
включая `/ru/storybook`, который к этой задаче отношения не имеет вообще,
то есть баг был до неё. Причина: Next.js 16 вызывает `proxy()` ВТОРОЙ раз —
на внутреннем адресе, в который сам же и переписал запрос. Второй проход
видит уже голый `/journal/x` без префикса `/ru` и безусловным
`set(LOCALE_HEADER, "en")` затирал локаль, которую первый проход только что
разрешил. Диагностировано временным заголовком, накапливающим по записи на
вызов (`|/ru/journal/x=ru|/journal/x=en`), а не перечитыванием файла:
догадаться отсюда было нечем, оба прохода по отдельности выглядят
корректно. Исправлено сохранением уже выставленного значения на не-`/ru`
ветке. Цена, названная в комментарии там же: клиент может прислать
`x-locale: ru` вручную и получить русский рендер на английском URL — это
язык отображения для одного подделанного запроса, не авторизация, и
краулеры этот заголовок не шлют вообще, так что canonical не затрагивается.

**Продолжение того же бага: сохранение заголовка чинило симптом, но
делало его подделываемым.** Первая версия фикса просто не затирала уже
выставленный `x-locale` на втором проходе — работало, но означало, что
клиент может прислать `x-locale: ru` руками и получить русский рендер на
английском URL. Сегодня это язык отображения для одного запроса, и оценка
«не авторизация» верна. Завтра — нет: как только перед приложением
появится общий кэш (nginx `proxy_cache`, CDN), ключ которого по умолчанию
это URL и только URL, ОДИН подделанный запрос положит русский ответ под
английский адрес и будет отдавать его всем до истечения записи. Класс
проблемы меняется с «навредил себе» на отравление кэша без единой правки
с нашей стороны.

**`Vary: x-locale` — учебниковый ответ, и он здесь НЕ РАБОТАЕТ.** Проверено
`curl -D -` против настоящего продакшн-билда, дважды. Добавленный к ответу
middleware — отбрасывается: Next.js перезаписывает заголовок своим списком
(`rsc, next-router-state-tree, ...`). Объявленный в `headers()` из
`next.config.ts` — доезжает до route-хендлеров (`/robots.txt`,
`/sitemap.xml`, OG-роуты), но на Server-Component-страницах опять
перезаписывается. То есть единственное место, где он был нужен, — ровно то,
куда он не попадает. И это ловушка: `curl` по `/robots.txt` показывает
`vary: x-locale` и выглядит как успех.

**Поэтому убран скрытый вход, а не описан.** Локаль теперь едет в
переписанном URL (`/ru/journal/x` → `/journal/x?__locale=ru`), а
`x-locale` стал исключительно ВЫХОДОМ прокси — он безусловно
перезаписывается на каждом проходе, клиентское значение отбрасывается.
Ответ становится чистой функцией URL, а это ровно то, что кэш и
предполагает; подделать `?__locale=ru` можно, и это безвредно — другой URL,
другой ключ кэша. Локаль впервые покрыта юнит-тестами (`proxy.test.ts`,
6 штук): раньше её не пиннило ничто, чем и объясняется, что она молча
ломалась.

**`cache()` действительно дедуплицирует — измерено, а не выведено.** В
плане это был открытый вопрос: документация React ограничивает кэш рендером
компонента, а в трекере Next.js есть незакрытый issue про `cache()`,
который не срабатывает именно в `generateMetadata`. Замер: `next build &&
next start`, `PRISMA_LOG_QUERIES=true` (переключатель добавлен в
`backend/src/db/client.ts` ровно для этого), один запрос
`/journal/flowbus`. Результат — **5 запросов всего: `Post` ровно один раз**
(а не два, хотя его просят и `generateMetadata`, и компонент страницы),
`SiteContent` ровно один раз (хотя `config` просят три места: layout сайта,
`generateMetadata` и сама страница), плюс `Work` для связанного кейса и два
`Block` для двух тел. То есть общий модуль `shared/lib/cached-content.ts`
работает поперёк `generateMetadata` и рендера. Побочно исправлена уже
существовавшая двойная выборка `config` на главной.

Правило, которое обязано быть записано, потому что нарушается молча:
**`cache(fn)` вычисляется только на уровне модуля.** Вызов внутри тела
компонента или внутри `generateMetadata` создаёт свежую мемоизированную
функцию на каждый вызов, не дедуплицирует ничего и не даёт ни ошибки, ни
предупреждения.

**`src/instrumentation.ts` — расположение и способ падения.** Файл лежит в
`src/`, а не в корне пакета: при наличии папки `src` продакшн-запуск
подхватывает инструментацию только оттуда, а корневой файл под `next start`
молча игнорируется (в dev с Turbopack при этом работает). Завершение —
явный `process.exit(1)`, не `throw`: брошенное из `register()` исключение
валит только `next dev`, а под `next start` сервер остаётся поднятым,
отвечает на первый запрос и перестаёт отвечать на все следующие — тот самый
симптом «принимает соединения, но не отвечает», который в этом README уже
записан за застрявшим процессом, то есть был бы диагностирован
неправильно. Проверено под `next build && next start`: `SEO_INDEXABLE=true`
с пустым `SITE_URL` и с `SITE_URL=http://localhost:3000` — оба раза код
выхода 1 и внятное сообщение; с полностью пустой SEO-конфигурацией
`/admin/login`, `/storybook` и `/` отвечают 200.

Node-специфичная половина вынесена в `src/instrumentation.node.ts` за
динамическим импортом: Turbopack компилирует инструментацию и под Edge, и
литеральный `process.exit` в общем файле давал предупреждение сборки об
неподдерживаемом Node API — тоже видно только в выводе реальной сборки.

**`app/robots.ts` обязан быть `force-dynamic` — иначе выкат ломался бы
молча и необратимо.** Первая версия его не имела, и `next build` показал
маршрут как `○ (Static)`: Next.js запекал robots.txt в момент сборки. А
собирается прод в GitHub Actions, где `SEO_INDEXABLE` и `SITE_URL` не
существуют — они лежат в `shared/.env` на сервере. То есть задеплоенный
файл говорил бы `Disallow: /` навсегда, независимо от окружения работающего
процесса, и никакая правка переменных на сервере это не починила бы.
Найдено чтением таблицы маршрутов в выводе сборки; проверено сценарием
«собрать без переменных, запустить с переменными» — robots.txt отдаёт
разрешающую версию, canonical абсолютный, `/ru/...` рендерится по-русски.
У `app/sitemap.ts` та же строка стоит по соседней причине (контент меняется
без передеплоя).

**Порядок выката на прод — самое опасное место всей задачи, и оно
автоматизировано.** Индексация opt-in, поэтому забытая на проде
переменная означает `noindex` на всём сайте: fail-safe, защищающий dev от
случайной индексации, оборачивается против прода. План предполагал ручную
установку переменных один раз при провижене — от этого отказались, потому
что «не забыть» это не мера.

`deploy-target.yml` получил два ОБЯЗАТЕЛЬНЫХ входа, `seo-indexable` и
`site-url`, и шаг «Publish SEO configuration», который кладёт их в
`shared/.env` цели через уже существующий `set-app-env-finish.sh`.
Значения задаются в месте вызова (`deploy-frontend.yaml`): у dev
`"false"` + `https://dev.yuriisoft.me`, у prod `"true"` +
`https://yuriisoft.me`. Входы, а не секреты — они не секретны, а в месте
вызова видно, какая среда индексируется. `required: true` означает, что
новую цель деплоя нельзя завести, не ответив на этот вопрос.

Две детали расстановки, обе про режим отказа, а не про аккуратность:

- Шаг стоит **до** деплоя, в отличие от соседнего «Sync optional env
 vars». `deploy-frontend-finish.sh` вкладывает `shared/.env` в новый
 релиз перед стартом, поэтому релиз поднимается уже индексируемым; после
 деплоя он стартовал бы с `noindex` и получал переменные только со
 вторым рестартом — короткое, но настоящее окно, в котором прод просит
 краулеров себя не индексировать.
- У шага **нет** `continue-on-error`: при сбое деплой не состоится, и
 продолжит работать прежний, корректно настроенный релиз. Сбой после
 деплоя оставил бы живым новый релиз с неверной конфигурацией.

Побочное следствие, названное явно: шаг зависит от
`/usr/local/bin/set-app-env-finish.sh` (`provision/12-set-app-env-helper.sh`).
Соседний шаг тоже от него зависел, но терпел его отсутствие; этот — нет,
так что цель, пропустившая этот шаг провижена, теперь роняет деплой вместо
тихой выкладки неправильно настроенного сайта.

Search Console по-прежнему заводится до выката — иначе не с чем будет
сравнивать падение покрытия. А пост-деплойная проверка `/robots.txt` на
`Disallow: /` остаётся в отдельной задаче вместе с откатом симлинка
(`deploy-frontend-finish.sh` переключает `current` до рестарта и назад не
откатывает): автоматическая публикация переменных убирает самый вероятный
способ ошибиться, но не подтверждает, что боевой сайт действительно
индексируем.

**Исправление с code review: молчаливые `catch` — оставлено в записи как
ошибка.** Первая версия ловила отказ БД голым `catch` в пяти
`generateMetadata`, в `sitemap.ts` и через `.catch(() => null)` в трёх
роутах OG-картинок. Задуман он под недоступную базу, но глотал всё
подряд, включая ошибки программиста: `TypeError` при сборке метаданных
тихо делал страницу `noindex` без записи в лог и без страницы ошибки, а
баг в маппинге карты сайта навсегда оставлял три URL вместо тридцати.
Исправлено не добавлением логов, а сужением: `shared/lib/db-outage-fallback.ts`
отдаёт запасное значение только при `isDatabaseUnavailableError(error)` —
предикат, который в репозитории появился ровно для этого различения, — и
пробрасывает всё остальное. Один хелпер на девять вызовов, чтобы сужение
нельзя было забыть в одном из них. Подробности —
`src/shared/lib/seo/README.md`.

**Продолжение того же исправления, найденное упавшей сборкой в CI.**
Сужение `catch`'а сделало ровно то, ради чего задумывалось: перестало
прятать ошибку — и та немедленно вылезла там, где раньше молча гасилась.
Сборка на деплое падала на пререндере `/opengraph-image`:

```
Error [PrismaClientKnownRequestError]: Invalid `prisma.siteContent.findUnique()` invocation
  code: 'ECONNREFUSED'
```

**Первопричина — не в SEO-слое, а в классификаторе ошибок.**
`isDatabaseConnectionError` (`backend/src/errors.ts`) знал только
`PrismaClientInitializationError` и код `P1001`. Но с драйверным адаптером
(`@prisma/adapter-pg`, обязателен с Prisma 7) отказ соединения может
прийти как `PrismaClientKnownRequestError`, у которого в `code` лежит
сырой сокетный код Node — `ECONNREFUSED`, — а не отображённый `P1001`.
Классификатор его не узнавал, перевода в `DatabaseUnavailableError` не
происходило, и `orDatabaseOutageFallback` совершенно правильно
пробрасывал незнакомую ошибку дальше.

**Сборка была лишь гонцом.** Та же дыра означала, что боевой Postgres,
отказывающий в соединении в этой форме, ронял бы страницы в `error.tsx`
вместо `<ServiceUnavailable/>` — то есть ровно тот сценарий, ради которого
весь фолбэк и существует. Незамеченной она оставалась потому, что
остановленный контейнер (как это проверялось руками) даёт форму
`PrismaClientInitializationError`, которую классификатор знал всегда.

**Исправлено расширением классификатора**: добавлены `P1002`/`P1017` и
набор сокетных кодов (`ECONNREFUSED`, `ECONNRESET`, `ENOTFOUND`,
`EHOSTUNREACH`, `ETIMEDOUT`, `EPIPE`). `P1000` (ошибка аутентификации)
намеренно НЕ добавлен: это неверно настроенный деплой, а не авария, и
прятать его за «база временно недоступна» значило бы обещать
восстановление, которого ожидание не принесёт.

Проверено воспроизведением сборки локально в точности как в CI
(плейсхолдерный `DATABASE_URL`, порт без слушателя) и обратным ходом: с
откаченным исправлением она падает тем же `ECONNREFUSED` на том же
маршруте, с исправлением — проходит. Отдельно проверено, что рантайм не
пострадал: при остановленном Postgres страница по-прежнему отдаёт 200 с
`noindex`, sitemap ужимается до трёх записей, после подъёма всё
восстанавливается.

**Второе исправление с того же review: отсутствие `max-image-preview:
large`.** При `IS_INDEXABLE` корневой layout не отдавал `robots` вообще —
казалось, что тег не нужен. Но дефолт отсутствующего тега это
`max-image-preview: standard`, миниатюра: сайт генерировал OG-карточку на
каждую страницу и тут же не давал её показывать, а Discover, требующий
`large`, был выключен. Теперь `robots` задаётся в обе стороны. Аудит
реального `<meta name="robots">` по всем маршрутам (а не чтение кода)

## 2026-08-10 — Фон OG-карточки: меш-градиент по тону категории, и вторая ловушка satori, найденная тем же способом, что и `oklch()`

**Что нужно сделать.** Пользователь: OG-карточка (заголовок, автор, дата,
плашка категории) должна теперь показывать элементы того же
меш-градиента, что и процедурная обложка поста, на своём фоне — не просто
крашеный акцентным цветом текст, как было сделано раньше в этой же
сессии.

**Как сделано, и какой был неверный первый ход.** Первая попытка добавить
фоновый слой использовала `position: "absolute", inset: 0` (стандартный
CSS-шорткат) поверх `radial-gradient(...)` в `backgroundImage`. Результат,
проверенный прямым рендером в PNG, а не угадан: **абсолютно плоский тёмный
фон, без единого намёка на градиент, без единой ошибки в консоли** — та же
форма отказа, что `render.tsx`'s уже существующий комментарий описывает
для `oklch()` (satori не поддерживает, но и не сообщает об этом). Проверка
по шагам (сначала `radial-gradient`, потом `linear-gradient`, потом явные
`top`/`left`/`width`/`height` вместо `inset`) показала: дело не в
градиентах вообще — оба типа градиента рендерятся корректно — а именно в
`inset: 0`, который satori молча игнорирует, из-за чего слой с фоном
схлопывается в элемент нулевого размера. Исправлено заменой на явные
`top: 0, left: 0, width: OG_SIZE.width, height: OG_SIZE.height` для
каждого абсолютно спозиционированного слоя.

Сам фон — три мягких `radial-gradient`-пятна (`rgba()`, не сплошной цвет:
альфа около 0.32, светлота/хрома НИЖЕ, чем у самой обложки поста, потому
что здесь под градиентом всегда стоит настоящий текст, а не пустая
область) через ту же `oklchToSrgbHex`, что уже используется для акцента
и для самой процедурной обложки — один тон приводит в движение и цвет
текста плашки категории, и фон, так что это выглядит как один
согласованный дизайн, а не два независимо раскрашенных элемента.
`OgCardProps.accent` (строка hex) заменён на `OgCardProps.hue` (число,
0-360) — теперь ЕДИНСТВЕННЫЙ параметр цвета всей карточки, и
`renderOgImage` сам решает, как из него получить и акцент, и фон, а не
получает уже готовый hex снаружи.

**Понятность для другого разработчика.** Обе ловушки satori
(`oklch()` и `inset`) роднит одно: ни одна не проявляется как ошибка —
обе тихо деградируют до "как будто ничего не произошло", и обе были
найдены ТОЛЬКО прямым рендером в PNG и просмотром глазами, не чтением
документации satori и не логами. Это ровно то, ради чего в этом
репозитории есть привычка "верифицировать вживую, не доверять 'должно
работать'" — здесь она поймала вторую по счёту, содержательно похожую
ловушку в том же самом файле.

**Нагрузка.** Три дополнительных `oklchToSrgbHex`-вызова и один
`radial-gradient` слой на рендер — рендерится РАЗ на (slug, locale) и
кешируется на час (`revalidate = 3600`), та же цена, что уже была у

**Расширяемость/заменяемость.** `meshBackgroundImage(hue)` — чистая

## 2026-08-11 — Найдено реальным a11y-тестом в CI: hue-акцент как ЦВЕТ ТЕКСТА не проходит контраст

`WorkDetailPage`'s пилюля "Case study" изначально была раскрашенным ТЕКСТОМ
(`Eyebrow` + `style={{color: accentColorForHue(hue)}}`) — та же lightness/
chroma (0.72/0.17), что у `palette.accent`. Живой прогон `a11y.spec.ts` в CI
упал на `color-contrast` для light-темы: 2.01-2.46:1 против нужных 4.5:1.

чернила (`StatusBadge`'s `text-accent-on-solid`), а не для текста напрямую
на фоне страницы; `lightPalette.accentText` (`theme/tokens.ts`) — отдельное,
руками затемнённое значение, подобранное для ОДНОГО фиксированного тона
(45°), которое произвольные per-проектные тона повторить не могут.

Проверено вычислительно (`oklchToSrgbHex` + формула контраста WCAG,
разброс тонов 0-345° с шагом 15°): как фон под тёмные чернила — 7.3-8.5:1

## 2026-08-12 — Прод: `/ru` падал с 500 (Internal Server Error) — не переводы, а известный баг Next.js за nginx

Срочный репорт: переключение на русский язык роняло сайт с 500. Первая
гипотеза (проверена и отброшена) — сломанные/неполные переводы: `en.json`/
`ru.json` (`shared/i18n/locales/`) сверены построчно — 97 ключей, идентичный
набор, обе валидный JSON, `pickFor`/`ln` и так безопасно откатываются на
`en` при отсутствующем ключе. Не туда.

Вторая гипотеза (тоже отброшена) — неверный `Host` в конфиге nginx
(`.scripts/provision/10-nginx-site.sh` уже ставит `proxy_set_header Host
$host;`, так что это не он). `curl -D -` на реальный прод/dev
(`dev.yuriisoft.me/ru`) показал настоящую причину прямо в заголовке ответа:
`x-middleware-rewrite: https://localhost:3001/?__locale=ru` — Next.js
пытается переписать `/ru/...` на URL со схемой `https`, хотя сам процесс
(`next start -H 127.0.0.1`, TLS только на nginx) говорит исключительно по
голому HTTP.

**Настоящая причина** — открытый баг апстрима,
[vercel/next.js#94745](https://github.com/vercel/next.js/issues/94745):
`request.nextUrl` внутри middleware нормализует ЛЮБОЙ loopback-хост
(`127.0.0.1`) в литеральную строку `"localhost"`, а серверный роутер
Next.js сравнивает эту строку с исходным, НЕнормализованным значением флага
`-H` (`"127.0.0.1"`) при решении, применять ли `NextResponse.rewrite()`
"внутри процесса" или проксировать по сети. Строки не совпадают →
Next.js считает rewrite "внешним" и реально ходит по сети сам к себе — с
унаследованной из `X-Forwarded-Proto: https` схемой `https`, на голый
HTTP-порт → `EPROTO`/`wrong version number` → 500 на КАЖДЫЙ `/ru`-запрос
(`/`, обычный английский путь, эту ветку `handleLocale` вообще не
проходит, поэтому был жив).

Воспроизведено вживую, не только прочтением кода: `next build && next
start -H 127.0.0.1` на локальной машине + `curl -H "X-Forwarded-Proto:
https"` — тот же самый 500 и тот же `x-middleware-rewrite: https://
localhost:.../…`. Пофикшено одной строкой в `handleLocale`
(`frontend/src/proxy.ts`): `url.protocol = "http:"` перед
`NextResponse.rewrite()` — цель rewrite'а это ВСЕГДА тот же самый процесс,
значит его схема должна быть постоянно `http`, независимо от схемы, с
которой пришёл исходный запрос. После фикса тот же самый repro отдаёт 200,
`<html lang="ru">`, корректные русские `title`/`og:*`.

Не стал переносить сам rewrite в `next.config.ts`'s `rewrites()` (тоже
рассматривался — конфиг-левел rewrite не проходит через этот конкретный
баг вовсе, так как не создаёт `x-middleware-rewrite`) — понижает риск
регрессии сильнее (`proxy.test.ts` уже пинит форму `handleLocale`'а 20
тестами, включая анти-cache-poisoning инвариант через `__locale` в URL);
однострочный фикс с точным комментарием и ссылкой на апстрим-баг — тот же
результат при на порядок меньшем диффе. Стоит вернуться к альтернативе,
если/когда апстрим смёржит правильный фикс (referenced PR #95917) и эта
строка станет не нужна.

Регрессионный тест (`proxy.test.ts`, "forces the rewrite target's protocol
to http...") сначала был написан неправильно — просто выставлял заголовок
`x-forwarded-proto: https` на `NextRequest`, что тест проходил ДАЖЕ БЕЗ
фикса (`NextRequest`, в отличие от реального сервера, не перекладывает этот
заголовок в `nextUrl.protocol` сам). Исправлено: тестовый `makeRequest()`
строит базовый `URL` сразу со схемой `https`, напрямую имитируя ФОРМУ
объекта, которую реальный серверный пайплайн Next.js уже успевает собрать
к моменту вызова middleware — проверено, что тест реально красный без
фикса и зелёный с ним (см. `mutation-testing.mdc`'s правило "докажи, что
тест ловит баг, а не просто проходит").

## 2026-08-14 — Реальный hydration mismatch на code-блоках, причина — глобальный автозапуск PrismJS

Пользователь принёс реальную консольную ошибку React: "A tree hydrated but
some attributes of the server rendered HTML didn't match the client
properties" — лишний `tabindex="0"` на `<pre>` и лишний `class="language-*"`
на `<code>`, которых `CodeBlockContent.tsx`'s JSX не задаёт вообще.

Воспроизведено вживую (не по коду): чистый `npm run dev` без кеша + Playwright
headless (без расширений браузера, чтобы исключить эту причину из списка
React) на `/journal/rtsp-...` — ошибка стабильно повторяется.

**Причина.** `import Prism from "prismjs"` сам по себе — не чистый импорт:
если не выставлен `Prism.manual`, модуль планирует СВОЙ собственный
`Prism.highlightAll()` (по `DOMContentLoaded` либо через `requestAnimationFrame`/
`setTimeout`), который сканирует ВЕСЬ документ на `pre[class*="language-"]`/
`code[class*="language-"]` и перекрашивает их напрямую в DOM — независимо от
и одновременно с гидратацией React тех же самых элементов, которые этот же
модуль уже подсветил через строковый API `Prism.highlight()`. Собственный
`highlightElement` из `prism-core.js` при этом безусловно ставит
`tabindex="0"` на родительский `<pre>`, если атрибута там ещё нет — отсюда
именно такой, а не любой другой, диф атрибутов.

**Исправлено** одной строкой в `codeHighlighter.ts` — `Prism.manual = true`
сразу после импорта. Безопасно ставить именно там: планирование автозапуска
всегда асинхронно (listener/rAF/setTimeout), а сам callback перечитывает
`Prism.manual` в момент реального срабатывания, а не в момент планирования.
Проверено вживую после фикса: тот же Playwright-прогон на холодном сервере —
ошибок гидратации нет, подсветка синтаксиса (`<span class="token ...">`)
работает как прежде.

**Тест.** `codeHighlighter.test.ts` пинит `Prism.manual === true` через
обычный top-level `import` — не `vi.resetModules()` + динамический `import()`
(тот приём уже дважды сработал в этот же день для точно такого же
`ignoreStatic`-случая на `shared/lib/seo/site-url.ts` и
`shared/ui/theme/adapters/project-graph.ts`). Здесь он, наоборот, сломал
Stryker'овскую per-test coverage-атрибуцию для ДРУГИХ тестов в том же файле:
`vi.resetModules()` в одном тесте увёл прогон `languageMap`/`highlightCode`
мутантов от тестов, которые их реально ловят (проверено руками: временная
мутация `ts: "typescript"` → `ts: ""` красит "wraps recognized tokens" при
прямом запуске, но Stryker с динамическим импортом в соседнем тесте
показывал её как `Survived`). Откатил обратно на top-level import; мутант
самого `Prism.manual = true` (единственная строка, которую это решение не
покрывает) принят как `Ignored` под `ignoreStatic` — не стал жертвовать
покрытием всего файла ради одной строки.
