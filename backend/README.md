# backend — серверная логика (npm workspace-пакет)

## Тесты

**Расположение тестовых файлов — рядом с кодом, не в отдельной папке.**
`password.test.ts` лежит рядом с `password.ts`, не в `backend/tests/`.
Обсуждали отдельно: co-location — стандартная конвенция Vitest/Jest
(находят тесты по умолчанию без специальной настройки glob-путей), не
влияет на то, что попадает в прод-сборку (проверено на собранном
`web/.next` — тестовые файлы туда не попадают независимо от того, где они
физически лежат, бандлер включает только то, что реально импортируется из
`src/index.ts`/`src/edge.ts`). Решено оставить co-location.


`npm test` (из `backend/`) — Vitest: юнит-тесты чистых функций
(`password.ts`, `tokens.ts`, `jwt.ts`, `rate-limit.ts`) и интеграционные
тесты, бьющие в настоящую тестовую БД (`session.ts`, `auth-service.ts`,
`create-admin-user.ts`) — таблицы очищаются перед каждым тестом
(`src/test-utils/db.ts`), не переиспользуются между файлами. Требует
отдельную БД `portfolio_test` (см. `.env.test.example`) — не ту же самую,
с которой вы работаете руками, чтобы тесты не удаляли ваши реальные
локальные данные.

Гоняется автоматически на каждый pull request и push в `master` через
[`.github/workflows/backend-web-checks.yml`](../.github/workflows/backend-web-checks.yml)
— там Postgres поднимается как эфemeral service-контейнер прямо в самом
workflow (не переиспользует ничего персистентного), мигрируется с нуля на
каждый прогон, плюс тайпчек `backend/` и полная сборка `web/` (`next build`)
— чтобы поймать не только логические баги, но и "сборка развалилась".

## Локальный запуск с нуля

```bash
# 1. Поднять локальный Postgres (docker-compose.yml в корне репозитория)
docker compose up -d

# 2. Установить зависимости всего workspace (из корня репозитория)
npm install

# 3. Скопировать backend/.env.example -> backend/.env, при необходимости
#    сгенерировать свой JWT_ACCESS_SECRET (минимум 32 символа)
cp backend/.env.example backend/.env

# 4. Прогнать миграции
cd backend && npx prisma migrate dev

# 5. Создать единственного admin-пользователя (интерактивно, без флагов)
npm run create-admin

# 6. Запустить сайт
cd ../web && npm run dev
```

`@portfolio/backend` — не отдельный сервис, а npm-пакет верхнего уровня,
который `web/` (Next.js) подключает как обычную зависимость через npm
workspaces. Рантайм всё равно один: один Next.js-процесс, один systemd-сервис
на VPS (см. журнал решений в `web/README.md`, записи про архитектуру backend
и про этот же путь). Сюда, начиная с Фазы 2 плана, переезжают: Prisma-схема
и клиент БД, авторизация (JWT/сессии), бизнес-логика (сервисы для
journal/work).

## 2026-07-18 — Как /backend стал npm workspace-пакетом, а не просто соседней папкой

**Что нужно сделать.** Разместить `backend/` рядом с `web/` на верхнем
уровне репозитория (явное пожелание — не вкладывать вглубь `web/src/`), но
так, чтобы это оставалось одной Next.js-сборкой/процессом, без отдельного
сервиса.

**Как сделано, шаг за шагом:**

1. Первая попытка — просто путь в `tsconfig.json` (`"@backend/*": ["../backend/src/*"]`),
   без npm-пакета. `next build` (сборщик Turbopack, дефолтный в Next.js 16)
   упал: `Module not found... Import map: aliased to relative
   '../backend/src/_smoke-test' inside of [project]/` — Turbopack
   принципиально не резолвит импорты, ведущие за пределы папки проекта,
   через "голый" путь.
2. Проверено: та же конструкция собирается с флагом `next build --webpack`
   без единой правки — старый бандлер (webpack) такого ограничения не
   имеет. Но это означало бы навсегда отказаться от Turbopack (быстрее,
   дефолт и будущее Next.js) во всех сборках и в `next dev`.
3. Выбран третий путь — **npm workspaces**: `backend/` получил свой
   `package.json` (`name: "@portfolio/backend"`), корень репозитория —
   `package.json` с полем `"workspaces": ["web", "backend"]` (`frontend/`
   сознательно не включён — у него свой независимый цикл установки/сборки,
   трогать его нельfor). `npm install` из корня создаёт symlink
   `node_modules/@portfolio/backend → ../backend`. Теперь это настоящий,
   резолвящийся через `node_modules` пакет — Turbopack прекрасно с этим
   работает, так же, как с любой другой библиотекой.
4. Так как `backend/` не компилируется заранее (нет своего build-шага,
   отдаёт исходный `.ts` прямо из `src/`), в `web/next.config.ts` добавлен
   `transpilePackages: ["@portfolio/backend"]` — иначе Next.js считает
   пакеты внутри `node_modules` уже собранными и не пропускает их через свой
   компилятор.
5. Проверено сборкой (`npm run build` в `web/`, дефолтный Turbopack) —
   `@portfolio/backend` резолвится и попадает в сборку.

**Понятность для другого разработчика.** `backend/package.json` явно
описывает, что это не отдельный сервис (см. его `description`). Импорт в
коде `web/` выглядит как обычная зависимость (`from "@portfolio/backend"`),
а не подозрительный относительный путь наверх (`../../backend/...`), что
понятнее и привычнее.

**Нагрузка.** Никакой лишней нагрузки в рантайме — `transpilePackages`
влияет только на этап сборки, итоговый бандл не отличается от того, как если
бы код лежал прямо в `web/src`.

**Расширяемость/заменяемость.** Самое ценное следствие: если backend
когда-нибудь действительно понадобится вынести в отдельный сервис (см.
план, Фаза 6, "если нужно будет масштабировать backend независимо"),
`@portfolio/backend` уже оформлен как самостоятельный пакет со своими
зависимостями (`backend/package.json`) — не нужно будет "выковыривать" код
из середины Next.js-приложения, только заменить транспорт (прямой вызов
функции → HTTP-клиент).

**Миграция данных / отказоустойчивость.** Не применимо к этому шагу — пакет
пока пустой (`BACKEND_PACKAGE_READY`-заглушка), реальные данные и Prisma
появятся в Фазе 2.

**SOLID.** Dependency Inversion в чистом виде: `web/` зависит от публичного
API пакета `@portfolio/backend` (то, что экспортирует его `src/index.ts`),
а не от внутренней структуры файлов — `backend/` может полностью
переорганизовать свою внутреннюю структуру, не задев `web/`, пока публичный
экспорт из `index.ts` не меняется.

## 2026-07-27 — Мутационное тестирование (StrykerJS): проверка, что тесты реально что-то проверяют

**Что нужно сделать.** Ввести mutation testing как практику — code coverage
отвечает только на вопрос "выполнилась ли эта строка во время теста?", а не
"заметит ли тест, если эта строка неверна?". Задача: не просто подключить
инструмент, а реально прогнать его на существующих тестах и исправить
найденные декоративные тесты, а не просто завести конфиг. Полное описание
идеи/механики — `.cursor/rules/mutation-testing.mdc`.

**Как сделано, включая находки по дороге (не только финальный результат):**

1. **Область: не весь `src/`.** `stryker.config.mjs`'s `mutate` — явный
   список чисто-логических файлов без обращений к БД (`auth/{password,
   tokens,jwt,rate-limit}.ts`, `content/{blocks,reading-time}.ts`,
   `errors.ts`), а не весь `src/`. Интеграционные тесты (`auth-service.ts`,
   `session.ts`, `content/{document,site-content,work,posts,admin-posts,
   admin-work}.ts`) бьют в реальный Postgres и уже гоняются с
   `fileParallelism: false` — прогонять их по разу на каждый мутант было бы
   очень медленно и превратило бы любую заминку БД в мутационно-тестовую
   "нестабильность", не связанную с качеством тестов.
2. **Первая находка (сломанное предположение): `stryker.config.mjs`,
   указывающий на обычный `vitest.config.ts`, заставлял "dry run" (нужен
   `@stryker-mutator/vitest-runner` для построения карты покрытия per-test)
   гонять ВЕСЬ обнаруженный набор тестов — точно как `vitest run` — а не
   только связанные с `mutate`. `vitest.related` ограничивает лишь то, что
   перезапускается на каждый отдельный мутант, а не сам dry run. Итог:
   первый прогон упал с реальной ошибкой БД ("The database is temporarily
   unavailable") локально, без поднятого Docker — то есть весь смысл
   "исключить интеграционные тесты" ломался этим же dry run. Исправлено
   отдельным `vitest.mutation.config.ts` с явным `include` только нужных
   тестовых файлов — теперь `npm run test:mutation` не требует БД вообще.
3. **Вторая находка:** 4 файла из первоначального списка
   (`content/{slug,locale,localized-text,site-content-defaults}.ts`) не
   импортируют Prisma сами, но и не имеют СОБСТВЕННОГО юнит-теста — их
   покрывают только интеграционные тесты (`site-content.test.ts`/
   `work.test.ts`). Мутировать их означало бы либо всё равно требовать БД,
   либо получить сплошной `NoCoverage`. Убраны из `mutate` до появления у
   них прямых тестов — задокументировано в `stryker.config.mjs`.
4. **Реальный прогон вскрыл настоящие декоративные тесты** (не гипотеза —
   проверено запуском): `jwt.ts` — ни один тест не проверял payload с
   ПРАВИЛЬНОЙ подписью, но НЕПРАВИЛЬНЫМИ типами полей (`sub`/`email`/`role`
   не строки), и ни один не проверял, что НЕ-JOSE-ошибка действительно
   прокидывается наружу, а не проглатывается как "невалидный токен";
   `errors.ts` — `isUniqueConstraintError` вообще не был протестирован
   (0% покрытия, не просто выжившие мутанты), сообщения об ошибках
   (`DatabaseUnavailableError`, `SlugAlreadyExistsError`) никогда не
   проверялись по содержимому, `formatValidationError` никогда не
   тестировался на вложенном пути (`.join(".")` неотличим от `.join("")`
   на пути из одного сегмента) или на нескольких issues одновременно
   (разделитель `"; "`); `blocks.ts` — блоки `"quote"` и `"note"` (успешный
   путь) и `data`-поля блока `"image"` никогда не парсились в тестах вообще;
   `rate-limit.ts` — ни один тест не фиксировал ТОЧНОЕ значение
   `retryAfterSeconds`, ни точную границу истечения окна (`resetAt < now`
   против `<=`), из-за чего мутант, ломающий сброс счётчика после истечения
   окна, выживал молча. Все эти пробелы закрыты реальными новыми
   тестами (не увеличением coverage ради цифры) — см. `git log`/дифф
   каждого `*.test.ts` файла для точных примеров.
5. **Настоящие эквивалентные мутанты — задокументированы, не проигнорированы
   молча.** Пара примеров: `password.ts` — `{type: argon2.argon2id}` →
   `{}` не меняет поведение, потому что argon2id и есть дефолт самой
   библиотеки `argon2` (проверено вызовом `argon2.hash()` без опций и
   разбором префикса хэша `$argon2id$...`); `reading-time.ts`'s
   `countWords` — `.trim()` и `\s+` (вместо `\s`) доказуемо избыточны при
   уже имеющемся `.filter(Boolean)` (проверено вручную на нескольких
   строках). Каждый такой случай — комментарий `// Stryker disable
   next-line <мутатор>` прямо у кода с объяснением, ПОЧЕМУ он эквивалентен,
   а не голая заглушка.
6. **Находка про сам механизм disable-комментариев (Windows/Stryker, не
   гипотеза — воспроизведено):** комментарий `// Stryker disable next-line`,
   поставленный ПЕРЕД многострочным объяснением (объяснение ПОСЛЕ
   директивы) не сработал для мутанта внутри цепочки `.replace()` в
   `slugify.ts`'s аналоге на стороне `web/` (см. `web/README.md`) — Stryker
   молча не отключил мутант. Рабочий паттерн, подтверждённый повторным
   прогоном: объяснение СНАЧАЛА, короткая директива `// Stryker disable
   next-line <мутатор>` ПОСЛЕДНЕЙ строкой прямо перед кодом.
7. **Найденный баг в СОБСТВЕННОМ новом тесте** (не в исходном коде):
   `jwt.test.ts`'s тест на прокидывание не-JOSE-ошибки сначала был написан
   без `await` перед `expect(...).rejects.toThrow(...)` — `finally` успевал
   восстановить `process.env.JWT_ACCESS_SECRET` ДО того, как промис
   реально урегулировался, что превращало это в необработанное отклонение
   промиса, всплывавшее асинхронно и приписываемое Stryker'ом случайному
   ДРУГОМУ мутанту/тесту (статус `# errors`, не `# survived`). Найдено по
   нестабильному `# errors` между повторными прогонами одного и того же
   набора тестов, не сразу — исправлено добавлением `await`.
8. **Производительность:** `ignoreStatic: true` в обоих `stryker.config.mjs`
   — сам Stryker предупредил, что статические мутанты (код,
   выполняющийся один раз при загрузке модуля) — 18% мутантов, но ~92%
   времени прогона.
9. **CI:** `test:mutation` — обязательный, блокирующий шаг в
   [`.github/workflows/backend-web-checks.yml`](../.github/workflows/backend-web-checks.yml)
   для `backend/` и `web/`, после обычных `vitest run`. Node в этом workflow
   поднят с 20 до 22 — только здесь, только потому что
   `@stryker-mutator/vitest-runner` требует Node ≥22.

**Понятность для другого разработчика.** `.cursor/rules/mutation-testing.mdc`
объясняет и сам образ мышления (какую мутацию тест обязан ловить), и
механику конкретно этого репозитория (почему область именно такая, где
живут пороги, как реагировать на выжившего мутанта) — не нужно заново
изобретать подход при следующем изменении `mutate`-списка.

**Нагрузка.** Реальный локальный прогон — единицы секунд для `backend/`
(74 теста, 218 мутантов) при `ignoreStatic: true`; на CI добавляет заметное,
но некритичное время к и без того не мгновенному job'у (мигрировать БД +
собрать `web/`).

**Расширяемость/заменяемость.** Список `mutate` — это явная, растущая со
временем граница: если `content/{slug,locale,localized-text,
site-content-defaults}.ts` когда-нибудь получат собственные юнит-тесты, их
можно сразу добавить в список без переделки остальной конфигурации.

**Миграция данных / отказоустойчивость.** Не применимо напрямую к данным —
но пункт 9 (Node 20 → 22 только в одном workflow) стоит держать в уме при
следующем изменении CI: остальные workflow’ы (`deploy-web.yaml`,
`visual-tests.yml`, `accept-visual-baselines.yml`, `deploy_release.yaml`)
намеренно НЕ тронуты, чтобы не менять поведение легаси-`frontend/`-пайплайна
заодно.

**SOLID.** Скорее методология тестирования, чем структура классов — но по
духу это тот же принцип, что и Dependency Inversion: тест обязан зависеть
от НАБЛЮДАЕМОГО ПОВЕДЕНИЯ функции (что она реально возвращает/бросает), а
не от факта, что какая-то её строка исполнилась.

## 2026-08-06 — `tech-slug.ts` добавлен в область мутационного тестирования

**Что нужно сделать.** Новый чистый файл (`content/tech-slug.ts` — см.

юнит-тесты "для галочки" — по правилу репозитория, он обязан пройти

**Как сделано.** Добавлен в `mutate` (`stryker.config.mjs`) И в `include`

файла собственный комментарий), забыть второй даёт 0% покрытия без единой

использует ИМЕННО `vitest.mutation.config.ts`'s `include`, не обычный
`vitest.config.ts`, а этот список ведётся вручную. Исправлено добавлением

выглядел как "тесты не написаны", хотя на деле файл с тестами просто не
был виден Stryker'у. Оставлено в этой записи, а не тихо исправлено, чтобы
следующий разработчик, добавляющий файл в `mutate`, не наступил на то же.

**Нагрузка/расширяемость/миграция.** Не применимо — тот же самый список,
та же самая механика, просто на одну строку длиннее в двух местах.

**SOLID.** Не применимо напрямую — эта запись про сам процесс мутационного
тестирования, не про структуру кода.

## 2026-08-08 — Не редактируйте `migration.sql` после того, как она применена

Prisma держит контрольную сумму каждого файла миграции. Дописанный
постфактум комментарий в уже применённую `migration.sql` означает, что
следующий `prisma migrate dev` откажется работать и предложит
**сбросить dev-базу целиком** («The migration ... was modified after it
was applied. We need to reset the "public" schema»). Наткнулся на это на
ровном месте: пояснение, почему у `contentUpdatedAt` нет бэкфилла, было
дописано в SQL уже после применения.

Правильный порядок — либо писать комментарий ДО первого применения (так
сделана `20260731220041_post_work_lifecycle_state` с её ручным
бэкфиллом), либо не трогать файл вовсе: место для «почему» — doc-комментарий
