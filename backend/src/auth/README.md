# backend/src/auth — авторизация (Фаза 2)

Единственный сегодня администратор, но спроектировано так, чтобы несколько
пользователей/устройств и будущий мобильный клиент не требовали редизайна
— см. обсуждение в исходном плане миграции.

## Что здесь и почему именно так

**Access-токен — JWT (`jwt.ts`), refresh-токен — не JWT, а случайная строка
(`tokens.ts`).** Access-токен живёт 15 минут, проверяется по подписи без
обращения к базе (дёшево, можно проверять в `middleware.ts` на каждый
запрос). Refresh-токен живёт 30 дней и обязан быть отзываемым (устройство
потеряли, вышли вручную) — а раз он всё равно всегда сверяется с базой
(`Session.refreshTokenHash`), кодировать его как JWT не даёт вообще ничего,
только увеличивает размер и добавляет второй секрет. Обычная случайная
строка (32 байта, `crypto.randomBytes`) проще и ровно так же безопасна для
этого случая.

**`jose`, не `jsonwebtoken`, для JWT.** `jsonwebtoken` работает только в
Node.js-рантайме (использует модуль `crypto` напрямую). `middleware.ts` в
Next.js по умолчанию выполняется в Edge-рантайме, где модуля `crypto` в
привычном виде нет. `jose` работает поверх Web Crypto API — одинаково в
Node и в Edge, так что не будет сюрприза "middleware не запускается,
потому что библиотека рассчитана только на Node".

**Argon2id, не bcrypt, для паролей (`password.ts`).** Текущая рекомендация
OWASP #1 для хеширования паролей; в `argon2` для Node есть готовые
prebuilt-бинарники под основные платформы, включая Linux/Alpine на VPS —
не проблема сборки из исходников на сервере.

**Refresh-токен хешируется SHA-256 (`tokens.ts`), не Argon2.** Пароль —
что-то, что человек мог выбрать слабым ("123456"), поэтому его хеш должен
быть медленным и дорогим для перебора. Refresh-токен — 256 бит случайных
данных, которые НИКТО не подбирает перебором (перебирать 2^256 вариантов
бессмысленно) — здесь важна быстрая проверка, а не "дорогая" защита от
словарной атаки, которой тут просто нет.

## 2026-07-18 — Смягчение user-enumeration через тайминг при логине

**Что нужно сделать.** `login(email, password)` должен возвращать одинаковую
ошибку и на "email не существует", и на "email существует, пароль неверный"
— иначе злоумышленник может перебором e-mail'ов узнавать, какие аккаунты
существуют.

**Как сделано.** Наивная реализация (`if (!user) return null` до вызова
`verifyPassword`) была бы уязвима: когда пользователя нет, ответ приходит
почти мгновенно (не считая один быстрый SQL-запрос), а когда пользователь
есть — ответ ждёт дорогую argon2-проверку (специально дорогую, это весь
смысл argon2!). Замер времени ответа выдаёт, существует ли email, даже без
знания пароля. Исправлено: если пользователь не найден, код всё равно
прогоняет `verifyPassword` против заранее посчитанного "фиктивного" хеша
(посчитан один раз за время жизни процесса, не на каждый запрос) — время
ответа одинаковое в обоих случаях.

**Понятность для другого разработчика.** Комментарий у `getDummyHash()`
прямо объясняет атаку, которую это предотвращает — без него строка выглядела
бы как непонятный лишний вызов.

**Нагрузка.** Один лишний argon2-вызов на КАЖДЫЙ неудачный логин с
несуществующим email — приемлемо: неудачные попытки логина не горячий путь,
а argon2 всё равно рассчитан на то, чтобы быть в меру дорогим.

**Расширяемость/заменяемость.** Не влияет — чисто внутренняя деталь
`login()`, наружу (HTTP-эндпоинт) виден только `null | AuthResult`.

**Миграция/отказоустойчивость.** Не применимо (нет схемы/данных, только
поведение функции).

**SOLID.** Single Responsibility соблюдён по слоям: `password.ts` не знает
про тайминг-атаки (просто hash/verify), `auth-service.ts` — единственное
место, отвечающее за то, чтобы внешний ответ не утекал информацию о том,
какой из двух факторов (email/пароль) был неверным.

## 2026-07-19 — Тест сразу нашёл реальный баг в `verifyAccessToken`

**Что нужно сделать.** Написать unit-тесты на `jwt.ts` (Vitest,
см. `backend/vitest.config.ts`).

**Как сделано.** Тест `verifyAccessToken("не-jwt-строка")` и
`verifyAccessToken("")` неожиданно не вернули `null`, а бросили необработанное
исключение `JWSInvalid: Invalid Compact JWS`. Причина: `catch`-блок ловил
только два конкретных подкласса ошибок `jose` —
`JWTExpired`/`JWSSignatureVerificationFailed` — а `jose` в реальности бросает
разные подклассы `JOSEError` в зависимости от того, ЧТО не так с токеном:
подпись не совпала — один подкласс; строка вообще не в формате JWT
(мусор/пустая строка) — другой (`JWSInvalid`). Ручное тестирование раньше
проверяло только "испорченный настоящий токен" (подделанная подпись — это
и есть единственный подкласс, который был обработан), поэтому баг не
проявлялся. Исправлено: ловится базовый класс `joseErrors.JOSEError`
целиком — любая ошибка ОТ `jose` означает "невалидный токен", а не
исключительную ситуацию для вызывающего кода.

**Понятность для другого разработчика.** Комментарий в `catch`-блоке прямо
объясняет, почему нужен именно базовый класс, а не перечисление подклассов
— чтобы никто не "исправил" обратно на более узкий список при рефакторинге.

**Нагрузка/расширяемость/миграция.** Не применимо — исправление корректности,
не архитектуры.

**SOLID.** Не впрямую применимо — это просто иллюстрация того, зачем
нужны тесты: баг существовал с самой первой версии файла, прошёл ручное
End-to-End тестирование (Фаза 2) незамеченным, и был найден в первый же
день, когда появились автоматические тесты.

## 2026-07-27 — Сессия перестаёт "внезапно рваться": тихий рефреш + переезд rate limiter на Redis

**Что нужно было сделать.** Три реальные жалобы одновременно: (1) долгая
работа в админке обрывалась истечением 15-минутного access-токена без
какого-либо использования уже существующего 30-дневного refresh-токена;
(2) при обрыве в fetch-запросе (не при переходе по странице) админ
оставался на месте с непонятной ошибкой вместо редиректа на логин; (3)
login rate limiter был in-memory (`Map`) — при горизонтальном
масштабировании (несколько инстансов Node за балансировщиком) каждый
инстанс считал бы попытки независимо, лимит фактически размывался бы в N
раз.

**Как сделано.**

1. **Тихий рефреш, в двух слоях, не одном.** Проактивный: клиент
   (`web/src/shared/lib/session-keepalive.tsx`) сам вызывает
   `/api/auth/refresh` каждые ~10 минут, но ТОЛЬКО пока вкладка видима
   (`document.visibilityState`) — не бесконечный фоновый таймер, сессия не
   должна продлеваться сама по себе, пока никто на неё не смотрит.
   Реактивный: `web/src/shared/lib/admin-api.ts`'s `request()` — при 401
   сам делает один `/api/auth/refresh` и повторяет исходный запрос ровно
   один раз; если и это не помогло (refresh-токен тоже мёртв) — явный
   `window.location.assign("/admin/login?from=...")`, а не молча
   проглоченная ошибка. `?from=` уже поддержан `AdminLoginPage` — после
   повторного входа админ возвращается ровно туда, откуда его унесло.

2. **Кто вообще может звать конкретный route — теперь решает сам route.**
   `web/src/proxy.ts` раньше был единственным местом, проверяющим JWT и
   решающим "admin или нет" по префиксу пути. Это заменено на
   `resolvePrincipal`/`defineAdminRoute`/`requirePage`
   (`web/src/shared/lib/auth/`, см. его README) — каждый route/page сам
   декларирует нужный scope, а не полагается на то, что proxy уже
   проверил. `proxy.ts` теперь занимается только тем, что физически может
   знать на уровне формы URL: locale-роутинг и rate limiting (ниже) —
   полное рассуждение, почему middleware в принципе не может нести
   детальную авторизацию, в комментарии самого `proxy.ts`.

3. **Rate limiter — с in-memory `Map` на Upstash Redis.** `rate-limit.ts`
   переписан вокруг одного примитива `RateLimiter.checkAndRecord(key,
   limit, windowSeconds)` за интерфейсом — `UpstashRateLimiter` в
   продакшене (когда заданы `UPSTASH_REDIS_REST_URL`/`_TOKEN`),
   `InMemoryRateLimiter` как локальный/тестовый фолбэк. Заодно упрощена
   семантика: раньше `checkLoginRateLimit`/`recordFailedLogin` считали
   ТОЛЬКО неудачные попытки (успешный логин "прощал" предыдущие опечатки),
   теперь `checkAndRecord` считает КАЖДУЮ попытку — проще (один вызов
   вместо двух в `login/route.ts`) и строже одновременно: старая версия
   давала возможность подбирать пароль бесконечно долго, изредка вставляя
   правильную попытку, чтобы счётчик не срабатывал. `resetLoginRateLimit`
   после успешного входа по-прежнему прощает предыдущие опечатки. Логин
   теперь проверяется по ДВУМ независимым ключам одновременно (per-IP И
   per-account) — распределённый подбор одного аккаунта с разных IP и
   подбор много аккаунтов с одного IP ловятся оба, ни один не ловился бы
   только одним измерением.

**Понятность для другого разработчика.** `web/src/shared/lib/auth/
README.md` — почему авторизация переехала на route/page, а не осталась
таблицей путей (там же — какой первый вариант отвергли и почему).
`rate-limit.ts`'s комментарии объясняют, почему это fixed window, а не
честный sliding window (осознанный компромисс, не недосмотр).

**Нагрузка / горизонтальное масштабирование.** Это единственная фаза,
которая реально закрывает последний stateful угол системы — до неё
JWT-проверка уже была stateless, но login rate limiting был in-memory на
процесс. Теперь весь путь запроса — от проверки токена (чистая CPU, без
похода в БД) до rate limiting (общий Redis) — корректен на любом числе
Next.js-инстансов за балансировщиком без какой-либо координации между ними
сверх самого Redis/Postgres.

**Отказоустойчивость.** Без `UPSTASH_REDIS_REST_URL`/`_TOKEN` в окружении
rate limiting молча откатывается на `InMemoryRateLimiter` — работает
локально/в тестах без реального Upstash-аккаунта, но защищает только ОДИН
процесс, не флот инстансов; это осознанный, документированный фолбэк, не
скрытая деградация.

**SOLID.** `RateLimiter` — интерфейс, `auth-service.ts`/`proxy.ts` знают
только про `checkAndRecord`/`reset`, не про то, Redis это или `Map`
(Dependency Inversion) — смена бэкенда (например, на self-hosted Redis
позже) не трогает ни одного вызывающего места.

**Как `UPSTASH_REDIS_REST_URL`/`_TOKEN` реально попадают на VPS.** Первый
заход был неверным: скрипт (`.scripts/set-app-env.sh`), который админ
руками запускает со своей машины через SSH с `sudo` на произвольные
команды — не подошёл по двум причинам сразу: (1) у деплой-аккаунта
(`yuriisoft`) вообще нет прав на `shared/.env` (0700, `nextapp`) и никогда
не было — это осознанное разделение прав, не забытая настройка; (2)
"руками с ноутбука" — это не автоматизация, которую просили. Исправлено:
узкий root-хелпер `.scripts/set-app-env-finish.sh` (устанавливается один
раз через `.scripts/provision/12-set-app-env-helper.sh`, вместе с точечным
`sudoers`-правилом только на этот бинарник) теперь вызывается
**автоматически из `deploy-web.yaml`** при каждом деплое — значения берутся
из GitHub Actions secrets (`UPSTASH_REDIS_REST_URL_DEV`/`_PROD` и т.д.), не
вводятся человеком. Только add/update, никогда auto-delete — пропавший
секрет в CI просто пропускает шаг (`continue-on-error`), а не стирает уже
рабочее значение на сервере. `DATABASE_URL`/`JWT_*` **сознательно** не
участвуют в этом механизме и не появятся в GitHub Actions — их сброс вживую
обнуляет все сессии или рвёт подключение к БД, это должно остаться
осознанным ручным действием (`provision/06-app-env.sh`), а не побочным
эффектом обычного деплоя.

## Ротация refresh-токенов (`session.ts`)

Каждый успешный `refreshSession()` отзывает использованный refresh-токен и
выдаёт новый — токен нельзя использовать повторно. Если украденный
refresh-токен когда-нибудь "срабатывает" ПОСЛЕ того, как легитимный клиент
уже успел обновиться (и старый токен уже отозван), попытка провалится — это
само по себе сигнал компрометации.

## 2026-08-06 — OWASP-аудит: сигнал компрометации фиксировался, но не использовался

Запись выше ("стоит логировать в будущем") описывала именно то, что и
происходило до этой даты: реплей уже отозванного токена корректно
проваливался сам по себе, но ничего больше не делал — если атакующий
перехватил ОДИН ответ ротации, у него мог быть и токен, на который клиент
только что перешёл, а этот токен продолжал бы работать сам по себе
неограниченно долго.

**Первая версия (неверная) и что в ней нашли.** Первый заход:
`detectReuseAndRevokeFamily` реагировал на ЛЮБУЮ строку `Session` с
`revokedAt !== null` (и не истёкшую) — включая отозванные через явный
`revokeSession` (logout с одного устройства) или
`revokeAllSessionsForUser`. Уже существующий тест
(`revokeSession`'s "revokes only the targeted session, leaving other
sessions for the same user active") немедленно упал: обычный logout с
одного устройства A, за которым следует повторное предъявление ТОГО ЖЕ
токена A (например, запрос, который уже был в полёте на клиенте), massively
отзывал вообще ВСЕ сессии пользователя, включая совершенно не связанное
устройство B — ровно то поведение, которое `revokeSession` существует,
чтобы НЕ делать.

**Исправлено — новое поле различает ПРИЧИНУ отзыва.** `Session` получил
`replacedBySessionId String?` (миграция
`20260807003602_session_replaced_by_session_id`) — заполняется РОВНО
`rotateSession`'ом, в момент, когда он отзывает старую строку из-за
выпуска новой; `revokeSession`/`revokeAllSessionsForUser` его никогда не
трогают. `detectReuseAndRevokeFamily` теперь проверяет
`revokedAt !== null && replacedBySessionId !== null && expiresAt >= now()`
— то есть реагирует именно на "этот токен был заменён РОТАЦИЕЙ, и кто-то
предъявил его снова", а не на "этот токен был отозван по ЛЮБОЙ причине".

**Понятность для другого разработчика.** Комментарий у
`detectReuseAndRevokeFamily` прямо называет первую (неверную) версию и
какой именно тест её поймал — та же дисциплина "неверная первая гипотеза
остаётся в записи", что и везде в этом README.

**Нагрузка.** Один дополнительный `UPDATE` (уже была одна запись за
ротацию) плюс один `UPDATE ... WHERE userId = ? AND revokedAt IS NULL`
(уже существовавший `revokeAllSessionsForUser`) — только в случае
реального обнаружения реплея, не на каждый обычный refresh.

**Расширяемость/заменяемость.** `replacedBySessionId` — простое строковое
поле без Prisma `@relation`: связь используется только для чтения по уже
полученной по первичному ключу строке (не JOIN), так что полноценная
self-relation добавила бы сложность без реальной нужды в ней.

**Миграция/отказоустойчивость.** Новое поле nullable, накатано и на
локальную dev-, и на тестовую (`portfolio_test`) базы — существующие
строки `Session` получают `NULL` автоматически, не требуя backfill (уже
отозванные до этой миграции строки просто никогда не будут восприняты как
"реплей ротации", что и корректно: у них физически нет данных о том, что
их заменило).

**SOLID.** Single Responsibility: `findSessionRow` (безусловное чтение)
теперь явно отделена от `findValidSession` (то же чтение + фильтр
"валидна ли") — `detectReuseAndRevokeFamily` нужен именно безусловный
вариант, чтобы отличить "неизвестный токен" от "известный, но отозванный
токен", а `findValidSession` эту разницу всегда стирала.

## 2026-08-06 — OWASP-аудит: отказ Upstash валил вообще ВСЕ запросы

**Что нужно сделать.** До этой даты `getRateLimiter()` тихо выбирал
`InMemoryRateLimiter`, если `UPSTASH_REDIS_REST_URL`/`_TOKEN` не заданы —
без единого предупреждения, даже в проде. А если креды заданы, но Upstash
временно недоступен, `UpstashRateLimiter.checkAndRecord()` бросал реальную
сетевую ошибку прямо в `frontend/src/proxy.ts`, которая ничего не ловила —
`enforceRateLimit` вызывается для КАЖДОГО запроса (см. `proxy.ts`'s
`matcher`), так что один сбой Redis клал вообще весь сайт, включая
статические страницы.

**Как сделано — не там, где буквально просил план, но по той же причине.**
Инструкция была "оберни `checkRateLimit` в try/catch в `proxy.ts`" — вместо
этого resilience-слой (`checkAndRecordResilient`) живёт в самом
`rate-limit.ts`, откуда его получают И `checkRateLimit` (тиры `proxy.ts`),
И `checkLoginRateLimit`/`resetLoginRateLimit` (`login/route.ts`) — у
`login/route.ts` РОВНО ТА ЖЕ уязвимость к сбою Upstash, что и у `proxy.ts`,
и дублировать try/catch в обоих местах означало бы два определения "что
считается восстановимым", которые могли бы разойтись. Два разных сценария
разведены явно, не одним общим catch-всё:

1. **Никогда не настроено (баг деплоя)** — `getRateLimiter()` теперь
   бросает `RateLimiterMisconfiguredError`, если `NODE_ENV === "production"`
   и кредов нет (кроме случая `DISABLE_RATE_LIMIT === "true"` — тот же
   флаг, что уже существует только для Playwright-suite, чей
   `next build && next start` сам ставит `NODE_ENV=production`, как
   настоящий деплой, но без реального Upstash). Эта ошибка НЕ ловится
   `checkAndRecordResilient` — распространяется дальше, специально: цель —
   провалиться громко на первом же запросе после плохого деплоя, а не
   молча работать со слабой защитой от брутфорса неопределённо долго.
2. **Временный сбой (сеть/Redis недоступен)** — реальный, а не
   гипотетический сбой самого `checkAndRecord()`/`reset()` перехватывается
   и падает на ОДИН общий `InMemoryRateLimiter`-fallback на весь процесс
   (не свежий экземпляр на каждый вызов — иначе счётчик никогда бы не
   накопился до реального лимита).

`RateLimiterMisconfiguredError` отличается по `.name`, не `instanceof` —
та же причина, что и `isDatabaseUnavailableError` в `errors.ts`
(Turbopack компилирует `@portfolio/backend`/`@portfolio/backend/edge`
раздельно на границе Server Component/Route Handler/Edge-proxy).

**Проверено вживую, не только юнит-тестом с мок-объектом.** Отдельный
одноразовый скрипт (`.tmp-verify-rate-limit-resilience.ts`, запущен через
`npx tsx` и удалён после проверки — не часть кодовой базы) реально
направил `@upstash/redis`'s настоящий клиент на несуществующий хост:
`checkRateLimit()` получил настоящую `ENOTFOUND`-ошибку от Node-стека DNS,
залогировал её и вернул `{ allowed: true }`, не бросив исключение. Второй
прогон того же скрипта, с `NODE_ENV=production` и полностью отсутствующими
кредами, подтвердил, что `RateLimiterMisconfiguredError` действительно
бросается с ожидаемым именем и сообщением.

**Понятность для другого разработчика.** Комментарий у
`checkAndRecordResilient` прямо называет, почему `RateLimiterMisconfiguredError`
специально пропускается НЕ через тот же fallback, что и всё остальное —
без этого объяснения кто-то мог бы "исправить" код так, чтобы ловить и её
тоже, тихо возвращая ту самую ситуацию, которую эта запись существует,
чтобы предотвратить.

**Нагрузка.** Не хуже прежнего в счастливом пути (одна попытка через
настоящий лимитер); на пути отказа — на один локальный
`InMemoryRateLimiter.checkAndRecord()`-вызов больше, что дешевле, чем сам
провалившийся сетевой запрос.

**Расширяемость/заменяемость.** `checkAndRecordResilient` — единственное
место, которое решает "что делать, когда лимитер падает" — новый вызывающий
код (будущий route) автоматически получает ту же защиту через
`checkRateLimit`, без необходимости знать про try/catch вообще.

**Миграция/отказоустойчивость.** Прямое отношение — это и есть фикс
отказоустойчивости: раньше временная недоступность Upstash была
single point of failure для всего сайта, теперь это единственный слабый
слой (rate-limiting на один процесс вместо распределённого), а не полный
отказ.

**SOLID.** Single Responsibility: `getRateLimiter()` отвечает только за
"какой backend выбрать и валидно ли окружение", `checkAndRecordResilient`
— только за "что делать, если ВЫБРАННЫЙ backend падает при вызове" — два
разных вопроса, ранее не разделённых вообще (второго вопроса не
существовало до этой правки).

**Поправка от 2026-08-06 (найдено PR-ревью, не при написании) —
`resetLoginRateLimit` чистил не то состояние.** Первая версия
`resetLoginRateLimit` вызывала `.reset()` только на НАСТРОЕННОМ лимитере
— но именно во время затянувшегося отказа Upstash (тот самый сценарий,
ради которого существует весь этот fallback) счётчик успешной попытки
входа накапливается в `fallbackLimiter`, а не в настроенном лимитере
(см. `checkAndRecordResilient` выше). Сброс только настроенного —
недостижимого в этот момент — лимитера НИЧЕГО не делал со счётчиком
fallback'а: он продолжал расти при каждом успешном входе на всём
протяжении отказа. У этого приложения ровно один admin-аккаунт
(`prisma/schema.prisma`'s комментарий у `User`) — несколько подряд
успешных входов во время реального отказа (возможно, именно ПОТОМУ что
админ пытается разобраться с этим же отказом) в итоге упирались бы в
лимит fallback'а и отдавали 429 настоящему, корректно
аутентифицирующемуся администратору — то есть resilience-слой,
существующий именно для того, чтобы сайт оставался доступным во время
отказа, делал вход МЕНЕЕ доступным в тот же самый момент.

**Исправлено.** `resetLoginRateLimit` теперь безусловно вызывает
`fallbackLimiter.reset(...)`, если `fallbackLimiter` вообще существует —
`InMemoryRateLimiter.reset()` на ключе, которого там нет, безвредный
no-op (`Map.delete` отсутствующего ключа), так что не нужно отдельно
знать, использовался ли fallback для этого конкретного ключа.

**Проверено вручную, а не только рассуждением.** Тест
(`rate-limit.test.ts`, "resetting after a successful login clears the
fallback's count too...") специально прогнан ПРОТИВ старой, неверной
версии (временный откат правки, без блока `if (fallbackLimiter) {...}`)
— упал именно так, как ожидалось (`AssertionError: expected false to be
true` на 6-м цикле), затем правка восстановлена и тот же тест снова
прошёл. Математика теста намеренно нетривиальна: лимит — 5, проверка —
`count > limit`, так что РОВНО 5 несброшенных попыток ещё читаются как
разрешённые (5 > 5 — ложь) — нужен именно 6-й цикл, чтобы тест был
настоящим различием "баг/фикс", а не совпадением, проходящим в обоих
случаях.

## 2026-08-06 — OWASP-аудит: JWT/Argon2 hardening + удаление мёртвого `JWT_REFRESH_SECRET`

**Что нужно сделать.** Четыре мелких, но реальных пробела:
`JWT_ACCESS_SECRET` принимался без проверки длины (короткий/угадываемый
HS256-секрет брутфорсится offline); `jwtVerify` не закреплял `algorithms`/
`issuer`/`audience` явно; Argon2-параметры стоимости зависели от дефолтов
библиотеки, не были закреплены явно; `JWT_REFRESH_SECRET` требовался
`.env.example`/`06-app-env.sh`, но ничего в приложении его не читает —
refresh-токены opaque (`tokens.ts`), не JWT.

**Как сделано.** `jwt.ts` получил `MIN_ACCESS_SECRET_LENGTH = 32`,
проверяемую в `getAccessSecret()` на КАЖДОМ вызове (не только при старте
процесса — секрет читается из `process.env` каждый раз, так что смена
переменной среды между вызовами тоже должна быть подхвачена, что и
проверяет отдельный тест). `TOKEN_ISSUER`/`TOKEN_AUDIENCE` — константы,
не env-настраиваемые (единственный issuer/audience в системе, делать их
настраиваемыми добавило бы только способ рассинхронизировать их друг с
другом), устанавливаются на подписи и проверяются на верификации вместе с
явным `algorithms: ["HS256"]`. `password.ts` закрепил `memoryCost:
65536, timeCost: 3, parallelism: 4` явно в объекте опций — тот же паттерн
"защита от смены дефолта библиотеки в будущей версии", что и раньше был
только у `type: argon2id`.

**Мутационное тестирование — не просто прогнано, а доведено до 100%
именно в изменённых файлах.** Первый прогон после этих правок дал
`jwt.ts` 100%, но `password.ts` — 66.67%: расширенный объект опций
(`{type, memoryCost, timeCost, parallelism}`) целиком заменялся Stryker'ом
на `{}`, и ни один тест этого не ловил (существовавший тест проверял
только префикс `$argon2id$`, не сами числа стоимости внутри хеша). Добавлен
тест, парсящий `$m=...,p=...,t=...$` прямо из СГЕНЕРИРОВАННОГО хеша и
проверяющий точные числа — после этого тот же мутант (`{}`) оказался
**подтверждённо эквивалентным** (проверено вручную:
`argon2.hash(x, {})` даёт БАЙТ-В-БАЙТ тот же `$argon2id$v=19$m=65536,p=4,
t=3$...`-профиль, что и явный вызов — те же дефолты node-argon2, что и
раньше), поэтому помечен `// Stryker disable next-line ObjectLiteral` с
объяснением ПЕРЕД директивой (порядок комментария/директивы важен — см.
`.cursor/rules/mutation-testing.mdc`), а не тестом. Итог: `password.ts`
100%, `jwt.ts` 100%, общий скор файла `rate-limit.ts` (задет тем же
проходом — см. запись про resilience выше) поднялся с 89.58% до 97.92%,
единственный оставшийся выживший мутант там — строка `ttl > 0 ? ttl :
windowSeconds`, которая существовала до этой правки и не была ею
затронута (не в скоупе этой конкретной задачи).

**Понятность для другого разработчика.** `getAccessSecret()`'s комментарий
прямо называет, что это "консервативная замена энтропии счётчиком
символов", не настоящая проверка случайности — не переоценивает, что эта
проверка реально гарантирует.

**Нагрузка.** Незначительная — одна проверка длины строки на вызов,
`.setIssuer()`/`.setAudience()` — те же операции, что `jose` уже делает
для `sub`/`exp`/`iat`.

**Расширяемость/заменяемость.** `TOKEN_ISSUER`/`TOKEN_AUDIENCE` экспортированы
(не приватные) специально, чтобы тесты могли подписывать "настоящие"
токены напрямую через `jose`, минуя `signAccessToken`, без дублирования
строковых литералов, которые могли бы разойтись с реальными константами.

**Миграция/отказоустойчивость.** `JWT_REFRESH_SECRET` удалён из
`.env.example` и `06-app-env.sh` (последний теперь также ОТКАЗЫВАЕТСЯ
писать `.env`, если `JWT_ACCESS_SECRET` короче 32 символов — та же
проверка, что и в самом приложении, но на шаге provisioning, до того как
плохой секрет попадёт в реальный деплой). Уже развёрнутые `.env`-файлы с
существующим `JWT_REFRESH_SECRET` не ломаются — переменная просто
перестаёт быть где-либо прочитанной, а не отсутствие переменной не
проверяется как ошибка.

**SOLID.** Не применимо структурно — hardening существующих проверок, не
новая архитектура.

## 2026-07-28 — `checkAndRecord` был не атомарным: `incr` + `expire` двумя раундтрипами

**Что нужно было сделать.** PR-ревью (комментарий от codex-connector, реальный
бот-ревьюер, не гипотетический сценарий) указал на `UpstashRateLimiter.
checkAndRecord`: `incr` и `expire` шли двумя отдельными вызовами к Redis. Если
процесс прерывается (или сам HTTP-запрос `expire` к Upstash падает по сети)
ровно между ними, ключ в Redis остаётся СЧЁТЧИКОМ БЕЗ TTL. Каждый следующий
вызов продолжает его инкрементировать — счётчик уже выше лимита, TTL никогда
не появится, чтобы окно когда-либо сбросилось, и ключ блокируется навсегда.

**Как сделано.** Инкремент и установка `expire` слиты в ОДНУ Lua-команду
(`redis.eval(script, keys, args)` — публичный метод `@upstash/redis`,
единственный сетевой раунд-трип, скрипт целиком выполняется на стороне
Redis). `RedisCommands.incr`/`.expire` заменены на один `RedisCommands.eval`
— интерфейс по-прежнему структурно совпадает с реальным клиентом
`@upstash/redis` (никакого адаптера не понадобилось, проверено
`tsc --noEmit`), так что `UpstashRateLimiter` остаётся так же
юнит-тестируемым на голом mock-объекте, как и раньше.

**Понятность для другого разработчика.** Комментарий у `INCR_AND_EXPIRE_SCRIPT`
прямо объясняет атаку/баг, который это предотвращает (со ссылкой на то, что
это найдено реальным ревью, а не придумано заранее) — чтобы никто не
"упростил" это обратно в два вызова при рефакторинге.

**Тесты.** Старый тест ("sets expiry only on the first increment") спайил
`redis.expire` — с этим методом исчезнувшим тест переписан на прямой счётчик
`expiryCalls` внутри мока. Добавлен отдельный тест, который пинит именно
атомарность (`toHaveBeenCalledTimes(1)` на `eval`, а не на две команды) — без
него регрессия обратно на `incr`+`expire` прошла бы все прежние тесты
незамеченной, потому что они проверяли только конечный результат (аллоу/блок,
TTL), а не механизм.

**Нагрузка.** Не хуже прежнего — было 1-2 сетевых вызова на проверку (incr,
иногда + expire), стало ровно 1 (`eval`) на первом хите окна и 1 на
последующих — на один вызов МЕНЬШЕ в общем случае, не больше.

**Миграция/отказоустойчивость.** Не требует миграции данных — чисто смена
механизма записи в тот же ключ Redis с тем же форматом значения (целое
число). Отказоустойчивость строго улучшилась: раньше частичный сбой
(`incr` прошёл, `expire` — нет) оставлял битое состояние в Redis без
возможности самовосстановления; теперь такой промежуточной фазы физически не
существует — либо применились оба redis-вызова внутри скрипта, либо ни один
(сетевой сбой ДО того, как Redis получил `EVAL`, не меняет состояние вообще).

**SOLID.** Не меняет форму интерфейса `RateLimiter`/`RedisCommands` с точки
зрения вызывающего кода — `checkLoginRateLimit`/`checkRateLimit` не в курсе,
что изменился протокол внутри `UpstashRateLimiter` (Open/Closed:
реализация эволюционировала, контракт наружу — нет).

## 2026-07-28 — Фоновые `<Link>`-префетчи Next.js делили бюджет с реальной навигацией

**Найдено:** реальным падением e2e visual-suite в CI, не гипотетически.
Baseline-скриншот одной из journal-страниц оказался снимком JSON-ответа
`{"error":"Too many requests."}` — во время прошлого прогона
`/update-snapshots` `global`-лимит (`proxy.ts`, 300 запросов / 5 минут)
успел исчерпаться собственным же фоновым трафиком suite'а раньше, чем
Playwright сделал реальный скриншот.

**Почему это не только про тесты.** Root cause общий и для прода тоже:
App Router сам автоматически префетчит КАЖДУЮ видимую на экране `<Link>` —
без единого клика пользователя. Страница со списком из 10+ карточек может
легитимно сгенерировать десяток фоновых запросов на один реальный визит.
Все они раньше считались в тот же `global:${ip}` бакет, что и настоящие
переходы — реальный посетитель с длинным списком открытых ссылок в
принципе мог словить лимит от действий собственного браузера, не от
чего-то, что он сам сделал.

**Как исправлено.** `enforceRateLimit` (`proxy.ts`) проверяет заголовок
`next-router-prefetch` (его App Router сам проставляет на все фоновые
префетчи) и заводит для них ОТДЕЛЬНЫЙ тир — `prefetch:${ip}`, лимит 900
(3× от `global`) за то же окно 5 минут — вместо общего с `global`.

**Почему НЕ просто исключить префетчи из лимита вообще.** Заголовок
проставляет клиент — его тривиально подделать в сыром HTTP-запросе. При
этом "префетч" внутри выполняет ТОЧНО ту же серверную работу (тот же
Server Component, тот же запрос к БД), что и настоящая навигация. Полное
исключение означало бы: злоумышленник просто добавляет
`next-router-prefetch: 1` к каждому запросу — и полностью обходит
`global`. Отдельный, более щедрый, но всё ещё ограниченный тир закрывает
и легитимный кейс (много фоновых префетчей — это нормально), и этот
конкретный обходной путь (свой потолок у "префетч"-трафика тоже есть).

**Тесты.** `proxy.ts` до этого не имел вообще ни одного теста — добавлен
`frontend/src/proxy.test.ts`, пинящий именно механизм (реальная навигация
исчерпывает `global`, но НЕ мешает следующему префетч-запросу с того же
IP; у префетчей свой отдельный потолок), а не просто "не падает".
Потребовалось экспортировать `InMemoryRateLimiter`/
`setRateLimiterForTesting` из `@portfolio/backend/edge` — раньше не были
доступны ни оттуда, ни из основного входа пакета, тестировать
`proxy.ts` было просто нечем.

**Нагрузка.** Не хуже прежнего — то же число реальных Redis-вызовов на
запрос (один `eval` на тир), просто на другой ключ для префетчей.

**Миграция/отказоустойчивость.** Не применимо — новый Redis-ключ появится
сам по себе при первом же префетч-запросе, старые `global`-счётчики
продолжают работать как раньше для настоящей навигации.

**Поправка от 2026-07-29 — этот тир на самом деле не работает в реальном
деплое.** При отладке отдельного бага (клик по `<Link>` не редиректился на
`/error/429` — см. `frontend/src/shared/ui/status-page/README.md`'s
запись за ту же дату) живой дамп заголовков ВНУТРИ `enforceRateLimit`,
против настоящего `next dev` И `next build && next start` (не только
против юнит-теста), показал: `request.headers.get("next-router-prefetch")`
всегда `null` — Next.js вырезает этот заголовок (вместе с `rsc`,
`next-router-state-tree`) из `request.headers` до того, как Proxy его
увидит. Это задокументированное поведение самого Next.js (см. страницу
`proxy` в их официальной документации), не баг именно этого приложения.
Практическое следствие: `isPrefetch` выше сегодня ВСЕГДА `false` на
реальном сервере, значит фоновые префетчи по-прежнему делят бюджет
`global` с настоящей навигацией — ровно та проблема, которую эта запись
считала решённой. Тест `proxy.test.ts`, описанный выше, по-прежнему
корректно проверяет логику самой функции (если бы заголовок дошёл, ветка
сработала бы правильно) — он не может поймать эту проблему, потому что
конструирует `NextRequest` напрямую, в обход реального конвейера запроса
Next.js, где и происходит вырезание. Код проверки оставлен как есть
(безвредный no-op, не мешает и не создаёт риска) — фактическое исправление
разделения бюджетов помечено как отдельная, сознательно не решённая задача
в комментарии `proxy.ts`.
