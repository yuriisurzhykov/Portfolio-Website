# backend/scripts — create-admin

## Почему только интерактивный ввод, без флагов/env для пароля

Пароль администратора не принимается ни как CLI-флаг (остаётся в истории
шелла и в `ps`/Task Manager на время выполнения), ни как переменная
окружения (тогда бы пришлось держать реальный пароль в `.env` файле на
диске). Только интерактивный ввод в консоли — пароль существует в памяти
процесса ровно те несколько секунд, что нужны на хеширование, и нигде не
сохраняется в открытом виде.

## 2026-07-18 — Маскированный ввод пароля зависал при пайпе данных

**Что нужно сделать.** Проверить `create-admin.ts` перед тем, как считать
его готовым.

**Как сделано.** Тест через `echo "email`npass`npass" | npm run create-admin`
завис и был прерван по таймауту. Причина: `promptPassword()` включает
`process.stdin.setRawMode(true)` для маскировки ввода звёздочками — это
работает только с настоящим TTY. У пайпнутого stdin TTY нет, поэтому вызов
либо падает, либо (как здесь) просто никогда не эмиттит нужные события —
скрипт зависает навсегда, без вывода ошибки. Добавлена проверка
`process.stdin.isTTY` — если это не терминал, используется обычный
`readline`-промпт без маскировки (тот же, что для email), вместо
зависания.

**Понятность для другого разработчика.** Без этой проверки поведение
скрипта в CI/автоматизации выглядело бы как необъяснимое зависание —
комментарий в коде прямо называет причину.

**Нагрузка/расширяемость/миграция.** Не применимо.

**SOLID.** Не применимо — защитная проверка окружения выполнения, не
структурное решение.

## 2026-07-18 — Второй, более серьёзный баг: скрипт "успешно" завершался, не создав пользователя (и одна неверная гипотеза по дороге)

**Что нужно сделать.** Проверить сценарий выше ещё раз после фикса с TTY.

**Как сделано, честно включая неверный первый диагноз:**

1. Скрипт отработал с кодом выхода 0, без единой ошибки — но прямой запрос
   к базе (`prisma.user.findMany()`) показал пустой массив: пользователь не
   создался.
2. **Первая гипотеза (оказалась неверной)**: подумал, что дело в том, что
   `prompt()` создавал новый `readline.createInterface` на каждый вопрос и
   закрывал его сразу после ответа — предположил, что при пайпнутом stdin
   это "теряет" уже забуферизованные, но не считанные строки. Переписал на
   один общий `readline.Interface` на весь скрипт.
3. Тест **всё равно упал** — но с другой, куда более информативной
   ошибкой: `Error [ERR_USE_AFTER_CLOSE]: readline was closed`, при попытке
   задать второй вопрос (про пароль). Это вскрыло настоящую причину:
   `readline` в Node.js сам закрывается, когда его input-поток эмиттит
   `'end'` — а при пайпнутом vводе (`echo "..." | script`) весь stdin
   передаётся и сразу закрывается почти одновременно с тем, как
   разрешается первый `question()`. Проблема была не в "потере
   забуферизованных строк между несколькими readline", а в том, что
   **множественные последовательные `question()`-вызовы через readline
   органически ненадёжны на пайпнутом/неинтерактивном stdin** — вне
   зависимости от того, один экземпляр `readline.Interface` или несколько.
   На настоящем интерактивном терминале это никогда не проявляется
   (пользователь физически не закрывает stdin между вопросами).

**Итоговое решение — не бороться с readline+pipe, а изменить архитектуру.**
Вынес саму бизнес-логику (валидация email/пароля, проверка на
существующего пользователя, хеширование, создание записи) в отдельную,
чистую функцию `createAdminUser(email, password)` в
`src/auth/create-admin-user.ts` — её можно вызвать напрямую с
фиксированными аргументами, без stdin/readline вообще. `create-admin.ts`
остался тонкой интерактивной обёрткой вокруг неё, которую нет смысла
пытаться автоматически тестировать через pipe — она проверяется один раз
вручную, как обычный CLI-инструмент для человека.

**Понятность для другого разработчика.** Комментарий в
`create-admin-user.ts` объясняет, почему логика вынесена отдельно —
включая ссылку на то, что порождало проблему, чтобы никто не попытался
"упростить" обратно в один файл и не наткнулся на то же самое.

**Нагрузка.** Не меняется — то же количество операций с БД/хешированием,
просто в отдельной функции.

**Расширяемость/заменяемость.** Заметно лучше: `createAdminUser()` можно
вызвать не только из интерактивного CLI, но и из будущего HTTP-эндпоинта
приглашения нового пользователя (Фаза 4+, если появится мультипользователь)
— бизнес-правило не привязано к тому, что ввод обязательно приходит из
терминала.

**Миграция/отказоустойчивость.** Прямое отношение: без этого фикса
"успешный" (exit code 0) запуск скрипта в каком-то будущем
автоматизированном сценарии (например, provisioning-скрипт при первом
деплое на VPS) мог бы молча не создать администратора — обнаружилось бы
это только при попытке залогиниться, что плохой отказоустойчивый сценарий.
Теперь бизнес-правило само по себе не зависит от того, как в него попали
данные, так что подобный класс "тихого" сбоя для НЕГО в принципе не
существует — можно написать честный unit-тест на `createAdminUser()`
напрямую, без манипуляций со стримами.

**SOLID.** Прямое применение Single Responsibility: "получить учётные
данные от человека" (I/O, тонкая обёртка) и "создать администратора по
готовым email+паролю" (бизнес-правило) — теперь два разных модуля с
разной причиной для изменения. Это же и хороший урок для всего процесса:
"выглядит рабочим при интерактивном запуске" — не то же самое, что
"корректно"; баг был невидим в нормальном интерактивном использовании и
проявлялся только при автоматизированном/пайпнутом vводе, что было ровно
тем сценарием, которым я и тестировал скрипт вместо реального ввода с
клавиатуры.

## 2026-07-19 — `split-bilingual-documents.ts` — разделение смешанных Document на EN/RU

**Что нужно сделать.** До этой миграции каждый `Document` (тело поста,
нарратив кейс-стади) хранил блоки со смешанным `text: {en, ru}` —
переводы жили внутри каждого блока. Новая модель — язык на уровне
`Document` целиком (`Post.bodyDocumentId`/`bodyDocumentIdRu`, аналогично
для `Work`), так что весь уже импортированный контент нужно физически
разложить на пары EN/RU документов, без ручного восстановления вручную.

**Как сделано.** `blockHasOldShape(block)` определяет, несёт ли блок
старую форму (`text`/`data.alt`/`approachList[].title|description`
как `{en, ru}`) — если ни один блок документа её не несёт, документ
пропускается (`skip (already split)`), что делает скрипт безопасным для
повторного запуска: ничего не задваивается, если он уже отработал (или
если документ был написан заново через новый BlockNote-редактор, который
всегда пишет обычные строки). Для документов со старой формой —
`createSplitDocument(blocks, "en"|"ru")` создаёт ДВА новых `Document`
(через `pickLocale`/`splitBlockData`, по одному вызову на язык), затем
старый смешанный `Document` удаляется (каскадно чистит его `Block`-строки).
RU-документ создаётся только если хоть один блок реально нёс непустой
русский текст (`blockHasNonEmptyRu`) — у существующих данных это всегда
так (импорт изначально писал оба языка полностью), но правило общее, не
основанное на предположении "все документы одинаковы".

Запущен один раз против локальной dev-базы (см. корневой план, шаг
проверки) — 4 поста и 7 проектов с кейс-стади успешно разделены,
повторный запуск подтверждённо ничего не изменил (`skip` на все 11).

**Понятность для другого разработчика.** `blockHasOldShape`/
`blockHasNonEmptyRu` держат тот же список "где может быть `{en, ru}`"
намеренно, а не через общий рекурсивный обход JSON — в `blocks.ts`'s схеме
на момент написания скрипта это ровно 3 места (`text`, `image.data.alt`,
`approachList.data.items[].title/description`), написать это явно —
единственный способ быть уверенным, что не пропущено ни одно, ни лишнее.

**Расширяемость.** `import-legacy-content.ts` (Фаза 3's скрипт) обновлён
в ту же сессию, чтобы производить УЖЕ разделённые EN/RU документы напрямую
(`toLocaleBlocks`) — свежий импорт на пустую базу больше не создаёт
старую форму вообще, так что `split-bilingual-documents.ts` нужен только
для базы, где уже накопился контент в старой форме до этой миграции
(включая эту самую dev-базу).

**Миграция/отказоустойчивость.** Ключевое инвариант-требование
("не потерять контент, не задвоить") проверено не рассуждением, а прогоном
против реальной базы + сравнением `document`/`block`-счётчиков до/после
(см. `getPostBySlug`/`getWorkBySlug`'s тесты на locale-фолбэк, которые
затем проверили, что и EN, и RU-версии действительно читаются).

**SOLID.** Single Responsibility по функциям: `splitBlockText`/
`splitBlockData` не знают про `Post`/`Work` вообще, только "как выглядит
блок в старой/новой форме"; `migratePosts`/`migrateWork` не знают, как
устроен блок внутри, только вызывают `splitDocument()` и обновляют FK.

## 2026-07-27 — `seed-e2e-fixtures.ts` — детерминированные фикстуры для `web/tests/`

**Что нужно сделать.** У `web/tests/` (Playwright visual/a11y suite, портированный из
`frontend/tests/`) появился новый источник данных для списка страниц — вместо статического
импорта `@/data/work`/`@/data/journal` теперь настоящий Postgres через `@portfolio/backend`. Первая
рабочая версия этого порта (описана в `web/tests/README.md`) ходила прямо в РЕАЛЬНУЮ dev-базу
(`backend/.env`) — это сработало и было проверено вживую, но пользователь указал, что решение о
стратегии данных для тестов нужно было обсудить ДО реализации, а не после: контент в dev-базе
постоянно меняется (новые проекты, новые посты через админку), из-за чего suite перестаёт быть
"регрессионным" в буквальном смысле — сравнение идёт не с фиксированной точкой, а с постоянно
двигающейся целью.

**Как сделано.** Новый скрипт хард-ресетит `backend/.env.test`'s `portfolio_test` (никогда не
`.env`'s реальную dev-базу) и заливает маленький, фиксированный набор фикстур: 3 work-айтема
(2 с кейс-стади разных вариантов шаблона — с hero-изображением и без, 1 без кейс-стади вообще) и
3 поста (2 с телом — один с code-блоком, один без, 1 "upcoming"-заглушка без тела вообще).
Специально покрыты ОБЕ ветки обоих фильтров, которые `web/tests/e2e/generate-pages-manifest.ts`
применяет (`hasCaseStudy`/"есть настоящее тело") — иначе эти фильтры существовали бы в коде, но
никогда реально не проверялись бы прогоном на противоположной ветке. Данные заводятся через
`createWork`/`createPost` (`content/admin-work.ts`/`content/admin-posts.ts`) — те же функции, что
вызывают ручки админки — а не через прямые `prisma.work.create`/`prisma.post.create`, чтобы не
дублировать логику создания `Document`/`Block` для кейс-стади/тела во втором месте.
`resetTestDatabase()` (`src/test-utils/db.ts`) переиспользован как есть — та же операция "очистить
все таблицы", что уже использует собственный интеграционный Vitest-suite `backend/`.

В отличие от `seed-site-content.ts` (идемпотентный, никогда не перезаписывает), этот скрипт —
жёсткий reset-then-seed при каждом запуске: visual/a11y-покрытию нужен именно фиксированный набор
каждый раз, а не "что осталось с прошлого прогона плюс это". Запускается через `npm run
seed-e2e-fixtures` (`dotenv -e .env.test -- tsx scripts/seed-e2e-fixtures.ts`), которую `web/`'s
`test:e2e*`/`test:visual`/`test:a11y` npm-скрипты вызывают автоматически перед генерацией манифеста
и запуском Playwright — см. `web/tests/README.md`, разделы 4 и 12 (запись "Correction" от
2026-07-27) для полного разбора, включая три альтернативных подхода (fake in-memory backend через
build-time alias, MSW + Next.js `testProxy`, изоляция через Storybook), которые обсуждались и
осознанно отложены в backlog, а не отвергнуты.

**Проверено вживую, а не "должно работать":** запущен два раза подряд против настоящего
`portfolio_test` (подтверждает, что reset-then-seed идемпотентен — никаких ошибок уникальности от
"хвостов" прошлого запуска), затем отдельно проверено прямым запросом к DEV-базе
(`prisma.work.count()` с `DATABASE_URL` из `.env`), что количество строк там не изменилось — сидинг
никогда не касается реального контента. Полный e2e-прогон (`generate-pages-manifest.ts` →
`next build && next start` → `test:a11y`) против засеянных данных: 14/14 тестов прошли.

**Понятность для другого разработчика.** Комментарий в самом скрипте прямо называет, ПОЧЕМУ это
`.env.test`, а не `.env` — а не просто "как", чтобы никто не "исправил" это обратно на dev-базу, не
зная историю.

**Нагрузка.** Не применимо — разовый запуск перед тестовым прогоном, не рантайм сайта.

**Расширяемость/заменяемость.** Добавить новый вариант шаблона (например, кейс-стади с
image-галереей) — добавить ещё один элемент в `FIXTURES.work`/`FIXTURES.posts`, ничего больше не
трогая; `generate-pages-manifest.ts` подхватит его автоматически при следующем прогоне.

**Миграция/отказоустойчивость.** Прямое отношение: без изоляции от dev-базы миграция схемы или
ручное редактирование контента через админку могли бы незаметно сломать e2e suite, не будучи
никак связаны с реальным багом в коде — ровно тот класс "тихой" нестабильности, которого этот
скрипт существует, чтобы избежать.

**SOLID.** Не новая структура, а повторное использование существующей (Dependency Inversion в
широком смысле): скрипт зависит от `createWork`/`createPost`/`resetTestDatabase` — уже
существующих абстракций записи данных — а не от деталей схемы Prisma напрямую.

## 2026-08-10 — `backfill-post-covers.ts` — обложки для постов, созданных до фичи процедурных обложек

**Что нужно сделать.** `createPost` (см. `backend/src/media/README.md`)
генерирует обложку автоматически только для постов, созданных ПОСЛЕ того,
как эта фича появилась. У всего, что уже было в базе, `coverAssetId`
остаётся `null` навсегда — и ничто это само не исправляет: `publishPost`
для уже опубликованного поста без реального черновика — осознанный no-op
(см. `admin-posts.ts`'s комментарий), путь до генерации обложки там даже
не вызывается. Простой клик "Update" в редакторе не помогает.

**Как сделано.** Проходит по ВСЕМ постам (включая черновики — тот же
уровень консистентности, что `createPost` уже даёт свежим постам), для
каждого вызывает `ensureCoverMatchesCategory` с его текущими реальными
title/category/excerpt. Безопасен к повтору — для поста, у которого
обложка уже соответствует текущей категории, это один дешёвый индексный
`findUnique`, без записи (та же функция, что уже вызывается из
`publishPost`, просто применённая массово).

**Проверено вживую** против реальной локальной базы (8 постов): первый
прогон — 7 обложек сгенерировано, 1 уже актуален; повторный прогон — все
8 "already up to date", ни одной лишней записи.

**Понятность для другого разработчика.** Тот же паттерн, что уже
использовал `split-bilingual-documents.ts` выше — "старый контент не
проходил через логику, которая появилась позже" — не первый раз, когда
это возникает в этом репозитории, и не последний (см. следующую запись).

**Расширяемость.** Ничего специфичного для обложек в самом паттерне
скрипта — обёртка над уже существующей идемпотентной функцией.

**Миграция/отказоустойчивость.** Прямое отношение — это и есть миграция
данных для уже накопленного контента.

**SOLID.** Single Responsibility: скрипт не знает, ПОЧЕМУ обложка может
не совпадать с категорией — он просто вызывает уже существующую функцию,
которая это знает (`ensureCoverMatchesCategory`), для каждого поста.

### Отложено осознанно — общий раннер для одноразовых скриптов при деплое

Пользователь спросил, почему такие скрипты (уже третий раз за историю
репозитория: `split-bilingual-documents.ts`, `seed-e2e-fixtures.ts`
частично, теперь `backfill-post-covers.ts`) нужно запускать руками через
SSH, а не автоматически на деплое — справедливый вопрос, паттерн реально
повторяется.

**Почему не сделано прямо сейчас.** Два разных довода, оба весомые
самостоятельно:

1. **Безопасность.** `deploy-frontend-finish.sh` — root-привилегированный
   скрипт, вызываемый через узкое sudoers NOPASSWD-правило именно
   ПОТОМУ, что делает ровно одну фиксированную, аудируемую вещь.
   "Выполни ещё и произвольный код из `backend/scripts/`" — это ровно
   та дыра, которую узость правила существует, чтобы закрыть.
2. **Разная критичность сбоя.** `prisma migrate deploy` обязан быть
   блокирующим шагом до переключения релиза — без него новый код не
   может работать с новой схемой. Прикладной бэкфилл (генерация
   картинок, запись на диск) — нет: если он упадёт, сайт всё равно
   должен подняться на новом коде; блокировать релиз ради этого
   неправильно.

**Рекомендованный дизайн, если/когда до этого дойдут руки** (обсуждался с
пользователем, не реализован):

- Новая таблица `ScriptRun` (`name @unique`, `runAt`) — трекает, какие
  одноразовые скрипты уже выполнялись, тот же принцип, что Prisma уже
  применяет к себе через `_prisma_migrations`.
- Конвенция: одноразовые data-миграции живут в
  `backend/scripts/data-migrations/`, каждая экспортирует `run()`.
- Один раннер, который проходит по папке, пропускает уже отмеченные в
  `ScriptRun`, выполняет новые, отмечает выполненные.
- Вызывается из `deploy-frontend-finish.sh`, но **ПОСЛЕ**
  `systemctl restart`, не блокирующим шагом — падение раннера не должно
  ронять деплой.

**Когда возвращаться к этому решению:** пользователь предпочёл ручной
процесс "по требованию" на этом этапе — пересмотреть, когда накопится
больше примеров таких скриптов (сигнал: четвёртый-пятый одноразовый
скрипт подряд, который снова придётся объяснять "как запустить на
проде" в чате).

## 2026-07-19 — `seed-site-content.ts` — идемпотентный посев Фазы 5

В отличие от `import-legacy-content.ts` (переносит существующий контент из
файлов один раз, при пустой базе) и `split-bilingual-documents.ts`
(разовая миграция формы хранения), этот скрипт рассчитан на повторные
запуски: для каждого `SiteContentKey` он проверяет `findUnique` и создаёт
строку ТОЛЬКО если её ещё нет — никакого `upsert` с `update: {}`, потому
что даже пустой `update` всё равно продвинул бы Prisma-колонку
`@updatedAt`, сделав её лживой для секции, которую администратор уже
отредактировал вручную через `/admin/settings/[key]`. Источник данных —
`content/site-content-defaults.ts`, то же самое определение, на которое
опирается фолбэк внутри `getSiteContent()` (см.
`content/README.md`'s разбор Фазы 5) — не отдельная копия контента, которая
могла бы разойтись с тем, что видит посетитель сайта до первого запуска
этого скрипта.
